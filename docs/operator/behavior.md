# Operator-visible behavior and boundaries

This page states what atrium does and refuses to do today. It describes current behavior only. Setting names, types and defaults live in the generated [setting reference](../config/reference.md) and are not repeated here.

## Access

- `atrium serve` binds `127.0.0.1` unless told otherwise. `--auth` selects how a listener authenticates and can be repeated: `proxy` (the default), `oidc`, and `local`. `proxy` and `oidc` can be combined; `local` cannot be combined with another mode. A listener in proxy or oidc mode refuses to start without an accepted Host (`--allowed-host`, or the public host setting).
- Local mode is the emergency path and binds only a numeric loopback address (`127.0.0.1` or `::1`). `atrium serve --auth local` exits non-zero for a wildcard, unspecified, hostname or other non-loopback `--host`.
- **Emergency listener.** `atrium serve --emergency-port <port>` also serves a local-mode listener from the same process on `--emergency-host` (default `127.0.0.1`), which must be a numeric address in `127.0.0.0/8` or `::1`; a hostname, wildcard, zone or other address exits non-zero before the database opens. It shares the database, settings, API tokens (issue and revocation) and background services with the public listener, but has its own rate limiter. The public listener keeps its own auth modes, Host check, CSRF and bearer-only API unchanged.
- **Listeners before readiness.** Serve binds the public, emergency and ops listeners before it starts background services or signals `READY=1`. If any bind fails, for example two listeners on one port, every socket bound so far is closed and serve exits non-zero without `READY=1`. If a listener fails after startup, serve marks itself stopping, shuts the other listeners down and exits non-zero. Serve sends `READY=1` once and `STOPPING=1` once. Every request on a local listener must also arrive from a loopback socket peer; forwarded address headers never make a non-loopback peer local. A local listener keeps the Host allowlist, CSRF and same-origin checks.
- `atrium serve` refuses to start and exits non-zero when proxy or oidc mode has no accepted Host (`--allowed-host`, or the public host setting). There is no flag that serves without authentication on a non-loopback address.
- Every request except `GET /healthz` must carry an accepted Host header; any other Host receives `400`.
- In proxy mode the request must carry a `Remote-Groups` header that lists `atrium_access`, otherwise it receives `403`. Static assets under `/static/` and valid signed media links are exempt from the group check. The Host check still applies to them. An admitted proxy request is the one operator with full authority. In a listener that does not select proxy mode, `Remote-Groups` and every other proxy header grant nothing. A listener that combines proxy and oidc mode trusts `Remote-Groups` from whoever can reach it, so the reverse proxy must strip or overwrite every `Remote-*` header on every request; run OIDC alone (`web.auth = "oidc"`) when the listener is reachable without such a proxy.
- In oidc mode a request needs a valid session, otherwise a page navigation is redirected to `/login` (with `next` for the page asked for), an htmx request receives `401` with `HX-Redirect`, and any other request is redirected to `/login`. Only `GET /healthz`, static assets, valid signed media links, `/login` and `/auth/callback` answer without a session. In a listener without oidc mode `/login`, `/auth/callback` and `/logout` answer `404`.
- Sign-in is the authorization code flow with PKCE (`S256` always; a provider that does not advertise `S256` is refused), a state value bound to the browser by a cookie, a nonce, and ID token verification (signature against the provider's JWKS with rotation, issuer, audience, expiry, nonce). Group names come from the configured claim in the ID token, with the userinfo endpoint as fallback. Any matching admitted selector grants the one operator: a group in `access_groups` (default `atrium_access,atrium_admin`), or, for providers without a group claim such as Google, a verified email or domain in `access_emails` or `access_domains`; for Google the domain is the hosted-domain (`hd`) claim. The hourly re-check runs for every provider and ends a session whose address, domain, group or provider account no longer qualifies. Refresh and access tokens are stored sealed with a key derived from the client secret; a group-based setup needs a client secret or an encrypted database, and the client secret itself can only be stored in an encrypted database (otherwise pin it with `ATRIUM_AUTH_OIDC_CLIENT_SECRET_FILE`). On https the session cookie is read only under its `__Host-` name. The `oidc_preset` setting picks defaults for Pocket ID, Authelia, Authentik, Keycloak, Google and Microsoft Entra; `generic` takes the claim and scopes from settings. Microsoft Entra reports group object IDs, so the group settings take those IDs.
- A session is stored in the database and referenced by an opaque cookie (`HttpOnly`, `SameSite=Lax`, `Secure` and the `__Host-` prefix on https). It ends after 7 idle days (sliding, `oidc_session_idle_days`), after 30 days in all (`oidc_session_max_days`), on sign-out (`POST /logout`), or when the hourly group re-check (`oidc_recheck_minutes`) finds the account without access or the provider rejects the refresh token. An unreachable provider keeps a session for up to one more hour. The OIDC client secret is the write-only `oidc_client_secret` secret.
- `/settings/auth` (the Sign-in tab) is reachable in every listener. It shows the OIDC connection when one is configured (provider, issuer, client ID and redirect URI; fields pinned by deployment configuration read-only) with the session lifetime settings, and the API token section: list, issue with an optional expiry, and revoke. The secret is shown once in the response to the issue request and never in a page or list. The page answers `no-store`. `atrium settings set` and `atrium secrets set` change the same settings from the CLI.
- In local mode there is no group check and every loopback request is the operator. Without an explicit allowed Host, the accepted Hosts are `localhost`, `127.0.0.1` and `[::1]`. The listener is meant to be reached through an SSH or VPN tunnel that terminates on the host; binding a VPN interface is not loopback and is refused.
- The NixOS module runs the public listener in proxy mode, optionally with oidc added, and, by default, a second listener bound to `127.0.0.1` in local mode.
- Public requests are limited in process by token buckets owned by each listener: 10 sign-in requests a minute per client address (`GET` and `POST /login`, `GET /auth/callback`), 120 `/api/v1` requests a minute per address and 60 a minute per bearer token. A refusal answers `429` with `Retry-After` in whole seconds and `Cache-Control: no-store`, and changes nothing: no pending login, session, proposal or token row, no tool run and no last-used update. The client address is the socket peer. Only a peer named in `web.trusted_proxy_cidrs` (or a repeated `--trusted-proxy`) may set `CF-Connecting-IP`; exactly one valid value is accepted, anything else answers `400`, and every other forwarded address header is ignored. The limits are code constants, not settings, and a restart clears them.
- `POST`, `PUT`, `PATCH` and `DELETE` requests need the CSRF token that atrium issues in a cookie and a request whose `Origin`, when present, matches the Host. Responses carry a Content-Security-Policy.
- `/api/v1` is a JSON API for a native client, available in every listener. It accepts only a bearer token: a locally issued `atr_` token, or, when `oidc_api_client_id` names the client, an RFC 9068 access token from the configured issuer. Session cookies and proxy headers grant nothing. Both formats pass one persisted revocation and usage gate: a token is stored only as its SHA-256 hash, an OIDC access token is enrolled on its first successful validation, and a revoked token is refused on the next request. `atrium auth token issue --name NAME [--expires-at RFC3339]`, `atrium auth token list` and `atrium auth token revoke ID`, and the Settings › Sign-in token section, issue, list and revoke tokens; the secret is shown once at issue. A JWT presented without a configured API client still answers `404` with code `api_unavailable`. The client is a separate public client at the same provider (for Pocket ID: PKCE, scopes `openid profile email groups offline_access`) and sends `Authorization: Bearer <access token>`. atrium accepts only an RFC 9068 access token (`typ: at+jwt`) signed by a key in the issuer's JWKS, from the configured issuer, whose `aud` contains and whose `client_id` equals `oidc_api_client_id`, and that is not expired (60 seconds of clock skew); ID tokens are refused. Groups come from the configured claim, with the userinfo endpoint as fallback, and decide admission as for web sign-in. A verified token is cached in memory until it expires or `oidc_recheck_minutes` passes. Session cookies, the CSRF cookie and `Remote-*` headers grant nothing under `/api/v1`, so in `proxy+oidc` the reverse proxy must pass `/api/v1` through without forward authentication. Refusals use one JSON envelope, `{"error":{"code","message","fields"}}`: `401` `unauthenticated` (no bearer) or `invalid_token`, with `WWW-Authenticate: Bearer`; `403` `forbidden` (no access) or `cross_origin` (a write whose `Origin` is not the Host); `415` for a write body that is not `application/json`; `429` `rate_limited` when an address or token bucket is exhausted; `503` `auth_unavailable` when the provider cannot be reached. The Host check applies first. Lists return `{"items","next_cursor"}`. `POST /api/v1/threads`, `POST /api/v1/threads/{id}/messages`, `POST /api/v1/approvals/{id}/approve` and `POST /api/v1/drafts/{id}/send` replay the first response for a repeated `Idempotency-Key` from the same account for ten minutes; the key with a different request answers `422` `idempotency_mismatch`. Run progress streams as server-sent events from `/api/v1/threads/{id}/runs/{run}/events`, resumable with `Last-Event-ID`. `GET /api/v1/pending` lists what Review's Needs you lists: pending approvals, blocked approvals and open or unknown drafts. Approve, deny and resolve under `/api/v1/approvals/{id}/` run the same approval pipeline as the Review cards, so an approval still runs its write once and only on approval; a second approve answers `409` `not_approved` and writes nothing. `GET /api/v1/undo` lists direct agent writes that carry an undo and undoable applied approvals, newest first, filterable by `thread_id` and `run_id`; `POST /api/v1/undo/{write:N|proposal:N}` undoes one through the same writes registry and pipeline as Activity. Drafts are read, edited, sent, discarded and resolved under `/api/v1/drafts/{id}`; send requires the reviewed `revision` (a changed draft answers `409` `stale`) and goes through the same send gate as the web. Resolutions made through the API are recorded with source `ui`, as from the web.
- A signed media link grants one file under `/apps/media/file/`. It carries an expiry and an HMAC-SHA256 signature, and is valid for 12 hours from issue. A missing, altered or expired signature is not accepted and the request falls back to the normal group check. The signing key is the host file's `app_keys.link_key_file`, used directly and never copied into the database, or the `link_key` secret in the media module, generated on first use. A deployment pin (`ATRIUM_MEDIA_LINK_KEY`, `ATRIUM_MEDIA_LINK_KEY_FILE` or `media.link_key_file`) wins over the stored value. An existing `media-link.key` beside the database is moved into the stored secret on first use and the file is removed, so links issued before the upgrade stay valid. Changing the key invalidates every issued link. Links issued under the old `/media/file/` path redirect without login, and the signature is checked at the new path.

## Web interface

- The light, dark or system theme chosen in the sidebar is stored in the `atrium_theme` cookie and applied by the server on the next page, so pages render in that theme without a flash. System follows the browser's colour-scheme preference. Any other cookie value renders the system theme.
- The sidebar holds Today (`/chat`), then Review, Library and Apps, then the threads (pinned, recent by day, then grouped by project; archived projects are left out) with New project and All threads (`/chat?view=all`), and Settings at the foot. Each of Review, Library and Apps opens on its first page and shows a tab strip of its pages. Collapsing the sidebar to a rail is stored in the `atrium_rail` cookie. Below 768px the sidebar opens as a sheet from the menu button, and a tab bar at the bottom holds Today, Threads, Review and Library; the tab bar is hidden inside a thread.
- `/chat` is home and shows the day. While the instance has no chat thread it shows a welcome screen with three starter prompts that fill the ask bar. Once a thread exists it shows the date in the configured time zone and a headline built from the Review count (it adds the next timed calendar event, "before Standup at 14:00", once the agenda loads), the lines of the day's morning digest when one was posted, then Needs you, with the ask bar docked at the bottom; a message sent from it starts a new thread. Needs you (`/review/strip`) shows at most three cards in `/review` order (pending proposals, blocked proposals, then open or unknown drafts), each acting in place as on Review, with the Review count and a View all link when more are waiting; it renders nothing when there is nothing to review. A side panel (stacked into the page below 1024px) shows Today, the day's calendar events from `/chat/agenda` when the calendar module is on, and Done for you (`/activity/recent`), the six most recent direct writes and automatic mail actions with Undo, each as a plain sentence such as "Added a task" or "Filed" and the subject; the tool name and target are the row's tooltip. The thread list with search and the Active and Archived views is at `/chat?view=all`.
- The ask bar holds attach, one chip that opens the model, effort, context, thinking, web search and cost cap, and send. On a phone the ask bar on home is one row until it is tapped, has text or has a file. A mail message, a knowledge record, a tracked package, a project file and an event on the home agenda each have Ask about this, which opens home with that item as a chip on the ask bar (`/chat?about=mail:<id>`, `knowledge:<id>`, `package:<id>`, `file:<id>` or `event:<date>:<uid>`). A thread about a project file starts in that project. An event whose uid, or a file whose name, has characters outside a plain set gets no link, because that text would enter the message; the message then starts with a line that names the item by id, and the assistant reads it through its own tools, so mail text never enters the operator's message. On a phone the thread's Work panel opens as a sheet from the bottom. In a thread, pin, archive, delete, move to project and the settings and cost summary are in the thread menu.
- `GET /today` redirects to the day's Today thread, creating it on the first visit of the calendar day in the configured time zone. It is a chat thread with role `today` titled `Today · 2 Jan 2006`; lookup and creation run in one write transaction, so concurrent first visits get the same thread. Earlier days' Today threads stay as ordinary threads. The daily digest posts a card into the day's Today thread (10 lines at most) and, with `digest_notify` on (default), pushes the same lines to the assistant channel. Titles appear only for attention sources and records that carry no marks; mail-derived items and marked records appear as counts that link to the review page or the unconfirmed Knowledge filter. Nothing is posted or pushed when there is nothing to act on.
- ⌘K or Ctrl+K, or the search button in the top bar, opens the command palette. It fuzzy-filters the pages (sections, their tabs, and settings tabs) and actions (New thread, light, dark or system theme, toggle sidebar), and searches thread titles and messages through `GET /chat/palette`. Arrow keys, Home and End move, Enter opens and Esc closes.
- Pages carry no tutorial or helper paragraphs. Explanations of a control are its `title` tooltip; errors, health, counts and deployment pins stay visible.
- Review and Done remain available with historical proposals and effects when
  their owning module is disabled. Approval, undo and resolution require the
  owner to stay enabled throughout admission. Disabling and re-enabling the owner
  does not revive a pending action: start it again. Refused actions are not retried
  automatically; an effect already started finishes recording its outcome, and an
  unknown outcome remains blocked. Drafts, Loops and Packages are unavailable
  while mail is disabled; the `/live/pause` and `/live/resume` web routes return
  404, but `atrium live pause`, `resume` and `status` stay available. A batch
  stopped partway by a disable shows what it already did with the refusal: the
  failed proposal on approve, and the effects already put back on undo, in the
  Review card, the CLI output and the API `409` body. Dismissing a permission request
  while assistant is disabled records the denial without resuming the run.
- Modules turn on and off without a restart. A change takes effect on the next request.
- A module disabled while a request is in progress refuses that request's mutations with a `module_disabled` error (`409` on `/api/v1`). Nothing is written after the refusal.
- An optional module that fails evaluation is unavailable, and enabling it is refused until the failure is repaired. The repair commands (`atrium settings`, `atrium secrets`, `atrium proposals`, `atrium live`) stay usable.
- Review and Activity are core pages. They stay available whatever the module state.
- A disabled module's scheduled jobs do not run.
- Review: Needs you (`/review`: pending proposals, proposals with a blocked write or undo, then drafts that are open or whose send outcome is unknown, each acting in place), Loops, Packages (`/watches`, packages in transit), Mail decisions (`/triage`; with no filter set it lists first, under Check these, up to 20 decisions that differ from where the mail went or that fell to the fallback stage, one row per sender (the newest, with a link to that sender's other decisions when there are more), then the rest under Filed, each decision once; a search, stage or outcome filter shows one list; the per-account statistics sit in a side panel), Inbox (`/inbox`, the 100 most recent notifications with Resend for stored but unpushed ones) and Done (`/activity`). The Review badge counts pending proposals, blocked proposals and open or unknown drafts, and updates after every card action. There is no proposals list: `GET /proposals` answers 404, and `GET /proposals/{id}` redirects (303) to the proposal's card in the thread that made it (`/chat/{thread}#proposal-{id}`) or, when no thread made it, to `/review#proposal-{id}`; notification and Notion links use it. `/drafts` still answers but is not in the navigation. Birthdays and anniversaries are not shown in the web interface; the agent keeps access to them.
- Library: Knowledge (`/library/knowledge`, the operator's durable records with search, scope and state filters; unconfirmed rows carry a checkbox, and Confirm selected (`POST /library/knowledge/confirm`) confirms the ticked records; a record page shows body, marks, writer, source, same-run siblings, history and the confirm, edit, retract, restore and purge actions; `/library/knowledge/profile` shows the profile block the model receives and why a pinned record is not in it), Wiki (`/library/wiki`, synced Notion pages not in the trash, newest edit first, with full-text search), Files (`/library/files`, every thread and project file, newest first, with download), Mail rules (`/rules`) and Scheduled (`/scheduled`, a list with pause, resume and delete; jobs are created and changed from chat).
- Apps: Media at `/apps/media/` (Downloads, Channels, Library). Old `/media/...` URLs answer 301 for GET and HEAD and 308 for other methods, keeping the path and query string.
- Projects are thread groups with no index or hub page. A project is created at `/projects/new` and edited at `/projects/{id}/edit`, which holds the form, the project files and archive or restore; the sidebar links both. A project can be marked Private: knowledge written in its threads stays readable only inside that project, and a chat outside it cannot reference its threads with `@thread/`.
- Pages load scripts only from `/static/`; there are no inline scripts or inline event handlers. Fonts are self-hosted under `/static/fonts/` with their OFL license files.
- A draft the assistant writes and a proposal it creates appear as cards in the thread where they were made. The draft card edits, sends and discards through the Drafts page endpoints, so sending still goes through the operator send gate; it shows Sending… while the request runs and Sent only after the server confirms. The proposal card approves, dismisses and undoes through the `/proposals/{id}/…` endpoints. An approval card shows the tool's arguments as labelled rows and offers Approve and Deny. A pending card checks its status every 20 seconds and replaces itself once the proposal is resolved elsewhere; a resolved card stops checking. The thread's Work panel lists the thread's pending approvals under Needs you, each with Approve, Deny and a link to its card; the section is hidden when nothing is pending. A refused action leaves the card in place with the error and its buttons for a retry. Resolved cards shrink to their title and outcome, keeping Undo where the proposal supports it. With focus inside a card, A approves or sends, D denies, dismisses or discards, and Esc closes it. A question from the assistant is a card whose answer field submits with Enter.
- **What acts directly and what asks.** Each assistant tool declares an effect and a channel: none, own accounts, notify, other people, or the internet. Own-account and notify actions act at once and appear on Done with Undo: tasks, knowledge records (`kb_write`, `kb_retract`), mail folders and moves, drafts, files, scheduled jobs, and the calendar, media and tracking proposals that carry their own approval card. The permission table decides the other channels by what the thread holds. People always asks. Internet allows in a clean thread, asks after `messages` or `personal`, denies after `pii`, and asks or denies once untrusted text is present. An ask on a tool without a card creates a permission request and parks the run: Approve resumes it and performs the call once, Deny resumes it with a refusal, and the tool does not run while the request is pending. Approval re-checks the current permission table, tool settings and thread marks before the call, so a tool disabled or a table tightened while the request waited is refused; this holds for the web card, a phone link and `atrium proposals approve`. Calls that already completed earlier in the same response keep their recorded results and are not run again, so the resumed response continues at the parked call. Scheduled, nightly and subagent runs never park, so an ask there is a deny. Mail send stays an operator action through the send gate.
- **Notion pages are read-only.** The page view no longer has Edit or Link buttons, and the agent has no Notion tools. Sync and the Wiki tab remain. Older `notion_link` and `notion_edit` proposals stay readable on their cards and can be dismissed, but no longer apply.

## Phone actions

- Phone actions are off by default. `phone_actions_enabled` turns them on and `phone_actions_kinds` lists the proposal kinds that may be approved or dismissed from a notification; the web-only kinds (Gmail label merge, inbox backlog, rebalance split and merge, deletion rule) cannot be enabled.
- When an allowed proposal is created, its notification on the assistant channel carries Approve and Dismiss actions. Each action is an HMAC-signed link valid for 12 hours and one use; at most 20 links are minted per hour. The link is the credential: `POST /actions/<token>` needs no session, but the Host check still applies and CSRF is skipped for that route.
- Redeeming a link approves or dismisses the proposal and records the resolution with source `phone`; the Activity page shows "approved via phone". A used, expired, tampered or unknown link changes nothing.
- The phone action section of the Notifications settings tab turns phone actions on, picks the allowed kinds, shows the outstanding link count and rotates the generated `action_link_key`; rotating invalidates every outstanding link. The section is shown while the notifications module is on.

## Mail safety

Every mailbox write goes through one safety gate.

- **Accounts.** A mail account is a `mail/<id>` connection of kind `mail` with the `imap` and `smtp` capabilities: its config holds the `preset` (`icloud` or `gmail`, which supplies the IMAP and SMTP hosts and the provider's folder behavior), `login`, `auth_method` and `enabled`, and its `mail/<id>/password` credential holds the app password. Host accounts are declared by `services.atrium.mailAccounts` and show read-only as set by deployment; operator accounts are added, tested and removed on the Mail settings page. The id (up to 32 lowercase letters, digits and single underscores, starting with a letter) keys the account's cached mail, so keep it stable. A disabled account is listed but never opened or synced. Removing an account stops its sync and keeps its cached mail and history. `ICLOUD_MAIL_USERNAME`, `ICLOUD_APP_PASSWORD`, `GMAIL_ADDRESS` and `GMAIL_APP_PASSWORD` are no longer read.
- **Gmail sign-in.** A Gmail account can use an app password or XOAUTH2. XOAUTH2 uses the Google OAuth wizard's Gmail refresh token: the access token is refreshed once for concurrent callers, a rejected token reconnects or retries AUTH once with a fresh token, and a refresh failure marks the credential needs-reauth. A token inside the 14-day expiry window shows as expiring.
- **Accounts page.** The Mail settings tab lists every account with its connection's state and reason and edits the mail behavior settings `uncertain_dest` and `openloops_remind_hour`. Host accounts show read-only as set by deployment. Test signs in over IMAP, lists the folders, then connects and authenticates over SMTP, and records the result as the connection's health; it changes nothing else. Add account takes an id, label, iCloud or Gmail preset, login, an auth method (app password, or XOAUTH2 for Gmail) and the credential; the account and its connection are kept only when the test passes. The app password is stored only in an encrypted database, in the connection's `mail/<id>/password` credential, and is never shown again. A Gmail account may instead use XOAUTH2, which stores no password and uses the Google OAuth wizard's Gmail refresh token. Editing a stored account tests again when the login or password changes. Removing a stored account deletes its connection and keeps its cached mail. The page has no live or shadow control. The atrium units pick up added, changed or removed accounts when they restart.
- **Modes.** The mail mode (`mail_mode`) is `shadow` (the default) or `live`; any other value is refused. It is an operator setting changed with `atrium settings set mail_mode shadow|live`; the write is audited and the Mail page shows the current mode. It is not a field on the settings pages. In `shadow`, atrium records what it would do and makes no automatic mailbox writes: the automatic pass returns without acting. A snooze that comes due in `shadow` records a skipped effect and stays pending.
- **Automatic writes** happen only in `live` mode and only while atrium is not paused (a `pause` file beside the database). They are limited to: filing or trashing read, unflagged inbox mail according to recorded decisions; flagging unread inbox mail from known contacts; applying the operator's folder corrections made after go-live; and rule-based deletions, which run at most once a day per account. Mail that was already read and in the inbox when live mode first started is never touched by the inbox pass. While paused, the scheduler records `skipped_pause` for assistant, mail, media and other scheduled work; the read-only mirrors `calendar/caldav`, `contacts/carddav` and `notion/notion-sync` and the backup job `core/backup` keep running, as their former timers did, so pause neither freezes the mirrors nor makes `notion-sync` stale.
- **Approval-required writes** are every other mailbox change, such as the proposals from rebalance, deletion and label scans. They are applied only when the operator approves the proposal. Approval is consent: it is the only scope in which a write passes the gate in `shadow` mode, and pause does not hold it back, because pause stops automatic writes only.
- **Assistant folder and move writes.** `mail_folder_create` and `mail_move` are direct, undoable assistant writes. Each records an effect in the effect ledger before the IMAP call, verifies the folder or messages first, and settles it after; an unknown outcome stays blocked until the operator resolves it. In `shadow` mode they record the intent and change nothing, and while mail writes are paused they are refused. Moves use COPY, STORE `\Deleted` and UID EXPUNGE, never IMAP MOVE, and one call moves at most the write cap of messages. Protected folders are refused. Undo runs under its own approval scope, so it still works after switching to `shadow`, and moves the messages back or deletes a folder only if it is still empty.
- **Operator send.** The assistant can save and edit drafts but has no tool to send them. Sending is an operator action from the Drafts page. A send that fails before the SMTP attempt returns the draft to Draft with the error recorded. In `shadow` mode the only append the gate allows outside an approved proposal is the copy of a sent message into the account's Sent mailbox.
- **Write caps.** A pass makes at most the write cap of automatic writes per account (setting `write_cap`, default 100, range 1 to 1000); the remainder is deferred to a later pass and logged.
- **Verification.** Before each write atrium re-reads the message on the server. If the message changed (for example it was read, flagged or moved in the meantime), the write is skipped and recorded as skipped with its reason.
- **Protected folders.** Trash, Sent, Drafts and Junk (identified by their special-use flags or well-known names such as Bin, Deleted Items, Sent Items and Spam) are never a source or a destination of automatic filing. Destinations must be existing, safely named folders; Gmail labels beginning with `\` or `[Gmail]` and system labels are refused.
- **Retries.** A message whose automatic action failed or was skipped is attempted again until the configured number of such outcomes (setting `write_attempts`, default 3) is recorded for it. A message already acted on is not acted on again.
- **Outcome unknown stays blocked.** atrium records the intent before it writes. If the connection is lost or the process is interrupted so that the result is unknown, the action is marked unknown and is never retried automatically until the operator resolves it: the Activity page offers It happened (`applied`) and It did not happen (`not-applied`), and `atrium live resolve ID --outcome applied|not-applied` does the same. An undo that copied the message back but did not expunge the original, or whose outcome is unknown, is likewise recorded as blocking; further undo of that action is refused until the operator resolves the mailbox by hand.
- **Resolving a blocked write.** After the operator has checked the mailbox, `atrium proposals resolve ID` settles every blocked ledger row of a proposal, and `atrium live resolve ID --outcome undone|not-undone|partial` settles a blocked automatic-action undo, and `--outcome applied|not-applied|partial` settles a blocked forward automatic action. Needs you (`/review`) offers the same for a proposal with a blocked write, and the Activity page for a blocked automatic action, as operator-only buttons under the usual CSRF and same-origin checks. A blocked proposal card shows the blocking row's recorded error text, or Outcome unknown when none was recorded. On a blocked proposal card a blocked forward write has one button, Mark checked; on the Activity page it has It happened and It did not happen. A blocked undo has two, Messages are back (`undone`: the undo counts as done, and resolving a corrected message this way also clears its correction) and Not moved back (`not-undone`: the undo may be attempted again); `atrium proposals resolve` needs `--outcome` only when one of its blocked rows is an undo. Resolving only appends who, when, the outcome and the previous error text (Outcome unknown when the row recorded none) to the append-only `effect_resolutions` table; the original outcome and error stay. It never opens the mailbox, never performs and never retries a write, and it does not decide whether the original write took effect. A proposal can then be approved or undone again, and a message held back by the blocked row is no longer skipped as unresolved. A row still marked in flight is refused while its write or undo runs: the running process renews the row every 30 seconds, and the row becomes resolvable 2 minutes after its last renewal (once the process stopped or hung). An in-flight automatic-action undo recorded before migration 6 has no start time and is resolvable at once. A proposal that is still being applied is refused. A write or undo that finishes after its row was resolved does not overwrite the recorded outcome, and a second undo of an action cannot start while its first is in flight or unresolved.
- **Undo.** Every applied automatic action that has an undo plan can be undone by the operator, which moves the message back, restores labels, restores the trash state or removes the flag. An undo is its own effect record with its own outcome. Undo runs under its own approval scope. Proposal undo reverses completed effects newest first and stops at the first reversal that does not complete.
- **Replay.** `atrium replay [--account ID] [--limit N] [--model]` re-runs routing for every stored message that already has a decision and prints one JSON line per message with the replayed and the latest stored decision, then a summary on stderr. Without `--model` it opens the database read-only and makes no IMAP, SMTP, embedding or paid classification call; a message that would reach the model stage reports stage `llm` with action `ask` and no destination. With `--model` it copies the database to a temporary file, and a message that reaches the model stage gets one paid folder classification (charged to the inference ledger of the copy, which is deleted afterwards); it still opens no IMAP, SMTP or embedding connection, and the database itself is not changed. A budget refusal or other deferral stops the model stage for the rest of the replay and those messages report `none`. A message with no stored vector skips the vector stages. It takes the accounts from the database rows (`mail_accounts`, then `accounts`), so a bare copy needs no accounts file; a message whose account has neither row replays as `none` and the summary names the account. Differences between the replayed and stored decisions do not change the exit status.
- **Message handling.** Moves use COPY, STORE `\Deleted` and UID EXPUNGE, not IMAP MOVE.

## Assistant limits

- When the assistant module is disabled, none of its tools are offered to any run, including the server `web_search` tool. When mail is disabled, `propose` omits `mail_triage` from its offered kinds and refuses a forced call for it.
- **Editing a schedule.** Each row on Library › Scheduled has an edit control that takes the schedule text (`daily 02:30`, `weekly sun 18:00` or a five-field cron line) and saves it through `POST /scheduled/{id}/schedule`. For a built-in job it also stores the job's `agent_schedule_*` setting, so the change survives a restart; a schedule pinned by the deployment is refused. An invalid schedule answers 422 and keeps the old one.
- **Scheduled runs** (cron) can read, add tasks with `task_add` (undoable on Done), notify and use their own-account writes; they cannot use the internet or reach other people. A scheduled run starts with the marks of the thread that created its schedule unless the operator wrote the prompt.
- **One run per job.** A scheduled run holds a lock file for its job and for each resource the job declares (the media jobs share `media-control`) in the `<database>.locks/` directory next to the database. The directory follows the database's real path, so a second scheduler reaching the same database through a symlink does not start a job that is already running; the lock files are never deleted. A running job renews its claim every 20 seconds and holds it for 90; a scheduler stopped by a signal releases the claim so the next start resumes the run at once, and after a crash the run resumes once the 90 seconds pass. A job whose claim was taken over stops before its next effect and does not record its run. `atrium media poll`, `atrium media sweep`, `atrium calendar sync` and `atrium contacts sync` run their job through the same claim: they wait up to 5 seconds for it, then exit 1 with `held by another invocation`; a manual run records a job run but does not move the job's next scheduled time. A failed job that declares a backoff retries after its backoff delay (doubling per consecutive failure up to its maximum) when that comes before its next occurrence.
Consecutive disabled-module occurrences without assistant threads share one `skipped_module` row: its first start is retained and its due/end timestamps advance to the latest skip. Interrupted assistant jobs wait as `skipped_module` without an end timestamp while their module is off; their threads remain reserved to the job claim and resume only through that claim when the module returns. Manual interruptions settle immediately as `error: interrupted` and release the claim. Manual failures and successes do not change scheduled failure backoff; a pending scheduled retry is kept when serve primes jobs after a restart. A manual command exits nonzero if it loses its claim. Invalid host-owned schedules (including one-shots, internal interval text and intervals below the scheduler minimum) warn and fall back to the declared default without blocking other jobs.

- **One scheduler pass.** `atrium agent tick` recovers interrupted jobs and starts one snapshot of due work, then waits for all work it started and its settlement. It exits 0 when it finished work or nothing was due, 75 (`EX_TEMPFAIL`) when every due job was busy in another invocation and nothing started, and 1 on an error; a systemd unit running it sets `SuccessExitStatus=75`. It does not remain running for future occurrences. Missing configuration is a skip (`skipped_unconfigured`), not a successful job; consecutive scheduled skips with the same reason share one job run whose end time moves forward, and a manual run always records its own job run. A scheduled job with several child runs, such as nightly dreaming's clean and marked groups, succeeds only when every child succeeds; an interrupted child resumes on the next pass without repeating finished children, and each dreaming child gets the nightly and monthly dreaming allowance that remains just before it runs. A job that reaches its own timeout ends `error` ("timed out after …") and is not resumed; only a shutdown releases a job for the next pass. Recovery never takes over a run another live process is executing, such as a job run the operator approved and resumed in `serve`: the job stays released and settles from its own runs once that run ends.
- **Lessons.** Dreaming also receives code-built signals: failed runs, writes the operator undid, dismissed proposals and denied permission requests in the last day. It may write a `Lesson: …` record with the tool names as aliases and the thread where it happened as its source. Lessons are ordinary unconfirmed knowledge records, so retrieval can surface them and the operator can retract them.
- **Nightly dreaming.** The nightly job gathers the last 24 hours in code: chat and scheduled threads (skipping threads of private projects) and a compact index of live records. It then runs one Haiku write step with `kb_search`, `kb_get`, `kb_write`, `kb_retract`, `task_add` and `task_list`. Records carry `source.thread_id` from the gathered set; the write thread takes the union of the gathered marks, so records from clean threads are unmarked and records from marked sources stay unconfirmed until the operator confirms them. Dreaming is capped at `dreaming_max_cost_usd` (default $0.30) per night and `dreaming_monthly_usd` (default $3) per calendar month; at the monthly cap it does not run and raises an attention item.
- **Memory.** The knowledge store is the agent's memory: `kb_search` and `kb_get` read records visible to the thread's project, `kb_write` creates or edits one and `kb_retract` retracts one, each write undoable on Done. A record written by `kb_write` takes its thread's marks and project; an edit can only add marks, and a retract must name a record in the thread's project. A record confirmed by the operator, or written by the operator or the import, cannot be edited or retracted by the agent. Pinned, confirmed, unmarked records outside a private project, or in the reading thread's own project, form the profile block the model receives; a private record without a project never does. The nightly dreaming run writes records with `source.thread_id` set; they take the gathered marks, so records from marked sources stay out of the prompt until confirmed, and a `pii` or `messages` record stays out even then. The Notion wiki is no longer read or written by the agent.
- **Chat** is the only run kind that can update or complete tasks, edit drafts, or change schedule records.
- **Server-ops worker.** The `ops-sampler` built-in job (default `*/15 * * * *`, `agent_schedule_ops_sampler`) samples the hosts named in `ops_hosts` through the Grafana metrics datasource and alerts endpoint every 15 minutes, with no model call: `up`, `cpu_pct`, `mem_pct`, `disk_root_pct`, `failed_units` and `alerts_firing` go into `ops_samples` (kept 14 days). `ops_hosts` holds address-shaped host ids (letters, digits, dots, dashes and underscores; the address part of the scrape target, without the port). The label selector and the five queries are host inputs: `ops_label_selector` (default `job="node"`) and `ops_query_up`, `ops_query_cpu`, `ops_query_mem`, `ops_query_disk`, `ops_query_failed_units`. Each query is a single-line PromQL template with the `{{host}}` placeholder and optionally `{{selector}}`; the selector is a comma-separated matcher list. Both are validated when the host file is read, so a value is one read query and cannot break out of its braces or add a second statement. When a fact changes state, crosses the 90% memory or disk threshold, or its firing alert set changes, and the change set differs from the last one recorded in the persistent `Ops` thread (kind worker, role ops), the sampler makes one Haiku classification request with a fixed JSON schema: no tools, no thinking, one message carrying the typed change, any quoted alert names and the last 24 hours of samples for those facts. Each request uses the Anthropic connection's current key, so a rotated or removed key takes effect at the next pass without a restart. Before it is sent, each request is checked against the Haiku run cap lowered to `ops_worker_max_run_usd` (default $0.10), the `ops_worker_monthly_usd` cap (default $5, counting every reserved, unknown and settled server-ops classification this month) and the monthly budget; the thread cost cap does not apply. Classification spend is recorded on a hidden accounting thread that never appears in the chat list, in memory search or in the nightly signals. A classification left open by a crash is closed as failed (`crashed`) by the scheduler's recovery pass once it is older than the run lease (30 minutes); its reservation expires under the unknown-outcome rule. Findings for facts in the change set go to `ops_findings`; findings for other facts are dropped. Findings of severity warning or critical appear under Needs decision in the attention view, on Needs you, and in the daily digest, and the sampler resolves a finding once its fact is back to normal; resolved findings are pruned after 30 days. A refused request, a missing key or a provider failure writes no finding and keeps the change pending, and each later pass with no new change retries it. A charged failure (a refusal, a truncated or unexpected stop, or a reply that breaks the schema) is retried at most once for the same change set and then held until the change set changes. A monthly budget refusal raises the "classification budget" attention item linking `/settings/usage`, which clears once the budget has room; a refusal by `ops_worker_monthly_usd` raises the server-ops budget item instead, without a deferral, for as long as the latest server-ops classification this month was refused by that cap. With `ops_worker_monthly_usd` at 0 the item shows whenever `ops_hosts` is set. `worker_status` reports `mode: fixed-schema-haiku`. No worker run starts automatically and nothing restarts or changes a host. The old `ops_condenser`, `ops_condenser_model` and `ops_condenser_max_tokens` settings are retired: `atrium db import-v2` drops them and reports each one, and an `ATRIUM_ASSISTANT_OPS_CONDENSER*` variable or an `assistant.ops_condenser*` host key stops startup naming the `ops_worker_*` settings that replace them.
- **References.** Typing `@` in the composer lists the chat threads; choosing one inserts `@thread/12`, and a message's Reference action copies `@thread/12/m34`. Sending stores the referenced text as a verbatim block appended to the message, labelled as data, not instructions. A thread reference carries the thread's operator and assistant text, newest exchanges first when it is over `agent_ref_tokens` (default 8,000, range 1,000-32,000); a message reference carries that one message. A message carries at most three references. An unknown or deleted thread, the thread itself, a message without text and an over-limit message are refused with nothing stored. The referenced text counts toward the context limit, and the reading thread takes the source thread's marks.
- **Research subagents** are limited to read-only tools, by default at most 12 steps and $0.25 of spend per run, with at most two running at once (`agent_subagent_max_steps`, `agent_subagent_max_cost_usd`, `agent_subagent_max_concurrent`). They cannot write, notify, schedule or start other agents. Their system prompt carries neither the operator profile nor project instructions. Their spend counts toward the parent: before each subagent request, the subagent's own cap, the cost cap of every parent run (counting the spend of that run and all its subagents) and the thread cost cap are checked, and a request that would pass any of them is refused.
- **Web search.** `search_web` searches the public web in a child subagent and returns a cited answer. It is offered in chat and cron runs when the thread's Web search option is on, and the permission table can ask with the exact query and question on the card. The child has the server `web_search` (at most `search_web_max_searches`, default 5), `web_fetch`, `recall` and `report`; its allowlist starts with URLs typed in the query and question, never the parent's. Its caps are `search_web_max_cost_usd` (default $0.15, search fees included) and `search_web_max_steps` (default 8), and it runs on `search_web_model` (default Haiku 5.5) at medium effort. A citation is kept only when its URL appeared in a search result or a successful fetch; a fetched page's quote must occur in the stored text to count as fetched, and a citation outside the verified set is dropped with its `[n]` marker. Only surviving URLs join the parent's allowlist. Chat no longer sends the server `web_search` directly, and the seeded `web` research role is retired.
- **Lookup readers.** `lookup` reads one source (mail, contacts, documents or knowledge) in a child subagent and returns typed fields. The child has only that source's read tools, `recall` and `report`; it cannot write, notify, reach people or use the internet. The fields are number, date, boolean, enum, id (mail message, file, knowledge record or thread) or text, at most 12. Text values are untrusted data. Boolean and enum fields carry no marks; numbers, dates and ids carry the child's kind marks; text adds `untrusted`. A name-and-organisation contacts lookup marks nothing, so the internet stays open; a mail lookup marks `pii` and `messages`.
- **Marked threads.** Tools mark a thread with what their result contains: `pii` (contact identifiers such as email addresses, phone numbers, birthdays, tracking and order numbers), `messages` (mail, calendar events, files, other threads' history), `personal` (knowledge records) and `untrusted` (text someone else wrote: web pages, mail bodies, Grafana telemetry). The permission table then decides each channel: own-account and notify tools keep working, other-people tools ask through their card, and internet tools ask or are refused by situation. A tool that leaves the allowed set is withdrawn for the rest of the run and later runs; the request keeps its tools array so thinking stays valid, and a call to a withdrawn tool returns an error and does nothing. A tool without a card that asks creates a permission request in the thread and parks the run. `task_list` and `schedule_list` return the marks of the threads that wrote the rows they list, a scheduled run inherits its schedule writer's marks, and `profile_set` and `nightly_observe` are refused on any marked thread. Phone action links never decide a permission request.
- **Models.** Chat threads run on Haiku 5.5, Sonnet 5.5 or Opus 5.5. A new thread takes the `default_model` setting (default `claude-haiku-5-5`) unless the new-thread form names a model; the thread's model, effort and context size can be changed later. Scheduled, nightly and subagent runs use Haiku 5.5; the `search_web` child uses `search_web_model` (default Haiku 5.5). Each run sends its thread's model and each usage row is priced at that model's rates; a model outside the built-in catalog is refused before a request is sent. The context size cannot exceed the model's context window. Haiku 5.5 bills prompts over 100K tokens at the higher rates; Sonnet 5.5 and Opus 5.5 have flat rates.
- **Per-run limits.** Each run stops after the maximum number of steps for its kind (`max_steps_chat`, `max_steps_cron`, `max_steps_nightly`, default 24 each, and `max_steps_worker`, default 8; research subagents use `agent_subagent_max_steps`) and the run cost cap of its model (`max_run_cost_usd_haiku_5_5` default $2, `max_run_cost_usd_sonnet_5_5` default $6, `max_run_cost_usd_opus_5_5` default $10; each covers writing a full 1M-token request at the 1-hour rate); all are settings. The old `max_run_cost_usd` setting no longer exists: a stored row or `ATRIUM_ASSISTANT_MAX_RUN_COST_USD` is ignored, and each logs a warning at command start naming the new settings (the stored row's warning also shows its value). Remove the orphaned row with `atrium settings unset max_run_cost_usd`, which is audited; values are not carried over to the new settings. The same check holds every request to the thread cost cap `thread_cost_cap_usd` (default $10): the thread's recorded spend across all its runs and its subagents' threads plus the next request's cold cost may not exceed it. A cost cap chosen in the new-thread form (or `cost_cap_usd` when creating a thread through `/api/v1`) lowers that cap for the thread; it cannot be changed later, so a thread stopped at its own cap needs a new thread. A thread has at most one running run of its own; its research subagents spend against the same cap. A run also stops when the same tool call returns the same result `doom_loop_threshold` times in a row (default 3). The stop reason is the run's error.
  The cap is checked before every request: the run stops when what it has spent plus the cost of writing the next request to the cache cold, at the thread's cache lifetime (`cache_ttl_chat`: 1-hour writes cost more than 5-minute writes), would pass the cap, and the refusal names the setting to raise, or says to start a new thread when the thread's own cap stopped it. A cold 400K-token Opus request costs $3.20 to write with a 1-hour cache.
- **Model stops.** A refusal, a reply cut off at the output or context limit, and an empty paused or ended turn each end the run with a message in the thread; a refusal names the policy category and any model the server recommends instead. When the server falls back to another model after a refusal, the thread notes the switch and the fallback's tokens are recorded as their own usage row at that model's rates.
- **Forced tool calls.** A forced `tool_choice` (`atrium agent run --tool-choice any|<tool>`) applies to the first request only and is sent only to models the catalog allows (Haiku 5.5); Sonnet 5.5 and Opus 5.5 receive the request without it. `search_web` can be forced in a chat or cron run; the server `web_search` exists only in the `search_web` child.
- **History and the prompt cache.** Each request carries the run's own messages and, newest first, earlier whole exchanges within `memory_verbatim_tokens` (default 16,000 tokens, at most a quarter of the context left after the tools and system prompt) unchanged, tool calls and results included; a tool result over `agent_stub_tokens` is still stored and paged with `recall`. Every operator message ends with the date and time its run started in the configured time zone. Older messages come first as memory-tree lines (summaries of older ranges, each with a zoom id). The tools, the system prompt with the profile and project block, and the older-history lines stay fixed for the whole run and carry the cache breakpoints, so each later step reads them from the prompt cache and writes only the new messages. A chat or cron message also gets a knowledge block: records that are not retracted, expired, ops, pinned or marked untrusted/pii/messages, and whose private project (if any) is the thread's, are matched by exact title or alias, full-text search and one embedding of the message text (2 s), gated by `kb_retrieval_distance` (default 0.35; full-text-only matches need two query terms), at most five records within `kb_retrieval_tokens` (default 1,500; 0 disables). The block is stored in the operator message and expanded in place, so later steps replay the same bytes; it adds no marks and nothing is added to the tools, system prompt or history prefix, so the cache breakpoints stay byte-identical.
- **Monthly budget.** Every paid model call is admitted through the inference ledger before it is sent: the full cold prompt plus the request's maximum output tokens, 8,000 input tokens for each allowed web search and the search fees are reserved against the run, parent run, thread and monthly limits, and a call that would exceed one is refused before any request. The prompt estimate counts text at its character rate and each attachment at the token estimate stored with it, not the size of the base64 copy inlined into the request. Memory summaries count toward the monthly budget; a memory job refused by the monthly budget stays queued until the first of the next month, a thread-cap refusal retries with the normal backoff, and only a run-cap refusal fails the job. Each reservation records its calendar month (`YYYY-MM`) in the time zone in use at that moment, and admission, the Usage page and the scheduler compare that key, so changing the time zone does not move committed spend out of the month. The monthly budget (`monthly_budget_usd`, default $150; edited on the Usage tab) is compared with the committed spend of that month. Chat stops starting new work at the chat share of the budget (`budget_chat_share`, default 100%), capped at 95%: the last 5% is reserved for classification. Scheduled, nightly and server-ops worker runs stop at the unattended share (`budget_unattended_share`, default 80%), which cannot exceed the chat share. An attempt whose outcome is unknown stays reserved; after 24 hours it becomes an estimated charge equal to its reservation, which keeps consuming the month. A stream that stops mid-generation (Stop, a dropped connection or a canceled caller) is settled with the output received so far, estimated from the delivered text and thinking and never less than the provider reported. Reservations from the previous month carry into the new month until they settle or expire. When the budget is exhausted, scheduled jobs that need no model call still run, and jobs whose paid work is conditional do their free work and defer the paid part. The server-ops worker also has its own monthly cap (`ops_worker_monthly_usd`, default $5) and per-run cap (`ops_worker_max_run_usd`, default $0.10). Dreaming also has its own caps: `dreaming_max_cost_usd` (default $0.30 per night) and `dreaming_monthly_usd` (default $3 per calendar month). A research subagent does not start once a budget limit has been reached.
- **Anthropic spend limit.** When the Anthropic organization's own spend cap refuses a request (HTTP 429 without a `retry-after` header), the run ends as a budget stop with a budget message and is not retried; scheduled jobs are recorded as skipped for budget.
- **Prompts.** The system prompt (`prompt_system`) and the shared subagent rules (`prompt_subagent`) are set with `atrium settings set`; an unset key uses the built-in text, and `atrium settings unset` restores it exactly. Edits are audited and apply to the next request of every thread. The untrusted-data preamble is fixed in code, is not a setting, and is always placed before the system prompt.
- **Sending mail** is an operator action only; see [Mail safety](#mail-safety).
- Tool permissions, run-kind restrictions and spending limits are enforced in code, not in prompts. Mail, files, pages and tool results are treated as untrusted data and cannot grant URL access or widen tool permissions. Arbitrary web fetches use an allowlist and SSRF protection on every redirect.
- Code execution is unavailable.

## Attention and tasks

- The attention query covers the enabled queues: proposals, drafts, open loops, commitments, event candidates, thread plans, packages, tasks, unanswered `ask_operator` questions and live server-ops findings of severity warning or critical, each listed until the operator answers it. Items are grouped as overdue, due soon, needs decision, waiting on them and upcoming. The cron-only `attention` tool and the daily digest read it. The attention page is not part of this build.
- Open loops come from mail the operator actually needs to answer: the latest message must not be bulk or automated (List-Id, List-Unsubscribe, Precedence bulk/list/junk, Auto-Submitted, a bulk Gmail category, an email service provider, a Reply-To that differs from From, or an automated sender address) and must not be addressed to the operator only in Cc; a message that lists the operator in To, or in neither To nor Cc (BCC, mail merge or a missing To header), still counts, as does a message whose cached raw headers are unavailable. Commitments follow the same rule and include only items addressed to or requested of the operator; items meant for other recipients of a group message are ignored. Birthdays are read from contacts for the calendar and are not an open-loop source.
- Tasks are a core store with open, done and dismissed status, a due date, reminder time, priority and an optional source. The assistant tools list, add, update and complete tasks directly, each undoable from Done; the reminder job inserts a task when a scheduled reminder is due. The assistant reads the attention view with the `attention` tool, and the morning digest posts it to Today and the assistant channel.
- Packages from shipping emails show the latest Ship24 event when the operator registers one with `track_package`. The hourly `package-tracking` job refreshes active trackers, stops polling delivered packages, and sends one notification on a delivered or exception transition. The monthly registration quota (`mail_ship24_monthly_quota`, default 10) refuses further registrations with a clear message.

## Weather

- The `weather` tool returns current conditions and an hourly/daily forecast for `weather_latitude` and `weather_longitude`, or for `weather_location_name` when coordinates are unset, and for a place named in the call. It reads Open-Meteo, needs no key, and sends only the coordinates or the place name. The location settings are unset by default; without a location the tool reports that it is not configured. The Open-Meteo connection record on the Connections page has a Test but no URL or credential, and carries the latitude, longitude and location-name fields: latitude must be between -90 and 90 and longitude between -180 and 180, and clearing a field unsets it.

## Settings and secrets

- **Host configuration and operator settings.** Host values come from the file named by `ATRIUM_HOST_CONFIG` and its `ATRIUM_<MODULE>_<KEY>` environment variables; an environment variable wins over the file. They are read-only in the application: `atrium settings set` and the Settings pages refuse them, naming the host destination. A host key is never read from or written to the database: a row with a host key is ignored, and a write that would create one is refused. Twelve tuning values (body cap, page and preview sizes, run history, HTTP timeout, calendar event, occurrence and candidate limits, contacts results and pass-run retention) are compiled constants, not settings. Operator preferences are stored in the database and edited in the application; they are not host configuration. A value the host file declares for an operator setting, including a `<name>_enabled` module flag, wins and makes that setting read-only. A cut-over operator or tuning key is refused from the legacy `ATRIUM_CONFIG` file and its environment variable with its destination. Connection `config`, `transport` and `credential_files` values expand `${NAME}` from the environment, and a host credential file that cannot be opened refuses the command. A host declaration that takes over an operator connection keeps its stored credential only while the scheme, host, port and base path of every endpoint the credential is sent to stay the same; changing one refuses the command, naming the connection and the two remedies (declare a credential file for it, or disconnect the stored credential first). A connection the host stops declaring stays disabled, including a built-in such as `service/embedding`.
- **Host-declared values are read-only.** A value the host file declares, including a module flag, cannot be changed or unset through the settings registry; `atrium settings set` and `unset` refuse it and name the source. The database key is the only remaining environment pin.
- **Naming.** The environment variable for a host key is `ATRIUM_<MODULE>_<KEY>`, where `<KEY>` is the whole key. When the key already begins with the module name, the module appears twice: `ATRIUM_ASSISTANT_ANTHROPIC_CA_FILE` for `anthropic_ca_file`. The [environment variable list](../config/environment.md) is authoritative. A host secret accepts only a `_FILE` variable naming a file whose trimmed contents are the value; a raw secret value is refused. An `ATRIUM_<MODULE>_<KEY>` variable for an operator or tuning key is refused at startup with its destination (`atrium settings set <key>` or the compiled constant), as is a connection-owned host key such as `ATRIUM_GRAFANA_GRAFANA_URL` (use `connections.<id>`). `ATRIUM_CONFIG` and its pin file are gone. The database key is `ATRIUM_DB_KEY` or `ATRIUM_DB_KEY_FILE`, or `database.keyFile` in the NixOS module.
- **Renamed variables.** The earlier unprefixed names (`ATRIUM_MODE`, `ATRIUM_TZ`, `ATRIUM_PUBLIC_URL`, `ATRIUM_CHAT_URL`, `ATRIUM_EMBED_URL`, `ATRIUM_CALENDAR_DIR`, `ATRIUM_ICLOUD_CALENDAR`, `ICLOUD_APPLE_ID`, `GOOGLE_OAUTH_CLIENT_ID`, `ATRIUM_CONTACTS_DIR`, `ATRIUM_MEDIA_ROOT`, `QBITTORRENT_URL`, `ATRIUM_MEDIA_MOVIES_URL`, `ATRIUM_MEDIA_TV_URL`, `ATRIUM_CODEMODE_SOCKET`, `ATRIUM_ASSISTANT_MAX_RUN_COST_USD`) are not read and do not pin anything. The command does not warn about them; remove them from the host environment.

For a secret the row records only `changed`. The table rejects updates and deletes, and the rows are listed read-only on the Activity page.

- **Integrations.** The Integrations settings page lists each legacy connection record (Open-Meteo, Grafana and Anthropic); qBittorrent, TMDB, EZTV, Notion, Ship24 and the embedding endpoint are on `/settings/connections` with their endpoint, credential state (set, unset or set by deployment) and health: untested, ok, failing, expiring (a known credential expiry within 14 days) or needs re-auth (the service refused the credential). The qBittorrent connection takes its CA bundle and proxy from the host (`ATRIUM_MEDIA_QBITTORRENT_CA_FILE`, `ATRIUM_MEDIA_QBITTORRENT_PROXY`) and uses the same transport for the CLI, the HTTP page and every runtime request.
- **Check on failure.** When a request from `atrium serve` to Grafana, qBittorrent or Ship24 fails to connect or answers 401, 403 or a 5xx status while the integration is recorded as working, its check runs at once instead of waiting for the daily check. After a check that passes, further failures wait 5 minutes before the next one.

## Modules

- **Toggles.** Mail, calendar, contacts, Notion, media, assistant, notifications and Grafana are modules with a `<name>_enabled` setting; core is always on. Change one with `atrium settings set <name>_enabled true` or `false` and restart the atrium units, or declare it in the host file with `ATRIUM_CORE_<NAME>_ENABLED`; a declared flag wins and cannot be changed through the CLI. The money module is removed: its tables and rows stay in the database, its stored settings are ignored, and its `fx-rates` scheduled job is cancelled on the next scheduler start.
- Module changes committed by the running web application take effect on its routes without a restart; disabling returns 404 and re-enabling restores the routes. Authentication, CSRF and signed-link checks still apply. A failed settings transaction changes no running module state. A separate CLI process or a host configuration change still needs the other atrium processes restarted.
- If core cannot be evaluated because of an error, startup fails with the owner named and exits nonzero instead of serving only core pages. An optional module whose evaluation fails is unavailable with that error, and the rest start. A module whose start work fails (for the assistant, seeding its built-in jobs) is unavailable with the start error, the failure is logged once per attempt, and the start is retried at the next settings change. Notifications checks for stale passes only while it is enabled.
- Disabled module pages use the normal rendered 404 page; disabled `/api/v1` routes keep the JSON `not_found` error response.
- The `/metrics` output can list metric families in a different order; metric names and labels are unchanged.
- **Contacts.** The contacts module needs the host `contacts.contacts_dir` and owns `contacts_lookup` and `atrium contacts sync`. Mail uses it as an optional source: with contacts off or no directory, the mail flag rule flags no sender as a contact and the triage flags view says no contact source is configured. On a database adopted from Phase A, the first start of this build enables contacts when `contacts_dir` is set.
- **Mail model endpoints.** Mail has one model endpoint: the embedding endpoint, the `service/embedding` connection, whose URL and model are its config and whose `bearer` credential comes from a host file; the bearer is sent only to its base URL. Mail classification has no local chat endpoint: flag, event, routing, scan and rebalance-naming judgments are fixed-schema Haiku requests through the `service/anthropic` connection under `monthly_budget_usd`. The connection's Test lists the models from `/models`, sends one embedding, records the result and the measured dimension, and says that mail content leaves this host when the endpoint is on a public host. While the explicit Test of the current URL, model and key is failing, mail is in the needs-settings state and enabling it is refused with the reason; a changed endpoint is not held to an old result, and an endpoint never tested is not blocked. A dimension that differs from the current index does not fail the Test. The removed chat inputs `mail_chat_url`, `mail_chat_model`, `mail_chat_max_tokens`, `mail_chat_key`, `mail_chat_ca_file` and `mail_chat_proxy` (as host keys, `ATRIUM_MAIL_MAIL_CHAT_*` variables or `_file` bindings) are refused naming that replacement, and `atrium endpoints probe` no longer exists.
- **Paid and free mail stages.** The folder judgment at the last routing stage, the flag vote and the event check for unread inbox mail, the commitment scan and the model package check are paid classifications: each message is one Haiku request with a fixed JSON schema (no tools or history; the flag vote and event check send sender, subject and the first 1500 body characters with at most 80 output tokens; the folder judgment also sends the allowed folders with their top sender domains and up to 10 similar filed messages, and may answer only one of those folders or `uncertain`), charged to the inference ledger and checked against the monthly budget before it is sent. A folder outside the supplied list is refused like any reply that does not match the schema, and an `uncertain` answer goes to the account's uncertain folder or no action as before. The first deferred classification in a pass (monthly budget, a run cap, no Anthropic key, a disabled Anthropic connection or one whose transport cannot be built, an authentication or provider failure) stops further paid classification for the rest of that pass on every account; the pass log names the reason and its cause (for a transport that cannot be built, the CA bundle or proxy error the connection Test shows; a scheduled ops job skipped for it carries the same text), and a budget refusal is not recorded as an endpoint failure. A deferred message keeps its contacts-only flag contribution with empty model fields and no event status, a message deferred at the folder judgment gets no routing decision and no fallback, and the next pass judges it once; a deferred commitment or model-only package scan leaves no scan marker, so the next pass scans that message once. A refusal, a truncated reply, another stop reason or a reply that does not match the schema is charged, logged as a warning that names the message, and ends only that message's classification; the pass continues with the next message. Such a message is asked again at most once, no earlier than one hour after the first charged attempt. A message waiting for that retry does not count toward the per-pass event, commitment or package scan limit, so later mail is still judged in the same pass. After the second charged failure it gets its final outcome without another request: the folder judgment routes it to the uncertain fallback, the flag vote leaves no model judgment, the event check records no event (`model gave no usable answer`), and a commitment or package scan marks it scanned with nothing found. No command re-asks a message after its final outcome; the operator files, flags or adds the event for it directly. Sync, rules, the correction, operator, learned and neighbour routing stages, calendar invitations, the package tracking-number match, snoozes and the recorded safe effects are free stages and keep running after paid classification stops. Rebalance folder naming is also a paid classification: each split cluster is one Haiku request with a fixed JSON schema for the new folder name, charged and budget-checked the same way. A budget deferral stages no split proposal for that cluster and the scan continues with the next one; an unavailable provider, a provider failure or a reply that does not match the schema keeps the name made from the cluster's first sender domain, or `Split` when there is none.
- **Embedding index.** Searches and new mail and Notion embeddings use the embedder that built the current index, and its stored dimension. Notion documents and knowledge records are clipped to the same compiled body limit as mail messages. An upgraded database keeps its 768-dimension index: the first `atrium serve` adopts the configured embedder when it returns 768 dimensions, and otherwise builds a new index as below. When the embedding connection's URL or model changes, `atrium serve` measures the new dimension and re-embeds every mail message and Notion page into a new index in fixed-size batches, while searches keep using the old index and embedder. The Mail settings page shows the index and the progress (done of total, and the last error); a failed batch leaves the old index in place and is retried a minute later. A restart resumes without re-embedding finished rows. When every row is embedded the new index replaces the old one in one transaction and the old index is dropped. Changing the embedder back before the swap discards the partial index. A key, CA bundle or proxy set for a new URL is not used for the old URL while the new index builds. Each embedded row records the hash of the text it sent: editing a knowledge record or a Notion page re-queues it, a write-back for a row that changed, was retracted or was deleted while the request was in flight is discarded, and retracting or deleting a record removes its vector in the same transaction.
- **Notion mirror.** `atrium serve` runs `notion/notion-sync` 3 minutes after start and every 15 minutes from the previous run's start. It shares its claim and resource lock with `atrium notion sync`, which refuses while another invocation holds the mirror. A missing Notion connection or token records `skipped_unconfigured` without a pass row; configured runs record the existing `notion-sync` pass. A failed run retries with backoff from 1 minute to 15 minutes. Serve cancels the mirror when stopping. There is no separate Notion sync unit or timer.
- **iCloud mirrors.** `atrium calendar sync` and `atrium contacts sync` read every iCloud calendar (events only) and address book over CalDAV and CardDAV, and make `calendar_dir` and `contacts_dir` hold exactly one file per server object (`<collection>/<name>.ics` or `.vcf`). Nothing is written to the server. An unchanged object is not rewritten, files are replaced atomically, objects deleted on the server are removed, and a sync that fails to fetch (bad login, unreachable server) changes nothing. Each run records a `caldav` or `carddav` pass. `atrium serve` runs them as the jobs `calendar/caldav` and `contacts/carddav` 1 minute after it starts and then every 15 minutes from the start of the previous run; a missing iCloud login or mirror directory records the job run `skipped_unconfigured` and no pass, and a failed run is retried after 1 minute, doubling per consecutive failure up to 15 minutes.
- **iCloud login.** Calendar and contacts sign in with the app password of an enabled iCloud-preset mail account: the one named by `calendar_account`, or the only one when `calendar_account` is empty. The user name is `icloud_apple_id`, or the account's login when that is empty. With no such account, several and no `calendar_account`, or a `calendar_account` that names no enabled iCloud account, the iCloud login is missing and the reason names the problem. The Calendar settings page (`/settings/calendar`) edits `calendar_account`, `icloud_apple_id`, `icloud_calendar`, `default_event_minutes`, `work_hours` and `work_days`.
- **Scheduling.** `find_slot` lists free windows of a requested length inside `work_hours` (default `09:00-17:00`) on `work_days` (default Monday to Friday) in the configured time zone, against the iCloud mirror and Google Calendar; timed events block time, all-day events do not. `calendar_list` and `find_slot` read every iCloud mirror collection when the calendar is `icloud` (or empty) and Google Calendar when it is `google`; any other name selects that mirror collection. `calendar_update` and `calendar_rsvp` only create proposals. On approval an update changes the title and times of the existing event, and its location and notes when given, and keeps everything else (recurrence, exceptions, alarms, organizer, attendees and other properties); on iCloud it also increments `SEQUENCE`. An RSVP changes only the operator's own response (iCloud: the attendee matching `icloud_apple_id`; Google: the attendee marked as self). Google writes send no notifications. Undo restores the previous event.
- **Calendar writes.** `calendar_create`, `calendar_update`, `calendar_rsvp`, `calendar_delete` and `event_propose` only create proposals; nothing reaches the calendar until the operator approves. On approval the write records an intent before the external call; a write whose outcome is unknown blocks its proposal, which is listed on Needs you until the operator resolves it with `atrium proposals resolve <id>` or Mark checked.
- **Needs settings.** A module is on only when its flag is true and its required settings are met: mail needs the `service/embedding` connection, and stays on when an automatic health check or a failed request marks that connection failing (only an explicit Test of the current embedding configuration holds it); calendar needs an iCloud CalDAV login or Google Calendar credentials; media needs the host `media.media_root` and the `service/qbittorrent` connection; the assistant needs nothing: without the `service/anthropic` API key it stays on, chat and paid scheduled runs are refused as not configured (scheduled jobs record `skipped_unconfigured` with no model request), model-free jobs such as task reminders and knowledge export and the Scheduled, settings and Export pages keep working, and `/settings/connections` shows the Anthropic credential as unset; notifications need `webpush_subject`; Grafana needs the `service/grafana` connection with its viewer token and the assistant. `atrium settings set <name>_enabled true` is refused, naming what is missing, while a requirement is unmet; a pinned flag whose requirements fail leaves the module in the needs-settings state, which behaves as off.
- **What disabling does.** A disabled module serves no pages (404) and offers no assistant tools, and its entries leave the navigation and the settings tabs. Its commands exit 0 without output or work, so its units and timers finish cleanly. The scheduler skips its built-in jobs (media channels, sweep and thumbnails, calendar candidates; the knowledge export needs the assistant, and its Notion target the Notion module), the mail pass skips its calendar event-candidate stage, and notification sends (media additions, skipped-budget notices) are dropped while notifications are off. Its tables and data stay. The mail pause kill switch on the CLI (`atrium live pause`, `resume`, `status`) and `atrium replay` stay available while mail is off; the web pause and resume routes return 404. The scheduled calendar-candidates job needs both calendar and mail. With the wiki root unset, the Notion write tools (`notion_create_page`, `notion_update_page`, `notion_move_page`, `notion_archive_page`, `notion_add_alias`) are hidden from the assistant. `atrium calendar google-auth` stays available while calendar is off.
- **Adoption on first start.** The first start of a database that already holds operator data (any row in settings, secrets, accounts, threads or usage) enables every module whose requirements are met and records the migration in `settings_audit`; a module whose requirements are not met stays off and is logged. A database with no operator data starts with core only. A pinned flag is never rewritten.
- **Units.** `atrium-watch` restarts only on failure, so a disabled module's clean exit does not restart in a loop. Scheduled jobs run inside `atrium serve` (there is no separate scheduler unit); the scheduler runs whenever `atrium serve` runs and admits each job by its own module, so with the assistant off the model-free media, DAV mirror and mail jobs still run while assistant jobs, calendar candidate drafting, Grafana jobs and cron prompts are recorded as `skipped_module`. A job whose shutdown policy is cancel (media thumbnails) is canceled as soon as serve starts stopping, and a canceled or timed-out ffmpeg or ffprobe is killed with every process it started; every other job may finish within the shutdown work deadline. Each job is bound to its module: disabling a module stops its running jobs (the run is recorded as `skipped_module`) and refuses their next external effect. The Scheduled page is read-only: built-in jobs are seeded on the first scheduler pass, and the scheduler syncs their schedules at startup and on each tick, so a changed schedule setting appears on the page after the next tick. `atrium agent tick` and `atrium agent scheduler` remain for manual runs; claims are fenced, so they never run a job serve is running.
- **Background services.** `atrium serve` supervises its background work: recovery of interrupted proposals and drafts (before the first request, then every minute), the embedding index, the connection health watch, the notifications monitor, the assistant catalog check and the scheduler. A failing service is logged (`service <name> failed; restarting in <delay>`) and restarted with a backoff from 1 s to 1 min; the web UI stays up. Enabling or disabling a module stops that module's services and jobs before the change is published and starts them again when it is enabled.
- **One owner per database.** `atrium serve` takes a nonblocking lock on `<database>.serve.lock`, next to the database's real path, before it opens or migrates the database, and holds it until the database is closed. A second serve on the same database, also through a symlink or a relative path, exits nonzero with `is in use by a running atrium serve or destructive database command`, without touching the database. A database file with more than one hard link is refused. `db rekey`, `db encrypt`, `db import-v2`, `db shell` and the install step of `restore` take the same lock and refuse while serve runs; `db backup`, `db check`, `backup` and `restore --verify` stay available. The kernel releases the lock when the process exits, also after a crash; the lock file is never deleted.

## Database

- **Encryption at rest.** With a database key, every command opens the database encrypted with SQLCipher, and a database created under that key is encrypted. The key is 64 hexadecimal digits, supplied by `db.key_file` in the configuration file, by `ATRIUM_DB_KEY` or `ATRIUM_DB_KEY_FILE`, or by the `db_key` systemd credential. Without a key the database stays plaintext.
- **Refusals.** atrium refuses to start or run a command, and changes nothing, when:
  - a key is configured but the file is plaintext;
  - the file is encrypted but no key is configured;
  - the key does not open the file;
  - a key is configured but the binary has no SQLCipher engine (the `modernc` build refuses any key);
  - the database has tables but no v3 marker (a v2 database): the message points at `atrium db import-v2`.
- **`atrium db` commands.**
  - `check` reports the database path and encryption state, runs `PRAGMA integrity_check`, and prints row counts of FTS5 and vec0 tables; it fails if the integrity check does not return `ok`.
  - `backup <dest>` writes a consistent copy encrypted like the source, verifies it, and refuses a destination that already exists.
  - `encrypt` converts a plaintext database to the configured key. It copies the database into a fresh encrypted file with `sqlcipher_export`, checks that the copy has an encrypted header, passes `PRAGMA integrity_check`, has the row count of every table, and returns the same nearest rows for a sample vector in each vec0 table, and only then replaces the file. It refuses when no key is configured, when the database is already encrypted, when another process holds it (the atrium units and timers must be stopped), and when it records an unknown newer schema. A refusal or failed check leaves the database unchanged. Snapshots and backups made before the conversion stay plaintext.
  - `rekey` re-encrypts an encrypted database under a new 64-hex-digit key read from `--new-key-file` or standard input, never from the command line. It refuses when no key is configured, when the new key equals the current key, when another process holds the database (the atrium units and timers must be stopped), and when the database records an unknown newer schema. It writes and verifies a re-encrypted copy before replacing the file, so a failed rekey leaves the database unchanged, and it records the retired key's id in `db_key_history`.
  - `shell` runs SQL statements read from standard input against the database.
  - `import-v2 <path>` copies a v2 database at schema version 11 into the configured fresh v3 database and prints one line per table with its carried, rebuilt or dropped row count, one line per setting with its action, one line per effective source pin and per secret, and a totals line ending in `unmapped_operator_choices=0`; a nonzero count fails the import. `--source-config` names the v2 `ATRIUM_CONFIG` file and `--source-env` a `NAME=VALUE` file whose pins decide the effective source value before a shadowed row. `settings_audit` history is carried unchanged before the sanitized import entries. An unknown public setting is dropped and named without its value; an unknown nonempty secret refuses the import by name. Scheduled jobs keep their schedule, enabled state and prompt override; a built-in job is matched to the module that now declares it, one no module declares is dropped (`drop-retired-job`), a stored schedule setting replaces the carried schedule, and no v2 job lease, run or claim is carried. It opens the source read-only and refuses a source that is already v3, is at another version, already has a v3 job claim table, has an embedding rebuild in progress, or has a mail or agent write in flight, and a destination that already holds imported rows. Everything is copied in one transaction with foreign keys checked, so a failure leaves the destination without imported rows. See [Upgrading](nixos.md#upgrading) for what it carries and leaves behind.
- **Migrations.** Pending schema migrations are applied under an exclusive lock when the web service or a command such as `atrium settings` or `atrium secrets` opens the database. atrium does not make a backup first. The v3 baseline is the schema in `internal/db/schema/`, created by migration 1 as a single step; the schema files are edited directly until the freeze in phase 11, and every later change is an additive migration. A database created by v2 has no v3 marker and is refused with a message pointing at `atrium db import-v2`.
- **Upgrading a v1 database.** v1 data reaches v3 through v2: import it into a v2 database with the v2 binary, then import that v2 database with `atrium db import-v2`. v3 refuses a v1 backup archive; decrypt or extract it with the v1 binary first.
- **Newer database, older binary.** A binary refuses a database that records a migration it does not know, before writing anything. Going back to an older release therefore needs a database backup taken before the upgrade, and loses every write made since; changing the binary alone does not reverse a migration.
- **What the database is not.** The database holds records, stored settings and assistant history. Uploaded files under `files/` beside it, the Notion wiki and the rebuildable message and media caches are separate, so the database alone is not a complete backup; `atrium backup` covers the database and `files/`.
- **Connection tuning.** Semantic search and mail routing run on one dedicated read connection with a 192 MiB page cache, so a process that searches can hold up to that much memory for the cache; every other connection caches 2 MiB. All connections keep temporary tables and indexes in memory and cap the WAL journal at 64 MiB.
- **`atrium backup <dest>`.** Writes one new archive (a tar file; it refuses an existing destination) holding a consistent copy of the database taken through the SQLite backup API, so it is safe while atrium runs, and every regular file and directory under `files/`. The mail and media caches, mirrors, `pause` and the media link key are not included and re-sync or regenerate after a restore. With a database key the files are sealed with a subkey derived from the key and a random per-archive salt kept in the header (file names stay visible), and the archive records a key verifier, the key id and the retired key ids, never the key; a keyed tag covers the header and the entry list. Without a key the archive is plaintext and carries checksums only. The header also declares the file and directory counts and the total stored size, and readers refuse entries beyond them. Archives are format 2; a format-1 archive is refused. The archive is staged beside the destination, read back and checked, and only then published; a destination that is the database or lives under `files/` is refused.
- **Scheduled backups.** `atrium serve` runs the model-free job `core/backup` on the host schedule `core.backup_schedule` (default `daily 03:00` in the operator time zone; an invalid value logs a warning and the default applies). The job is persistent: a run missed while serve was down runs once at start, however many occurrences were missed. Each run writes one new verified archive `atrium-<UTC timestamp>.backup` into the host directory `core.backup_directory`, recording the `backup` pass, then deletes regular `atrium-*.backup` files directly in that directory beyond the newest `core.backup_keep` (default 5) that are older than `core.backup_keep_days` (default 14) days; the newest archive is never deleted and a failed archive prunes nothing. Without a directory the job records `skipped_unconfigured`, writes no archive and no pass row. A run has 2 hours; at the timeout, or 105 seconds into a shutdown, it stops writing within a few MiB, discards its temporary files, publishes nothing and releases the `backup` resource. Each run first deletes its own temporary files (`.atrium-<timestamp>.backup.<n>`, `.atrium-snapshot.<n>` and their `-journal`, `-wal`, `-shm` sidecars) in the directory that are older than 2 hours, which a killed process may leave behind. `atrium backup <dest>` shares the job's claim and `backup` resource and refuses with `held by another invocation` while the job runs. With NixOS, `services.atrium.backup.*` renders these host keys; there is no backup unit or timer.
- **`atrium restore <archive>`.** Replaces the database and `files/` with the archive contents. It first reads the whole archive without writing anything and checks its tag, entry sizes and sealed contents, then unpacks it into a temporary directory beside the database, runs the database checks and migrates an older schema. It refuses unless it holds the database lock and exclusive access (the atrium units and timers must be stopped), when the archive records a newer schema than the binary knows, when the archive is corrupt, modified or holds anything but regular files and directories, when it is a v1 archive, and when the key does not match: an encrypted archive needs the key it was made under, which after a rekey is the old key and is passed with `--key-file`; a plaintext archive is refused while a key is configured, and passing `--key-file` for a plaintext archive is an error. It also refuses when an existing database cannot be opened and locked with the configured key or the archive's key, because a running instance cannot then be ruled out (this includes replacing an encrypted database with a plaintext archive); `--replace-unopenable` overrides that refusal. Restore never deletes the state it replaces: the previous database (with any `-wal`, `-shm` and `-journal` files) and `files/` are renamed to `*.pre-restore-<UTC timestamp>` beside the originals and their paths are printed, and the operator removes them. Staged files are synced before the swap, and a failure during the swap puts the original layout back. The restored database keeps the key it was archived under; configure that key before starting atrium, or rekey.
- **`atrium restore --verify <archive>`.** Does the same read-only archive pass, unpacking, key checks and database checks (`integrity_check`, FTS5 and vec0 counts, a nearest-neighbour check on each non-empty vec0 table, a migration of the temporary copy), then discards the temporary copy and writes nothing else. When the state directory does not exist yet, the temporary copy is staged beside the archive instead.

## Operations

- **Ops listener.** `atrium serve` also listens on `ops_listen` (`ATRIUM_CORE_OPS_LISTEN`, default `127.0.0.1:9180`; `off` turns it off). A bind or serve failure of the ops listener stops serve like any other listener failure. While serve drains, the ops listener keeps collecting metrics and running the readiness checks against the database. The host input is deployment-only. The public listener never serves `/metrics`, `/readyz` or `/debug/pprof/`; `/healthz` stays on the public listener.
- **`GET /metrics`.** Prometheus text format, recomputed at most every 15 seconds. Existing gauges and counters: `atrium_budget_monthly_usd`, `atrium_budget_spent_usd`, `atrium_budget_spent_ratio`, `atrium_scheduler_jobs{state}`, `atrium_scheduler_job_next_due_timestamp_seconds{scheduled_job}`, `atrium_scheduler_job_last_started_timestamp_seconds{scheduled_job,status}`, `atrium_job_last_success_timestamp_seconds{pass}`, `atrium_job_stale{pass}`, `atrium_readiness_check_ok{check}`, `atrium_db_exclusive_waits_total`, `atrium_db_exclusive_timeouts_total`. In-process metrics: `atrium_http_requests_total{route,method,status}`, `atrium_http_request_duration_seconds{route,method,status}`, `atrium_llm_requests_total{model,kind,partial}`, `atrium_llm_request_duration_seconds{model,kind}`, `atrium_llm_tokens_total{model,kind,type}`, `atrium_llm_cost_usd_total{model,kind}`, `atrium_runs_total{kind,state}`, `atrium_run_steps{kind}`, `atrium_run_duration_seconds{kind}`, `atrium_tool_calls_total{tool,ok}`, `atrium_tool_duration_seconds{tool,ok}`, `atrium_mail_sync_new_total{account}`, `atrium_mail_sync_gone_total{account}`, `atrium_mail_sync_flag_changes_total{account}`, `atrium_mail_sync_duration_seconds{account}`, `atrium_embed_requests_total{model,ok}`, `atrium_embed_duration_seconds{model}`, `atrium_notification_delivery_total{channel,backend,ok}`, `atrium_db_transactions_total{ok}`, `atrium_db_transaction_duration_seconds`. Database-backed gauges: `atrium_queue_depth{queue}`, `atrium_integration_state{integration,state}` (one series per connection; `integration` is the connection id), `atrium_action_links_outstanding`, `atrium_action_links_minted_last_hour`, `atrium_action_links_used_total`, `atrium_notifications_undelivered`, `atrium_notification_push_failing_devices`, `atrium_mail_sync_last_success_timestamp_seconds{account}`. Labels avoid `job`, `instance`, thread, message, run and mail ids, which the scraper sets or which are unbounded. The alert rules and Grafana dashboard for these metrics are `nix/monitoring/atrium.rules.yml` and `nix/monitoring/atrium-dashboard.json`.
- **Tracing.** With `observability.tracesEndpoint` set (or the host `otel_traces_endpoint`), atrium exports OTLP/HTTP spans to that full URL; empty disables tracing. Spans cover HTTP requests, agent runs and steps, Anthropic requests, tool calls, mail sync, embedding calls, connection checks, notification delivery and database transactions. Attributes are an allowlist of opaque ids, counts, durations, model/tool/route names and status codes; prompts, completions, mail content, subjects, addresses, tool arguments and results, and secrets are never recorded. `OTEL_SDK_DISABLED=true` turns export off. Log records carry `TRACE_ID` and `SPAN_ID` when a span is active.
- **`GET /readyz`.** JSON `{"status", "checks"}`. `not_ready` (503) when the database cannot be read or records a newer schema, the configuration does not load, the background services have not started, scheduler recovery has not succeeded, a critical service is backing off or stalled, or serve is draining (check `runtime`: `starting` or `draining`). `degraded` (200) when a pass is stale. Otherwise `ready` (200).
- **`GET /livez` and `GET /healthz` (ops listener).** `/livez` answers 200 `alive`, or 503 `stalled` naming each critical service whose heartbeat is older than its stall limit; it stays 200 while serve drains. `/healthz` answers JSON `{"started", "draining", "ready", "degraded", "services"}`; each service has `name`, `status`, `critical`, `stalled`, `restarts` and a scrubbed `last_error`, and `recovery` reports scheduler recovery. `degraded` is true while a noncritical service backs off or stalls; readiness stays 200 then.
- **Stopping serve.** On SIGTERM or SIGINT, or when a listener fails, serve marks itself draining (`/readyz` 503, systemd `STOPPING=1` once), stops claiming jobs and restarting services, stops accepting requests on the public and emergency listeners and lets accepted requests and running jobs finish, with job and effect renewals alive. Assistant runs, scheduled ones included, finish the model request or tool call in flight and stop at their next step; such a run stays interrupted and resumes at the next start. 105 seconds after the signal it cancels what is still running (an external write still waiting is recorded unknown and blocked, never retried; a canceled run stays interrupted); the last 15 seconds settle the effect ledger and interrupted runs. Then the ops listener closes, the database is checkpointed and closed and the serve lock is released. The systemd watchdog keeps being fed while the drain is healthy. A further signal during the drain changes nothing. Serve exits 0 only when every step finished; work that did not settle, a failed or busy final checkpoint, or a listener failure exits 1. A signal that interrupts startup is a clean stop, not a failure: serve exits with the signal's status.
- **Pass runs.** `atrium sync`, `atrium notion sync`, `atrium proposals scan-all` and `atrium backup` each record one `pass_runs` row (job `sync`, `notion-sync`, `scan` or `backup`, start and finish time, `ok` or `failed` with the error) whichever process runs them. Rows older than the compiled 90-day retention are pruned when a run is recorded. A job is stale when its newest run failed, or when its last success is older than its limit: 1 hour for `sync` and `notion-sync`, 35 days for `scan`, 8 days for `backup`. A job that has never run is not stale.
- **Stale notices.** While notifications are on, `atrium serve` checks for stale jobs at start and every 5 minutes and sends one notification on the system channel per stale job; it sends again only after the job recovers and goes stale again.
- **Notification channels.** Notifications go to one of three channels: `assistant` (the `notify` tool), `media` (new releases) and `system` (stale passes, skipped scheduled runs, 80% and 100% of the monthly budget once per month, mail pause and resume, and integration health). Each channel has a content setting on the Notifications page: `auto` and `full` push the title and text, `title` pushes only the title `atrium` and a pointer to the app.
- **Delivery and health.** Every notification is recorded in the inbox before delivery; delivery is best effort with no retry queue. A notification counts as delivered when at least one Web Push device accepts it; with no devices it stays in the inbox only. A failed delivery can be resent from the inbox; a delivered one is not sent again. A device with three consecutive failures shows in a banner on every page until a delivery to it succeeds.
- **Web Push.** The Notifications page enables or disables push on the current browser, lists the subscribed devices with Remove, and sends a test push to every device. iOS needs the site added to the Home Screen first and shows no action buttons. Pushes need `webpush_subject` (a `mailto:` or `https:` URL), edited on the Notifications page. The VAPID key is generated on first use as the secret `webpush_vapid_private_key` and can be pinned (64 hex digits or the 43-character base64url private key). After a key change every device must enable push again. A push carries the title, at most 240 characters of the body, the thread or page path that opens on tap and, for phone actions, the Approve and Dismiss links; the channel content setting applies. Pushes are encrypted (RFC 8291, aes128gcm) and signed (VAPID, RFC 8292), go only to `https` endpoints at public addresses without a proxy, and take `webpush_ca_file` as an extra CA bundle. Priority 4 and 5 send urgency `high`. A push service answering 404 or 410 deletes the subscription; other failures are counted per device. The web app manifest is `/static/manifest.json`, and the service worker `/static/sw.js` is registered for scope `/`; the CSP allows `worker-src 'self'`.
- **Profiling.** `/debug/pprof/` is served on the ops listener only with `ops_pprof` (`ATRIUM_CORE_OPS_PPROF=true`).
