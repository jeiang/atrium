# Operator-visible behavior and boundaries

This page states what atrium does and refuses to do today. It describes current behavior only. Setting names, types and defaults live in the generated [setting reference](../config/reference.md) and are not repeated here.

## Access

- `atrium serve` binds `127.0.0.1` unless told otherwise. `--auth` selects how a listener authenticates and can be repeated: `proxy` (the default), `oidc`, and `local`. `proxy` and `oidc` can be combined; `local` cannot be combined with another mode. A listener in proxy or oidc mode refuses to start without an accepted Host (`--allowed-host`, or the public host setting).
- `atrium serve` refuses to start, exits non-zero and warns that authentication is recommended because the instance holds API keys and mailbox access, when no authentication is in force: local mode on an address that is not loopback, or proxy mode without an accepted Host. `--force-disable-auth` starts it anyway on any interface, logs a warning at start, and shows a persistent "Authentication is disabled" banner on every page. With `--force-disable-auth` on a non-loopback address, `--allowed-host` (or the public host setting) is required, and without it `atrium serve` exits non-zero. The flag has no effect when proxy authentication is configured or local mode listens on loopback; the banner then does not appear.
- Every request except `GET /healthz` must carry an accepted Host header; any other Host receives `400`.
- In proxy mode the request must carry a `Remote-Groups` header that lists `atrium_access`, otherwise it receives `403`. Static assets under `/static/` and valid signed media links are exempt from the group check. The Host check still applies to them. A proxy request is an administrator only when `Remote-Groups` also lists the admin group (`oidc_admin_group`, default `atrium_admin`); otherwise it is access-only, so the identity provider behind the proxy must send `atrium_admin` for administrator features. In a listener that does not select proxy mode, `Remote-Groups` and every other proxy header grant nothing. A listener that combines proxy and oidc mode trusts `Remote-Groups` from whoever can reach it, so the reverse proxy must strip or overwrite every `Remote-*` header on every request; run OIDC alone (`web.auth = "oidc"`) when the listener is reachable without such a proxy.
- In oidc mode a request needs a valid session, otherwise a page navigation is redirected to `/login` (with `next` for the page asked for), an htmx request receives `401` with `HX-Redirect`, and any other request is redirected to `/login`. Only `GET /healthz`, static assets, valid signed media links, `/login` and `/auth/callback` answer without a session. In a listener without oidc mode `/login`, `/auth/callback` and `/logout` answer `404`.
- Sign-in is the authorization code flow with PKCE (`S256` always; a provider that does not advertise `S256` is refused), a state value bound to the browser by a cookie, a nonce, and ID token verification (signature against the provider's JWKS with rotation, issuer, audience, expiry, nonce). Group names come from the configured claim in the ID token, with the userinfo endpoint as fallback. A member of the admin group (default `atrium_admin`) is an administrator; a member of the access group (default `atrium_access`) can use atrium; an administrator needs no second group. Providers without a group claim, such as Google, grant access through verified email or domain allowlists per role (`oidc_access_emails`, `oidc_admin_emails`, `oidc_access_domains`, `oidc_admin_domains`); for Google the domain is the hosted-domain (`hd`) claim. The hourly re-check runs for every provider and ends or demotes a session whose address, domain, group or provider account no longer qualifies. Refresh and access tokens are stored sealed with a key derived from the client secret; a group-based setup needs a client secret or an encrypted database, and the client secret itself can only be stored in an encrypted database (otherwise pin it with `ATRIUM_AUTH_OIDC_CLIENT_SECRET_FILE`). On https the session cookie is read only under its `__Host-` name. The `oidc_preset` setting picks defaults for Pocket ID, Authelia, Authentik, Keycloak, Google and Microsoft Entra; `generic` takes the claim and scopes from settings. Microsoft Entra reports group object IDs, so the group settings take those IDs.
- A session is stored in the database and referenced by an opaque cookie (`HttpOnly`, `SameSite=Lax`, `Secure` and the `__Host-` prefix on https). It ends after 7 idle days (sliding, `oidc_session_idle_days`), after 30 days in all (`oidc_session_max_days`), on sign-out (`POST /logout`), or when the hourly group re-check (`oidc_recheck_minutes`) finds the account without access or the provider rejects the refresh token. An unreachable provider keeps a session for up to one more hour. The OIDC client secret is the write-only `oidc_client_secret` secret.
- `atrium login-link` prints a single-use administrator sign-in link: `<public URL>/login/link#<token>`, valid for 15 minutes unless `--minutes` says otherwise (1 to 60). It needs only the host's database access and the public URL, so it works with no OIDC configured and when OIDC is misconfigured, in a listener with oidc mode. The token is in the URL fragment and is never sent to the server by the browser until `Continue` posts it; opening the link only shows the landing page. The token is an HMAC-signed nonce (keyed by the generated `action_link_key` secret) and only its hash is stored. A link works once: a used or expired link, and any tampered or unknown token, creates no session. Issuing a link and every redemption attempt are recorded in the settings audit under the key `login_link`, without the token. A link session is an administrator session that ends after 8 hours, is not re-checked against the identity provider, and opens `/settings/auth` when sign-in is not set up, otherwise `/chat`.
- In an oidc-mode listener `/settings/auth` (the Sign-in tab) sets up OIDC: pick a provider (Pocket ID, Authelia, Authentik, Keycloak, Google, Microsoft Entra or generic OIDC), follow its identity-provider steps with the redirect URI and group names to copy, and enter the client details. Fields pinned by deployment configuration show read-only. Test sign-in opens the provider in a new tab with a separate test state; it never creates or replaces a session. The test passes only when the tested account gets both access and administrator rights under the tested settings. Activate saves exactly the tested settings (and the client secret, which needs an encrypted database unless pinned) in one transaction and only for a test that passed within 15 minutes; editing the form or testing again withdraws the pass. A failed test changes nothing. The pending test lives in the running process and is lost on restart. `atrium settings set` and `atrium secrets set` still change the same settings without the test.
- Administrator-only routes answer `403` to a session without the admin group: everything under `/settings` and `POST /live/resume`. Pause stays open to everyone with access.
- In local mode there is no group check and every request is an administrator. Without an explicit allowed Host, the accepted Hosts are `localhost`, `127.0.0.1` and `[::1]`.
- The NixOS module runs the public listener in proxy mode, optionally with oidc added, and, by default, a second listener bound to `127.0.0.1` in local mode.
- `POST`, `PUT`, `PATCH` and `DELETE` requests need the CSRF token that atrium issues in a cookie and a request whose `Origin`, when present, matches the Host. Responses carry a Content-Security-Policy.
- A signed media link grants one file under `/media/file/`. It carries an expiry and an HMAC-SHA256 signature, and is valid for 12 hours from issue. A missing, altered or expired signature is not accepted and the request falls back to the normal group check. The signing key is the `link_key` secret in the media module. A deployment pin (`ATRIUM_MEDIA_LINK_KEY`, `ATRIUM_MEDIA_LINK_KEY_FILE` or `media.link_key_file`) wins over the stored value; otherwise the key is stored in the database, generated on first use. An existing `media-link.key` beside the database is moved into the stored secret on first use and the file is removed, so links issued before the upgrade stay valid. Changing the key invalidates every issued link.

## Mail safety

Every mailbox write goes through one safety gate.

- **Accounts.** Mail accounts come from the TOML file named by `mail_accounts_file` (a deploy-time setting): one `[[account]]` table per account with `id` (up to 32 lowercase letters, digits and single underscores, starting with a letter; it keys the account's cached mail, so keep it stable), `preset` (`icloud` or `gmail`, which supplies the IMAP and SMTP hosts and the provider's folder behavior), `login`, `password_file` (`${NAME}` expands an environment variable, for example `${CREDENTIALS_DIRECTORY}`), and optional `label` and `enabled` (default true). Every command reads the file at start and refuses to run, naming the entry, when it has an unknown key, a duplicate id, an invalid id, an unknown preset, or a missing or empty password file. A disabled account is listed but never opened or synced. Removing an account from the file stops its sync and keeps its cached mail and history. `ICLOUD_MAIL_USERNAME`, `ICLOUD_APP_PASSWORD`, `GMAIL_ADDRESS` and `GMAIL_APP_PASSWORD` are no longer read.
- **Accounts page.** The Mail settings tab lists every account with its health. Accounts from the file show read-only as set by deployment. Test signs in over IMAP and lists the folders, records the result as the account's health (`mail_<id>`, shown in the admin banner while not ok), and changes nothing else. Add account takes an id, label, iCloud or Gmail preset, login and app password; it runs the same check first and stores nothing when it fails. The app password is stored only in an encrypted database (as the secret `mail_password_<id>`) and is never shown again. Editing a stored account tests again when the login or password changes. Removing a stored account deletes its record and password and keeps its cached mail. The page has no live or shadow control. The atrium units pick up added, changed or removed accounts when they restart.
- **Modes.** The mail mode (`mail_mode`) is `shadow` (the default) or `live`; any other value is refused. It is a deploy-time setting of class `bootstrap`: only an environment variable or the configuration file sets it, and `atrium settings set` cannot change it. In `shadow`, atrium records what it would do and makes no automatic mailbox writes: the automatic pass returns without acting.
- **Automatic writes** happen only in `live` mode and only while atrium is not paused (a `pause` file beside the database). They are limited to: filing or trashing read, unflagged inbox mail according to recorded decisions; flagging unread inbox mail from known contacts; applying the operator's folder corrections made after go-live; and rule-based deletions, which run at most once a day per account. Mail that was already read and in the inbox when live mode first started is never touched by the inbox pass.
- **Approval-required writes** are every other mailbox change, such as the proposals from rebalance, deletion and label scans. They are applied only when the operator approves the proposal; the approval is the only scope in which they pass the gate in `shadow` mode.
- **Operator send.** The assistant can save and edit drafts but has no tool to send them. Sending is an operator action from the Drafts page. In `shadow` mode the only append the gate allows outside an approved proposal is the copy of a sent message into the account's Sent mailbox.
- **Write caps.** A pass makes at most the write cap of automatic writes per account (setting `write_cap`, default 100, range 1 to 1000); the remainder is deferred to a later pass and logged.
- **Verification.** Before each write atrium re-reads the message on the server. If the message changed (for example it was read, flagged or moved in the meantime), the write is skipped and recorded as skipped with its reason.
- **Protected folders.** Trash, Sent, Drafts and Junk (identified by their special-use flags or well-known names such as Bin, Deleted Items, Sent Items and Spam) are never a source or a destination of automatic filing. Destinations must be existing, safely named folders; Gmail labels beginning with `\` or `[Gmail]` and system labels are refused.
- **Retries.** A message whose automatic action failed or was skipped is attempted again until the configured number of such outcomes (setting `write_attempts`, default 3) is recorded for it. A message already acted on is not acted on again.
- **Outcome unknown stays blocked.** atrium records the intent before it writes. If the connection is lost or the process is interrupted so that the result is unknown, the action is marked interrupted and is never retried automatically. An undo that copied the message back but did not expunge the original, or whose outcome is unknown, is likewise recorded as blocking; further undo of that action is refused until the operator resolves the mailbox by hand.
- **Resolving a blocked write.** After the operator has checked the mailbox, `atrium proposals resolve ID` settles every blocked ledger row of a proposal, and `atrium live resolve ID --outcome undone|not-undone` settles a blocked automatic-action undo. The Proposals page offers the same for a proposal with a blocked write, and the Activity page for a blocked undo, as operator-only buttons under the usual CSRF and same-origin checks. A blocked forward write has one button, Mark checked. A blocked undo has two, Messages are back (`undone`: the undo counts as done, and resolving a corrected message this way also clears its correction) and Not moved back (`not-undone`: the undo may be attempted again); `atrium proposals resolve` needs `--outcome` only when one of its blocked rows is an undo. Resolving only rewrites the blocking row to a settled marker and appends who, when, the outcome and the previous error text to the append-only `write_resolutions` table; it never opens the mailbox, never performs and never retries a write, and it does not decide whether the original write took effect. A proposal can then be approved or undone again, and a message held back by the blocked row is no longer skipped as unresolved. A row still marked in flight is refused while its write or undo runs: the running process renews the row every 30 seconds, and the row becomes resolvable 2 minutes after its last renewal (once the process stopped or hung). An in-flight automatic-action undo recorded before migration 6 has no start time and is resolvable at once. A proposal that is still being applied is refused. A write or undo that finishes after its row was resolved does not overwrite the recorded outcome, and a second undo of an action cannot start while its first is in flight or unresolved.
- **Undo.** Every applied automatic action that has an undo plan can be undone by the operator, which moves the message back, restores labels, restores the trash state or removes the flag. Undo runs under its own approval scope and also records its outcome.
- **Message handling.** Moves use COPY, STORE `\Deleted` and UID EXPUNGE, not IMAP MOVE.

## Assistant limits

- **Scheduled runs** (cron) cannot call any tool whose effect is a write. They can read, and they can create proposals for the operator to approve.
- **Nightly runs** have the same read access and may in addition create, update, move, archive and alias Notion pages, and update the profile. Profile changes are logged and undoable.
- **Chat** is the only run kind that can create calendar events, edit drafts, or change media or schedule records.
- **Research subagents** are limited to read-only tools, by default at most 12 steps and $0.25 of spend per run, with at most two running at once (`agent_subagent_max_steps`, `agent_subagent_max_cost_usd`, `agent_subagent_max_concurrent`). They cannot write, notify, schedule or start other agents.
- **Models.** Chat threads run on Haiku 5.5, Sonnet 5.5 or Opus 5.5. A new thread takes the `default_model` setting (default `claude-haiku-5-5`) unless the new-thread form names a model; the thread's model, effort and context size can be changed later. Scheduled, nightly and subagent runs use Haiku 5.5. Each run sends its thread's model and each usage row is priced at that model's rates; a model outside the built-in catalog is refused before a request is sent. The context size cannot exceed the model's context window. Haiku 5.5 bills prompts over 100K tokens at the higher rates; Sonnet 5.5 and Opus 5.5 have flat rates.
- **Per-run limits.** Each run stops after the maximum number of steps for its kind (`max_steps_chat`, `max_steps_cron`, `max_steps_nightly`, default 24 each; research subagents use `agent_subagent_max_steps`) and the run cost cap of its model (`max_run_cost_usd_haiku_5_5` default $2, `max_run_cost_usd_sonnet_5_5` default $6, `max_run_cost_usd_opus_5_5` default $10; each covers writing a full 1M-token request at the 1-hour rate); all are settings. The old `max_run_cost_usd` setting no longer exists: a stored row or `ATRIUM_ASSISTANT_MAX_RUN_COST_USD` is ignored, and each logs a warning at command start naming the new settings (the stored row's warning also shows its value). Remove the orphaned row with `atrium settings unset max_run_cost_usd`, which is audited; values are not carried over to the new settings. A run also stops when the same tool call returns the same result `doom_loop_threshold` times in a row (default 3). The stop reason is the run's error.
  The cap is checked before every request, including the client-side compaction request (priced as uncached input plus its output limit): the run stops when what it has spent plus the cost of writing the next request to the cache cold, at the thread's cache lifetime (`cache_ttl_chat`: 1-hour writes cost more than 5-minute writes), would pass the cap, and the refusal names the setting to raise. A cold 400K-token Opus request costs $3.20 to write with a 1-hour cache.
- **Model stops.** A refusal, a reply cut off at the output or context limit, and an empty paused or ended turn each end the run with a message in the thread; a refusal names the policy category and any model the server recommends instead. When the server falls back to another model after a refusal, the thread notes the switch and the fallback's tokens are recorded as their own usage row at that model's rates.
- **Forced tool calls.** A forced `tool_choice` (`atrium agent run --tool-choice any|<tool>`) applies to the first request only and is sent only to models the catalog allows (Haiku 5.5); Sonnet 5.5 and Opus 5.5 receive the request without it.
- **Monthly budget.** Spend for the calendar month in the operator's time zone is compared with the monthly budget (`monthly_budget_usd`, default $150). Chat stops starting new work at the chat share of the budget (`budget_chat_share`, default and ceiling 100%). Scheduled and nightly runs stop at the unattended share (`budget_unattended_share`, default 80%), which cannot exceed the chat share. A research subagent does not start once a budget limit has been reached.
- **Anthropic spend limit.** When the Anthropic organization's own spend cap refuses a request (HTTP 429 without a `retry-after` header), the run ends as a budget stop with a budget message and is not retried; scheduled jobs are recorded as skipped for budget.
- **Skills.** Skills are portable as `SKILL.md` folders: frontmatter with `name` and `description`, then the Markdown body. The Skills settings page exports every skill as a zip and imports a `SKILL.md` or a zip of skill folders; `atrium skills export <dir>` and `atrium skills import <path>` do the same for directories, a single skill or a zip. An import replaces skills of the same name and leaves an unchanged skill (and its update time) alone, is all-or-nothing, caps each `SKILL.md` near four bytes per `agent_skill_body_chars` character plus 4 KiB of frontmatter and an import at 16 MiB,  and refuses a name, description or body outside the skill limits. The skills index in the system prompt is capped by `agent_skill_index_chars` (default 4000). Built-in skills come first, then the most recently updated, then by name; the first skill that does not fit and all after it are left out, the prompt says how many, and the Skills page marks each as not indexed. `load_skill` still reads a skill that is not indexed.
- **Prompts.** The system prompt (`prompt_system`), the compaction summary instructions (`prompt_summary`) and the shared subagent rules (`prompt_subagent`) are editable on the Prompts settings page or with `atrium settings set`; an unset key uses the built-in text, and Reset (or `atrium settings unset`) restores it exactly. Edits are audited and apply to the next request of every thread. The untrusted-data preamble is fixed in code, is not a setting, and is always placed before the system prompt.
- **Sending mail** is an operator action only; see [Mail safety](#mail-safety).
- Tool permissions, run-kind restrictions and spending limits are enforced in code, not in prompts. Mail, files, pages and tool results are treated as untrusted data and cannot grant URL access or extend skills. Arbitrary web fetches use an allowlist and SSRF protection on every redirect.
- Code execution is unavailable.

## Settings and secrets

- **Precedence.** For a setting: an environment variable, then the configuration file, then a value stored in the database, then the default. An environment variable or configuration file value pins the setting.
- **Pins are read-only.** A pinned setting cannot be changed or unset through the settings registry; `atrium settings set` and `unset` refuse it and name the source of the pin.
- **Naming.** The environment variable for a setting is `ATRIUM_<MODULE>_<KEY>`, where `<KEY>` is the whole registry key. When the key already begins with the module name, the module appears twice: `ATRIUM_ANTHROPIC_ANTHROPIC_ADMIN_KEY` and `ATRIUM_OPENAI_OPENAI_ADMIN_KEY` for the keys `anthropic_admin_key` and `openai_admin_key`. For the database key (module `db`, key `key`) the variable is `ATRIUM_DB_KEY`. The [environment variable list](../config/environment.md) is authoritative. A secret setting's environment variable also has a `_FILE` form naming a file whose trimmed contents are the value, for example `ATRIUM_DB_KEY_FILE`; setting both forms is refused. In the configuration file a secret accepts only its `<key>_file` form.
- **Renamed variables.** The earlier unprefixed names (`ATRIUM_MODE`, `ATRIUM_TZ`, `ATRIUM_PUBLIC_URL`, `ATRIUM_CHAT_URL`, `ATRIUM_EMBED_URL`, `ATRIUM_CALENDAR_DIR`, `ATRIUM_ICLOUD_CALENDAR`, `ICLOUD_APPLE_ID`, `GOOGLE_OAUTH_CLIENT_ID`, `ATRIUM_CONTACTS_DIR`, `NTFY_URL`, `NTFY_TOPIC`, `NTFY_MEDIA_TOPIC`, `ATRIUM_MEDIA_ROOT`, `QBITTORRENT_URL`, `ATRIUM_MEDIA_MOVIES_URL`, `ATRIUM_MEDIA_TV_URL`, `ATRIUM_CODEMODE_SOCKET`, `ATRIUM_ASSISTANT_MAX_RUN_COST_USD`) are not read and do not pin anything. When one is set, each command logs a warning at start naming the `ATRIUM_<MODULE>_<KEY>` variable to use instead.
- **Time zone and public URL.** The `tz`, `public_url` and `http_timeout_seconds` settings are read from the database after migration by every command that opens it, so a value set through the registry applies to the web server, the scheduler, the nightly run, the mail watcher and the CLI alike. A pin always wins.
- **Settings CLI.** `atrium settings list`, `get`, `set` and `unset` show or change instance-level values; each shows the effective value, its source (`pin`, `db`, `default`) and its class. Secret settings are neither shown nor changed here.
- **Secrets CLI.** `atrium secrets set <name>` reads the value from standard input (the command line never carries it), `delete` removes it, and `status` reports each secret as `set`, `unset` or `pinned`. Secrets are write-only: no command returns a stored secret. Setting a secret that the deployment pins is refused. A pin-only secret, such as the database key, can be neither stored nor deleted through the CLI.
- **Encrypted database required for stored API and admin keys.** The Anthropic API key and the Anthropic and OpenAI admin keys are refused by `atrium secrets set` unless the database is encrypted.
- **Anthropic API key.** `anthropic_api_key` is a write-only secret setting. `ANTHROPIC_API_KEY` (and `ATRIUM_ANTHROPIC_ANTHROPIC_API_KEY`, with a `_FILE` form of either) pins it; a pinned key cannot be stored or changed. At web start atrium lists the models the key can use and logs a warning for each catalog model the Models API does not offer, or when the list cannot be fetched; startup continues either way.
- **Audit log.** Every settings write and every secret change appends a row to the append-only `settings_audit` table with the key, the actor, the source (`cli`, `ui` or `migration`), and the old and new values. For a secret the row records only `changed`. The table rejects updates and deletes, and the rows are listed read-only on the Activity page.
- **Redaction.** Secret values of at least eight characters are scrubbed from log output, including their URL- and JSON-escaped forms, from audit values and from the recorded `agent_writes` snapshots.
- **Integrations.** The Integrations settings page lists each connection record (ntfy, qBittorrent, TMDB, Notion, Grafana and Anthropic) with its URL, credential state (set, unset or set by deployment) and health: untested, ok, failing, expiring (a known credential expiry within 14 days) or needs re-auth (the service refused the credential). A pinned or deployment-only value is shown read-only, and Test still runs against it. Test checks the values typed in the form first and saves them only when the check passes, so a failed Test leaves the working record as it was; testing unchanged values records the result. `atrium serve` checks every configured integration at start and every 24 hours. Every result is recorded and an admin banner shows while a record is not ok; a change from a previously recorded state also sends one high-priority message on the system channel (the first result for a record sends none). Disconnect clears the URL and credential (refused while either is pinned); the owning module then needs settings and its data stays.
- **Credential checks.** The Notion Test signs in as the integration and fails with "no pages shared with the integration" until a page is shared; when it passes it shows the number of shared pages (`100+` past the first page of results). The Grafana Test signs in with the service account token and searches dashboards: a refused token needs re-auth, and a token that may not search fails with a request to give it the Viewer role. The Anthropic Test lists the models with the key; the form asks for a key from a Console workspace with a monthly spend limit. The Notion token (`notion_token`), Grafana URL (`grafana_url`) and Grafana token (`grafana_viewer_token`) are settings; `NOTION_TOKEN`, `GRAFANA_URL` and `GRAFANA_VIEWER_TOKEN` are no longer read, and a command that sees one logs a warning naming the replacement.
- **Media credentials.** `media_qbittorrent_api_key` and `media_tmdb_token` are secrets (pinnable; stored only in an encrypted database). With the qBittorrent key set, every qBittorrent request carries `Authorization: Bearer <key>`, and Test fails on a server older than 5.2, which has no API keys; without it requests go unauthenticated as before. Every TMDB request carries the read token as `Authorization: Bearer <token>` and never as a query parameter; `TMDB_API_KEY` is no longer read, and a refused token shows as a TMDB error. Media pages that show TMDB data carry the TMDB attribution.
- **Outbound TLS and proxies.** Each integration has `<name>_ca_file` (a PEM bundle added to the system roots) and `<name>_proxy` (an `http`, `https` or `socks5` URL; otherwise the proxy environment variables apply). An unreadable or empty CA bundle and an unknown or invalid certificate fail the request; certificate verification cannot be turned off, and the lint check rejects code that sets `InsecureSkipVerify`. ntfy, Notion, Grafana, qBittorrent and TMDB use this transport for every request and Test; Anthropic uses it for Test only.
- **Check on failure.** When a request from `atrium serve` to ntfy, Notion, Grafana, qBittorrent or TMDB fails to connect or answers 401, 403 or a 5xx status while the integration is recorded as working, its check runs at once instead of waiting for the daily check. After a check that passes, further failures wait 5 minutes before the next one.

## Modules

- **Toggles.** Mail, calendar, contacts, Notion, media, assistant, notifications and Grafana are modules with a `<name>_enabled` setting; core is always on. Change one with `atrium settings set <name>_enabled true` or `false` and restart the atrium units, or pin it with `ATRIUM_CORE_<NAME>_ENABLED`. A pinned flag cannot be changed through the CLI. The money module is removed: its tables and rows stay in the database, its stored settings are ignored, and its `fx-rates` scheduled job is cancelled on the next scheduler start.
- **Contacts.** The contacts module needs `contacts_dir` and owns `contacts_lookup` and `atrium contacts sync`. Mail uses it as an optional source: with contacts off or no directory, the mail flag rule flags no sender as a contact and the triage flags view says no contact source is configured. On a database adopted from Phase A, the first start of this build enables contacts when `contacts_dir` is set.
- **Mail model endpoints.** The chat endpoint (`mail_chat_url`, `mail_chat_model`) and the embed endpoint (`mail_embed_url`, `mail_embed_model`) are any OpenAI-compatible servers. Each can take a Bearer key, `mail_chat_key` and `mail_embed_key` (secrets, pinnable; stored only in an encrypted database), sent only to its own endpoint. `atrium endpoints probe` (available while mail is off) lists the models from `/models`, sends one strict JSON-schema chat request and one embedding, records the result and the measured embedding dimension, warns on stderr when an endpoint is on a public host, and exits 1 if either probe fails. While the recorded probe for the current URL, model and key is failing, mail is in the needs-settings state and enabling it is refused with the reason; a changed endpoint is not held to an old result, and an endpoint never probed is not blocked. An embedder whose dimension differs from the stored 768 fails the probe.
- **iCloud mirrors.** `atrium calendar sync` and `atrium contacts sync` read every iCloud calendar (events only) and address book over CalDAV and CardDAV, and make `calendar_dir` and `contacts_dir` hold exactly one file per server object (`<collection>/<name>.ics` or `.vcf`). Nothing is written to the server. An unchanged object is not rewritten, files are replaced atomically, objects deleted on the server are removed, and a sync that fails to fetch (bad login, unreachable server) changes nothing. Each run records a `caldav` or `carddav` pass.
- **iCloud login.** Calendar and contacts sign in with the app password of an enabled iCloud-preset mail account: the one named by `calendar_account`, or the only one when `calendar_account` is empty. The user name is `icloud_apple_id`, or the account's login when that is empty. With no such account, several and no `calendar_account`, or a `calendar_account` that names no enabled iCloud account, the iCloud login is missing and the reason names the problem.
- **Scheduling.** `find_slot` lists free windows of a requested length inside `work_hours` (default `09:00-17:00`) on `work_days` (default Monday to Friday) in the configured time zone, against the iCloud mirror and Google Calendar; timed events block time, all-day events do not. `calendar_update` and `calendar_rsvp` only create proposals. On approval an update changes the title and times of the existing event, and its location and notes when given, and keeps everything else (recurrence, exceptions, alarms, organizer, attendees and other properties); on iCloud it also increments `SEQUENCE`. An RSVP changes only the operator's own response (iCloud: the attendee matching `icloud_apple_id`; Google: the attendee marked as self). Google writes send no notifications. Undo restores the previous event.
- **Needs settings.** A module is on only when its flag is true and its required settings are met: mail needs `mail_chat_url` and `mail_embed_url`; calendar needs an iCloud CalDAV login or Google Calendar credentials; Notion needs `notion_token`; media needs `media_root` and `media_qbittorrent_url`; the assistant needs `anthropic_api_key`; notifications need `ntfy_url`; Grafana needs `grafana_url`, `grafana_viewer_token` and the assistant. `atrium settings set <name>_enabled true` is refused, naming what is missing, while a requirement is unmet; a pinned flag whose requirements fail leaves the module in the needs-settings state, which behaves as off.
- **What disabling does.** A disabled module serves no pages (404) and offers no assistant tools, and its entries leave the navigation and the settings tabs. Its commands exit 0 without output or work, so its units and timers finish cleanly. The scheduler skips its built-in jobs (media channels, sweep and thumbnails, calendar candidates), the mail pass skips its calendar event-candidate stage, and notification sends (media additions, skipped-budget notices) are dropped while notifications are off. Its tables and data stay. The mail pause kill switch (`atrium live pause`, `resume`, `status` and the web pause and resume buttons) stays available while mail is off. The scheduled calendar-candidates job needs both calendar and mail. With the wiki root unset, the Notion write tools (`notion_create_page`, `notion_update_page`, `notion_move_page`, `notion_archive_page`, `notion_add_alias`) are hidden from the assistant. `atrium calendar google-auth` stays available while calendar is off.
- **Adoption on first start.** The first start of a database that already holds operator data (any row in settings, secrets, accounts, threads or usage) enables every module whose requirements are met and records the migration in `settings_audit`; a module whose requirements are not met stays off and is logged. A database with no operator data starts with core only. A pinned flag is never rewritten.
- **Units.** `atrium-watch` and `atrium-agent-scheduler` restart only on failure, so a disabled module's clean exit does not restart in a loop. The scheduler runs from the assistant: with the assistant off it exits, and the media and calendar jobs it hosts do not run.

## Database

- **Encryption at rest.** With a database key, every command opens the database encrypted with SQLCipher, and a database created under that key is encrypted. The key is 64 hexadecimal digits, supplied by `db.key_file` in the configuration file, by `ATRIUM_DB_KEY` or `ATRIUM_DB_KEY_FILE`, or by the `db_key` systemd credential. Without a key the database stays plaintext.
- **Refusals.** atrium refuses to start or run a command, and changes nothing, when:
  - a key is configured but the file is plaintext;
  - the file is encrypted but no key is configured;
  - the key does not open the file;
  - a key is configured but the binary has no SQLCipher engine (the `modernc` build refuses any key).
- **`atrium db` commands.**
  - `check` reports the database path and encryption state, runs `PRAGMA integrity_check`, and prints row counts of FTS5 and vec0 tables; it fails if the integrity check does not return `ok`.
  - `backup <dest>` writes a consistent copy encrypted like the source, verifies it, and refuses a destination that already exists.
  - `encrypt` converts a plaintext database to the configured key. It copies the database into a fresh encrypted file with `sqlcipher_export`, checks that the copy has an encrypted header, passes `PRAGMA integrity_check`, has the row count of every table, and returns the same nearest rows for a sample vector in each vec0 table, and only then replaces the file. It refuses when no key is configured, when the database is already encrypted, when another process holds it (the atrium units and timers must be stopped), and when it records an unknown newer schema. A refusal or failed check leaves the database unchanged. Snapshots and backups made before the conversion stay plaintext.
  - `rekey` re-encrypts an encrypted database under a new 64-hex-digit key read from `--new-key-file` or standard input, never from the command line. It refuses when no key is configured, when the new key equals the current key, when another process holds the database (the atrium units and timers must be stopped), and when the database records an unknown newer schema. It writes and verifies a re-encrypted copy before replacing the file, so a failed rekey leaves the database unchanged, and it records the retired key's id in `db_key_history`.
  - `shell` runs SQL statements read from standard input against the database.
- **Migrations.** Pending schema migrations are applied under an exclusive lock when the web service or a command such as `atrium settings` or `atrium secrets` opens the database. atrium does not make a backup first.
- **Newer database, older binary.** A binary refuses a database that records a migration it does not know, before writing anything. Going back to an older release therefore needs a database backup taken before the upgrade, and loses every write made since; changing the binary alone does not reverse a migration.
- **What the database is not.** The database holds records, stored settings and assistant history. Uploaded files under `files/` beside it, the Notion wiki and the rebuildable message and media caches are separate, so the database alone is not a complete backup; `atrium backup` covers the database and `files/`.
- **Connection tuning.** Semantic search and mail routing run on one dedicated read connection with a 192 MiB page cache, so a process that searches can hold up to that much memory for the cache; every other connection caches 2 MiB. All connections keep temporary tables and indexes in memory and cap the WAL journal at 64 MiB.
- **`atrium backup <dest>`.** Writes one new archive (a tar file; it refuses an existing destination) holding a consistent copy of the database taken through the SQLite backup API, so it is safe while atrium runs, and every regular file under `files/`. The mail and media caches, mirrors, `pause` and the media link key are not included and re-sync or regenerate after a restore. With a database key the files are sealed with a subkey derived from the key and a random per-archive salt kept in the header (file names stay visible), and the archive records a key verifier, the key id and the retired key ids, never the key; a keyed tag covers the header and the entry list. Without a key the archive is plaintext and carries checksums only. The header also declares the file count and total stored size, and readers refuse entries beyond them. The archive is read back and checked before it is moved into place.
- **Scheduled backups.** With `services.atrium.backup.enable` the host runs `atrium backup` on a timer into a directory, one new archive per run; the timer never prunes.
- **`atrium restore <archive>`.** Replaces the database and `files/` with the archive contents. It first reads the whole archive without writing anything and checks its tag, entry sizes and sealed contents, then unpacks it into a temporary directory beside the database, runs the database checks and migrates an older schema. It refuses unless it holds the database lock and exclusive access (the atrium units and timers must be stopped), when the archive records a newer schema than the binary knows, when the archive is corrupt, modified or holds anything but regular files, and when the key does not match: an encrypted archive needs the key it was made under, which after a rekey is the old key and is passed with `--key-file`; a plaintext archive is refused while a key is configured. It also refuses when an existing database cannot be opened and locked with the configured key or the archive's key, because a running instance cannot then be ruled out (this includes replacing an encrypted database with a plaintext archive); `--replace-unopenable` overrides that refusal. Restore never deletes the state it replaces: the previous database (with any `-wal`, `-shm` and `-journal` files) and `files/` are renamed to `*.pre-restore-<UTC timestamp>` beside the originals and their paths are printed, and the operator removes them. Staged files are synced before the swap, and a failure during the swap puts the original layout back. The restored database keeps the key it was archived under; configure that key before starting atrium, or rekey.
- **`atrium restore --verify <archive>`.** Does the same read-only archive pass, unpacking, key checks and database checks (`integrity_check`, FTS5 and vec0 counts, a nearest-neighbour check on each non-empty vec0 table, a migration of the temporary copy), then discards the temporary copy and writes nothing else.

## Operations

- **Ops listener.** `atrium serve` also listens on `ops_listen` (`ATRIUM_CORE_OPS_LISTEN`, default `127.0.0.1:9180`; `off` turns it off, and the NixOS module sets `off` for `atrium-web-local`). The setting is deployment-only. The public listener never serves `/metrics`, `/readyz` or `/debug/pprof/`; `/healthz` stays on the public listener.
- **`GET /metrics`.** Prometheus text format, recomputed at most every 15 seconds: `atrium_budget_monthly_usd`, `atrium_budget_spent_usd`, `atrium_budget_spent_ratio`, `atrium_scheduler_jobs{state}`, `atrium_scheduler_job_next_due_timestamp_seconds{scheduled_job}`, `atrium_scheduler_job_last_started_timestamp_seconds{scheduled_job,status}`, `atrium_job_last_success_timestamp_seconds{pass}`, `atrium_job_stale{pass}`, `atrium_readiness_check_ok{check}`, and the counters `atrium_db_exclusive_waits_total` and `atrium_db_exclusive_timeouts_total` for the serving process. Labels avoid `job` and `instance`, which the scraper sets. The alert rules and Grafana dashboard for these metrics are `nix/monitoring/atrium.rules.yml` and `nix/monitoring/atrium-dashboard.json`, also exposed as `services.atrium.monitoring.ruleFile` and `dashboardFile`.
- **`GET /readyz`.** JSON `{"status", "checks"}`. `not_ready` (503) when the database cannot be read or records a newer schema, or the configuration does not load. `degraded` (200) when a pass is stale or a third party fails its check (ntfy `/v1/health` while notifications are on; that result is kept 30 seconds). Otherwise `ready` (200).
- **Pass runs.** `atrium sync`, `atrium notion sync`, `atrium proposals scan-all` and `atrium backup` each record one `pass_runs` row (job `sync`, `notion-sync`, `scan` or `backup`, start and finish time, `ok` or `failed` with the error) whichever process runs them. Rows older than `pass_run_retention_days` (default 90) are pruned when a run is recorded. A job is stale when its newest run failed, or when its last success is older than its limit: 1 hour for `sync` and `notion-sync`, 35 days for `scan`, 8 days for `backup`. A job that has never run is not stale.
- **Stale notices.** While notifications are on, `atrium serve` checks for stale jobs at start and every 5 minutes and sends one notification on the system channel per stale job; it sends again only after the job recovers and goes stale again.
- **Notification channels.** Notifications go to one of three channels: `assistant` (the `notify` tool), `media` (new releases) and `system` (stale passes, skipped scheduled runs, 80% and 100% of the monthly budget once per month, mail pause and resume, and channel health). Each channel has its own ntfy topic. When the channels are first created they take the Phase A topics (`ntfy_topic` for assistant and system, `ntfy_media_topic` or else `ntfy_topic` for media); a channel reset gives it a new random 128-bit topic. The Notifications settings page shows each topic as an `ntfy://` subscribe link and sends a test message.
- **ntfy account.** On an encrypted database the Notifications page takes an ntfy username and password once and mints one never-expiring token per channel through `POST /v1/account/token`; only the tokens are stored, as secrets `ntfy_token_<channel>`. Without a channel token, `NTFY_TOKEN` is used. Resetting a channel revokes its token. An ntfy.sh server shows a warning that topic names must be kept secret.
- **Privacy.** atrium checks each topic by reading it anonymously (at serve start for unchecked channels and with Check privacy). A topic that refuses the anonymous read is `private` and gets the full title and text; otherwise only the title `atrium` and a pointer to the app are sent. A per-channel content setting (`auto`, `full`, `title`) overrides this.
- **Delivery and health.** Every notification is recorded in the inbox before delivery; delivery is best effort with no retry queue. A failed delivery can be resent from the inbox; a delivered one is not sent again. After three consecutive failures a channel is failing: administrators see a banner on every page and one high-priority message goes to the system channel. A successful delivery clears it.
- **Profiling.** `/debug/pprof/` is served on the ops listener only with `ops_pprof` (`ATRIUM_CORE_OPS_PPROF=true`).
