# Encrypted SQLite for a single Go binary (ticket #23)

Researched 2026-10-17. Inference is marked `[inference]`; nothing here was built or benchmarked (research protocol forbids builds), so every performance statement is a vendor/author claim or a reading of source code, not a measurement.

## 1. Answer in brief

1. Two real families exist. **Pure Go**: `ncruces/go-sqlite3` (SQLite compiled to Wasm, translated to Go) plus its encrypting VFS wrappers `vfs/adiantum` (Adiantum) and `vfs/xts` (AES-XTS). **cgo**: SQLCipher (AES-256-CBC + HMAC-SHA512 per page) or SQLite3 Multiple Ciphers (ChaCha20-Poly1305 by default, and a SQLCipher-compatible mode), compiled into the binary.
2. The ncruces VFS ciphers are length-preserving disk-encryption modes: deterministic, no per-page MAC, no tamper/forgery protection, no `PRAGMA rekey`. The maintainer says the encrypted file should be re-created with the Backup API to change key or decrypt. SQLCipher has per-page random IV and HMAC, `PRAGMA rekey`, `sqlcipher_export()`, and a packaged CLI.
3. **atrium has a hard dependency that decides this: `sqlite-vec` (`vec0` virtual tables, partition keys) for mail and Notion KNN search.** It is a loadable C extension. It works with cgo drivers (official Go cgo bindings, compiled in). The official ncruces binding is pinned to ncruces v0.17.1 (2024) and replaces ncruces's embedded Wasm, so it cannot be assumed to work with current ncruces (`wasm2go`-based, v0.35.6). The pure-Go route therefore requires replacing `vec0` (ncruces `ext/vec1` or KNN in Go) before cutover. Phase A ("same SQLite schema and data") must read the existing `vec0` shadow tables, so Phase A needs cgo + sqlite-vec anyway.
4. FTS5, WAL, online backup, and multi-process WAL all work with either family. FTS5 and vec0 shadow tables are ordinary tables inside the file, so they are encrypted with everything else.
5. **Recommendation:** Phase A on a cgo driver (`mattn/go-sqlite3`, FTS5 tag, sqlite-vec cgo bindings). Phase B: SQLCipher format, official SQLCipher source (nixpkgs ships 4.19.0, BSD-3-Clause), raw 256-bit key from a `*_file` secret (skips the PBKDF2 cost), one pooled set of connections, migration by an offline `atrium db encrypt` that copies into a fresh encrypted file and verifies counts. Keep the DB opener behind one function so the driver can be swapped. Choose pure Go only if the team decides to drop `vec0` and accepts "no tamper detection, no rekey, no standard CLI".
6. Host backups (btrfs snapshot then restic) keep working unchanged: both encrypt/dedup at file level, the snapshot is crash-consistent, restic already encrypts client-side. Encryption at rest does not retroactively protect existing plaintext history in restic snapshots or btrfs snapshots.

## 3. Options

### A. `ncruces/go-sqlite3` + `vfs/adiantum` or `vfs/xts` (pure Go, no cgo)

- Current: module v0.35.6 (2026-09-23) ([proxy](https://proxy.golang.org/github.com/ncruces/go-sqlite3/@latest), [release](https://github.com/ncruces/go-sqlite3/releases)); go 1.26; SQLite is Wasm translated to Go with [wasm2go](https://github.com/ncruces/go-sqlite3#readme), driver `database/sql` compatible.
- Encryption is a VFS wrapper: Adiantum uses XChaCha12 + AES + NH + Poly1305, 4 KiB blocks, Argon2id for `textkey`; XTS uses AES-XTS, 512-byte sectors, PBKDF2-HMAC-SHA512 for `textkey`, "only NIST and FIPS 140-3 approved primitives" ([adiantum README](https://github.com/ncruces/go-sqlite3/blob/main/vfs/adiantum/README.md), [xts README](https://github.com/ncruces/go-sqlite3/blob/main/vfs/xts/README.md)). `hexkey` (32 raw bytes) avoids the KDF ([adiantum package doc](https://raw.githubusercontent.com/ncruces/go-sqlite3/v0.35.6/vfs/adiantum/api.go)).
- What is encrypted: everything except super-journals; temp files get random keys; READMEs advise `PRAGMA temp_store = memory`. The VFS wraps main DB, `-wal` and `-journal` ([hbsh.go](https://raw.githubusercontent.com/ncruces/go-sqlite3/v0.35.6/vfs/adiantum/hbsh.go): "Encrypt everything except super journals and memory files"). The `-shm` is a wal-index of hash tables, not page content ([walformat](https://sqlite.org/walformat.html)).
- Security properties, in the project's own words: fully deterministic; an adversary with several snapshots learns which blocks changed, unchanged or reverted; "does not claim protect databases against tampering or forgery"; encrypted backups should be signed; a `VACUUM` rebuilds the file and defeats differential analysis ([adiantum README](https://github.com/ncruces/go-sqlite3/blob/main/vfs/adiantum/README.md)).
- Key change/decrypt: no `rekey`. Maintainer: "Rekeying is not implemented because it's not clear how to do so atomically… use Backup … to a new file with no encryption, or a different key" ([discussion 359](https://github.com/ncruces/go-sqlite3/discussions/359)). `Conn.Backup(srcDB, dstURI)` opens the destination URI (so `?vfs=adiantum&hexkey=...` works) and blocks until done ([backup.go](https://raw.githubusercontent.com/ncruces/go-sqlite3/v0.35.6/backup.go)).
- WAL: shared-memory WAL works on Linux/macOS/Windows (mmap), across processes; Linux needs OFD locks (kernel 3.15+). Other configs degrade to in-process or EXCLUSIVE-only ([vfs README](https://github.com/ncruces/go-sqlite3/blob/main/vfs/README.md), [support matrix](https://github.com/ncruces/go-sqlite3/wiki/Support-matrix)). The VFS is a from-scratch reimplementation: "not as battle tested as the original" (same README). Release v0.35.3 fixed a WAL data-corruption bug on Windows ([releases](https://github.com/ncruces/go-sqlite3/releases)).
- Write path: each write is rounded to 4 KiB blocks with read-decrypt-modify-encrypt-write for partial blocks ([hbsh.go](https://raw.githubusercontent.com/ncruces/go-sqlite3/v0.35.6/vfs/adiantum/hbsh.go)). A WAL frame is page size + 24-byte header ([walformat](https://sqlite.org/walformat.html)), so frames straddle blocks. `[inference]` this means roughly two block read-modify-writes per frame; needs a benchmark with atrium's write pattern.
- FTS5: provided as Go-translated extension `ext/fts5` registered per connection (`fts5.Register(conn)`, also allows custom Go tokenizers since v0.35.4) ([fts5.go](https://raw.githubusercontent.com/ncruces/go-sqlite3/v0.35.6/ext/fts5/fts5.go), [ext README](https://raw.githubusercontent.com/ncruces/go-sqlite3/main/ext/README.md)). Registered through `driver.Open(dsn, fn ...func(*sqlite3.Conn) error)` ([driver.go](https://raw.githubusercontent.com/ncruces/go-sqlite3/v0.35.6/driver/driver.go)).
- sqlite-vec: not loadable. The official binding `sqlite-vec-go-bindings/ncruces` embeds its own Wasm build and its `go.mod` requires ncruces v0.17.1 plus wazero ([README](https://raw.githubusercontent.com/asg017/sqlite-vec-go-bindings/main/README.md), [go.mod](https://raw.githubusercontent.com/asg017/sqlite-vec-go-bindings/main/go.mod)); latest tag v0.1.6, 2024-11-20 ([proxy](https://proxy.golang.org/github.com/asg017/sqlite-vec-go-bindings/@latest)). Current ncruces ships a Go translation instead of wazero (v0.35.6 `go.mod` requires `go-sqlite3-wasm/v6`). `[inference]` the binding cannot be combined with current ncruces. Alternatives inside ncruces: `ext/vec1`, SQLite's own vector extension, "version 0.8", IVFADC ANN or exact flat/no-index modes, cosine and L2, metadata columns and filtered queries, roadmap lists partition keys as not yet done ([vec1 doc](https://sqlite.org/vec1/doc/trunk/doc/vec1.md), [user manual](https://sqlite.org/vec1doc.html)). Different SQL surface and storage format than `vec0`.
- Performance (unencrypted driver): competitive with mattn/modernc in the Mar-2026 [go-sqlite-bench](https://github.com/cvilsmeier/go-sqlite-bench): e.g. 1M-row insert 2719 ms vs mattn 1480 ms, concurrent read N=8 2355 vs 2395 ms, "Real" insert 1469 vs 1586 ms. Author's caveat: "Do not trust benchmarks, write your own". README warns memory use is higher because every connection runs in its own Wasm instance ([README](https://github.com/ncruces/go-sqlite3#readme)). No published benchmark of the encrypting VFS found. Adiantum was designed for CPUs without AES instructions (10.6 cycles/byte on Cortex-A7, over 5x faster than AES-256-XTS there) ([paper](https://eprint.iacr.org/2018/720)); `[inference]` on x86-64/arm64 with AES instructions XTS may be competitive, so benchmark both on the target host.
- Build: `CGO_ENABLED=0`, trivially static, easy cross-compile, matches "static release binaries" and CI matrix.
- Operations: the file cannot be opened with `sqlite3` or `sqlcipher`; atrium would need its own `atrium db shell/dump` for debugging and recovery.
- Other pure-Go encryption: `alvarolm/go-sqlite3-xchacha` (non-deterministic XChaCha20-Poly1305 VFS, 20 bytes/page overhead) and `go-sqlite3-aesgcm`, both 2026-04-24 pseudo-versions by one author, self-described AI-assisted, maintainer response "Nothing immediately jumps out" ([discussion 382](https://github.com/ncruces/go-sqlite3/discussions/382), [proxy](https://proxy.golang.org/github.com/alvarolm/go-sqlite3-xchacha/@latest)). Not recommended without a review.

### B. SQLCipher via cgo, statically linked

- Upstream: SQLCipher Community Edition, BSD-3-Clause ([LICENSE](https://raw.githubusercontent.com/sqlcipher/sqlcipher/master/LICENSE.md)); 4.19.0 is current and baselines SQLite 3.53.4 as of 4.18.0 ([CHANGELOG](https://raw.githubusercontent.com/sqlcipher/sqlcipher/master/CHANGELOG.md)); nixpkgs unstable has `sqlcipher` 4.19.0 BSD-3-Clause (nixos MCP query).
- Design: AES-256-CBC per page, random IV per page regenerated on each write, HMAC-SHA512 over ciphertext+IV per page, PBKDF2-HMAC-SHA512 with 256,000 iterations, random 16-byte salt in the file header; "the entire database file appears to contain random data"; WAL pages, rollback journals and statement journals are encrypted with the database key; other transient files are not, so disable file temp store (`SQLITE_TEMP_STORE=2`) ([design](https://www.zetetic.net/sqlcipher/design/)). Per-page HMAC detects modification of a page but not rollback of a page to an older valid version (same point made by the ncruces README about page MACs).
- Crypto provider: OpenSSL libcrypto in the Community build; official docs say Commercial/Enterprise "optimized" modules can be up to 4x faster than Community for some workloads; typical overhead "as little as 5-15%" ([performance](https://www.zetetic.net/sqlcipher/performance/)). The performance page says never repeatedly open/close connections because key derivation is expensive by design.
- Raw key: `PRAGMA key = "x'<64 hex>'"` skips key derivation; a 96-hex form supplies the salt too ([API](https://www.zetetic.net/sqlcipher/sqlcipher-api/)).
- Key rotation: `PRAGMA rekey` re-encrypts every page in place; it cannot encrypt a plaintext DB ([API](https://www.zetetic.net/sqlcipher/sqlcipher-api/)). 4.19.0 "Fix error reporting for failed rekey operations" ([CHANGELOG](https://raw.githubusercontent.com/sqlcipher/sqlcipher/master/CHANGELOG.md)). Crash-atomicity of rekey is not documented in what I read `[inference]` treat it as non-atomic, take a verified copy first.
- Plaintext to encrypted: `ATTACH DATABASE 'encrypted.db' AS e KEY '…'; SELECT sqlcipher_export('e');` copies "schema, triggers, virtual tables, and all data" ([API](https://www.zetetic.net/sqlcipher/sqlcipher-api/)). `[inference]` virtual tables with real shadow tables (FTS5, vec0) are exactly the case where this must be tested before trusting it.
- Online backup: SQLite backup API works across the SQLCipher codec; page size and reserve (SQLCipher reserves bytes per page for IV+HMAC) differ from plaintext, so plaintext to encrypted via the backup API is not the supported path `[inference]`; use `sqlcipher_export` or an app-level copy. Encrypted to encrypted with the same settings is the normal backup route.
- FTS5: build flag; the SQLCipher repo documents running its tests with `--enable-fts5` ([README](https://raw.githubusercontent.com/sqlcipher/sqlcipher/master/README.md)). WAL: supported, as above.
- CLI: `sqlcipher` is packaged in nixpkgs, so operators can open the file by hand (`PRAGMA key`).
- Go drivers:
  - `mutecomm/go-sqlcipher/v4`: latest tag v4.4.2, 2020-12-07, upstream says it has had no commits since December 2020 ([proxy](https://proxy.golang.org/github.com/mutecomm/go-sqlcipher/v4/@latest), [MAINTENANCE](https://raw.githubusercontent.com/mutecomm/go-sqlcipher/master/MAINTENANCE)). Do not use.
  - `WissCore/go-sqlcipher/v4`: 2026 fork by one maintainer; vendors SQLCipher 4.15.0 / SQLite 3.53.0, signed releases, SBOM, CI scanners; needs a C compiler and OpenSSL headers ([README](https://raw.githubusercontent.com/WissCore/go-sqlcipher/main/README.md)). Other forks exist (`benoitpetit`, `SE-I-T-Digital` at 4.16.0) [search result](https://pkg.go.dev/github.com/SE-I-T-Digital/go-sqlcipher), none with proven long-term maintenance. Single-maintainer supply-chain risk.
  - `mattn/go-sqlite3` v1.14.52 (2026-09-05) has a `libsqlite3` build tag that links the system library instead of its amalgamation ([README](https://raw.githubusercontent.com/mattn/go-sqlite3/master/README.md), [sqlite3_libsqlite3.go](https://raw.githubusercontent.com/mattn/go-sqlite3/master/sqlite3_libsqlite3.go)). `[inference]` pointing that tag at `libsqlcipher` (which exports the `sqlite3_*` symbols) lets atrium use the official nixpkgs SQLCipher with the same driver as Phase A; its cgo `LDFLAGS` hard-code `-lsqlite3` so a Nix wrapper/overridden `CGO_LDFLAGS` or a thin `libsqlite3` alias is needed. Needs a spike.
- sqlite-vec: official cgo binding compiles `sqlite-vec.c` with `-DSQLITE_CORE` and registers via `sqlite3_auto_extension`; "While this works with CGO SQLite/Go libraries like mattn/go-sqlite3" ([lib.go](https://raw.githubusercontent.com/asg017/sqlite-vec-go-bindings/main/cgo/lib.go), [README](https://raw.githubusercontent.com/asg017/sqlite-vec-go-bindings/main/README.md)). `[inference]` it links against whichever `sqlite3_*` symbols the binary provides, so SQLCipher works the same way. sqlite-vec itself: v0.1.9 stable (2026-03-31), 0.1.10 alphas to 2026-05-18, "pre-v1, expect breaking changes"; vec0 is exhaustive KNN in the released line, DiskANN/IVF sources exist on main ([releases](https://github.com/asg017/sqlite-vec/releases.atom), [README](https://github.com/asg017/sqlite-vec)). nixpkgs has `sqlite-vec` 0.1.9 (MIT).
- Static linking: documented recipe is musl cross-compiler with `-linkmode external -extldflags -static`; with SQLCipher, also link `libcrypto.a` ([mattn README](https://raw.githubusercontent.com/mattn/go-sqlite3/master/README.md), WissCore docs/building.md referenced in its README). `[inference]` under Nix, `pkgsStatic` for `sqlcipher`+`openssl`; for non-Nix release binaries a musl build container in CI. Costs: cgo makes cross-compilation from the CI matrix harder, build time higher, and the binary now contains OpenSSL (CVE cadence).

### C. SQLite3 Multiple Ciphers (SQLite3MC) via cgo

- Upstream v2.6.1 (2026-10-12). Ciphers: ChaCha20-Poly1305 (recommended default, per-database and per-page nonce), SQLCipher-compatible AES-256-CBC (SHA1/256/512 HMAC), Ascon-128, AEGIS, wxSQLite3 AES, RC4; encrypts main file and journals; limitations equal to SQLite SEE: TEMP tables and in-memory DBs not encrypted, bytes 16-23 of the header usually plaintext; `sqlite3_rekey` can also decrypt; rekey may VACUUM and need up to 3x disk space ([overview](https://utelle.github.io/SQLite3MultipleCiphers/), [C API](https://utelle.github.io/SQLite3MultipleCiphers/docs/configuration/config_capi/)). It can read SQLCipher-format files, so a later switch between SQLCipher and SQLite3MC is possible `[inference]` if the SQLCipher cipher mode and parameters match.
- Go binding: only `alvarolm/sqlite3mc` (v0.4.2, 2026-10-09; README: "not reviewed, use at your own risk, built mostly with Claude Code"; mattn fork + SQLite3MC 2.5.0 amalgamation, SQLite 3.53.4) ([README](https://raw.githubusercontent.com/alvarolm/sqlite3mc/main/README.md), [proxy](https://proxy.golang.org/github.com/alvarolm/sqlite3mc/@latest)). No ncruces/SQLite3MC integration exists: maintainer ruled out SQLite3MC in favour of VFS wrappers ([issue 55 via search](https://github.com/ncruces/go-sqlite3/issues/55)). Vendoring SQLite3MC into our own mattn-style fork is possible but is ownership of a C amalgamation fork (inference).

### D. Alternatives considered

- **SQLite Encryption Extension (SEE)**: official, paid, AES (hwaci.com). Not evaluated further: license cost and closed distribution do not fit a public repo `[inference]`.
- **Encrypt below SQLite** (LUKS/dm-crypt, fscrypt, encrypted btrfs/ZFS): no code in atrium, works with any SQLite and `vec0`, protects against stolen disk only; does not protect snapshots or backups copied off-host. cornn-flaek has no disk encryption configured under `modules/` today. Worth offering as a documented complement, not as the product feature (the plan chose whole-file DB encryption so that backups and snapshots are ciphertext).
- **Column/value-level encryption** (secrets only): SQLCipher's VLE is Commercial/Enterprise-only ([API](https://www.zetetic.net/sqlcipher/sqlcipher-api/)); an app-level seal for OAuth tokens is a separate decision (see candidate tickets).
- **libSQL/Turso encryption, `modernc.org/sqlite`**: not researched (no evidence collected here); modernc v1.60.1 exists ([proxy](https://proxy.golang.org/modernc.org/sqlite/@latest)). Mark as not evaluated.

## 5. Migration from the plaintext `atrium.db`

Constraints: Phase A keeps plaintext (schema and data must round-trip into the Go port unchanged). Encryption is Phase B. Doing the conversion offline with the service stopped avoids needing WAL coordination (runbook confirms several processes; `db.exclusive` flock exists for jobs).

Recommended `atrium db encrypt` (and `atrium db rekey`, same code path):
1. Refuse if units are running (or take the existing flock plus a pause file) and `PRAGMA wal_checkpoint(TRUNCATE)` the source.
2. Open the plaintext source read-only; create `atrium.db.new` as encrypted with the new key; `PRAGMA temp_store=MEMORY`.
3. Copy using the normal schema initialiser on the new DB, then `INSERT … SELECT` per ordinary table, FTS5 tables (contentful, so copy rows including `rowid`), and `vec0` tables (`SELECT rowid, <partition>, embedding FROM old` into the new `vec0`). This avoids relying on `sqlcipher_export` for virtual tables. If testing shows `sqlcipher_export` handles FTS5+vec0 correctly, use it and still verify.
4. Verify: `PRAGMA integrity_check` and `foreign_key_check`, row counts per table, `SELECT count(*)` on each FTS5 and vec0 table, a sample KNN query returns identical top-k, FTS5 `integrity-check` command, `PRAGMA cipher_integrity_check` (SQLCipher).
5. Atomically `rename()` new over old, keep `atrium.db.plain.bak` (0600) until the operator confirms, then remove.
6. Record `user_version`/a `schema_meta` row so the Go binary can refuse to open a mismatched file.

For ncruces the equivalent is `Conn.Backup` into `file:atrium.db.new?vfs=adiantum&hexkey=…` (page-for-page copy, preserving vec0/FTS shadow tables as-is; but see section 3A on vec0 availability).

Residue caveats (apply to every option): the plaintext file leaves copies in btrfs snapshots (the artemis backup takes a read-only snapshot of `/persist` daily), in restic history (retention keep-daily 7, weekly 4, monthly 6 per `cornn-flaek/modules/backups/default.nix`), and freed blocks on CoW storage. Encrypting now does not erase old plaintext; restic repos are client-side encrypted (AES-256-CTR + Poly1305-AES, [restic design](https://restic.readthedocs.io/en/stable/100_references.html)) so exposure is limited to someone with the restic password or the live host. `shred` is not effective on btrfs (inference). Decide whether to `restic forget --prune` the pre-migration snapshots after the retention window.

## 6. Key management and rotation

- Source: a `database.key_file` (Phase B config, `*_file` convention from the plan) holding 32 random bytes, hex. `atrium init` generates it with mode 0600 if absent. For SQLCipher use `PRAGMA key="x'…'"` (no PBKDF2, [API](https://www.zetetic.net/sqlcipher/sqlcipher-api/)); for ncruces use `hexkey` (no Argon2id). Do not use a human passphrase: KDF cost is paid on every new connection (SQLCipher 256,000 PBKDF2 iterations, ncruces Argon2id 64 MiB × 3), the performance page warns about exactly this.
- Key delivery under systemd: `LoadCredential=`/sops secret path, same as other secrets. The key and the data live on the same host, so at-rest encryption protects against stolen disks, copied snapshots/backups and leaked files, not against root on the running host or a process compromise `[inference]`. State this in docs so the feature is not oversold.
- Rotation: offline `atrium db rekey --new-key-file` that writes a fresh file under the new key via the same copy+verify path as section 5, then renames. `PRAGMA rekey` is acceptable only after a verified backup (atomicity undocumented, ncruces refuses to provide it for that reason). Rotation rewrites every page, so the next restic run uploads the whole DB (SQLite untouched pages are otherwise byte-stable between runs).
- Wrong/missing key must be a clear startup error, not a silent empty DB: SQLCipher does not fail on `PRAGMA key`, only on the first read ("test with `SELECT count(*) FROM sqlite_master`"). SQLite3MC documents that a key set on an empty (zero-byte) file only takes effect after a first write, so a typo'd path or truncated file looks like a fresh DB ([C API](https://utelle.github.io/SQLite3MultipleCiphers/docs/configuration/config_capi/)). Add a startup guard that opens, reads `sqlite_master`, and compares a stored app marker.

## 7. Interaction with host backups (restic etc.)

- Current flow: `btrfs subvolume snapshot -r /persist` then restic from the snapshot (artemis); other nodes use per-service jobs with optional `pauseUnits`/`prepareCommand`. The atrium unit has no prepare hook today. A crash-consistent snapshot of a WAL-mode DB is recoverable on open (SQLite replays the WAL), provided the `-wal` file is captured in the same snapshot, which a subvolume snapshot guarantees; a file-by-file copy of a hot DB is the danger case ([howtocorrupt](https://sqlite.org/howtocorrupt.html), "Backup or restore while a transaction is active"). Encryption does not change this, but both `-wal` must be encrypted with the same key and must travel with the DB file.
- Restic splits files into 512 KiB–8 MiB content-defined chunks, avg ~1 MiB ([restic design](https://restic.readthedocs.io/en/stable/100_references.html)). SQLCipher/SQLite3MC/Adiantum leave unwritten pages byte-identical, so incremental dedup still works for untouched regions; `VACUUM`, rekey, migration or `ncruces` Backup re-creation rewrites everything. `[inference]` encrypted pages are incompressible, so restic compression (repo v2) gains disappear.
- Restore: the key must be restorable independently of the data (the existing secrets are sops-managed in cornn-flaek, and the artemis backup set includes `etc/ssh`, which `[inference]` holds the host key sops decrypts with; verify before relying on it). Losing the key loses the DB: add a runbook section and a `key_check` command.
- Application-level backup: provide `atrium db backup <dest>` that uses the SQLite backup API (or `VACUUM INTO` with the same key) into a consistent, encrypted file and can be wired into restic `prepareCommand`. The existing NixOS host backups do not need it for artemis (snapshot), but VPS deployments without snapshots do.
- Litestream-style WAL shipping works on the WAL file, so an encrypted WAL is not compatible with plaintext replication `[inference]`; ncruces has `ncruces/litestream` (read replicas) which is a different thing ([vfs README](https://github.com/ncruces/go-sqlite3/blob/main/vfs/README.md)). Treat continuous replication as out of scope.

## 8. Recommendation (tied to plan decisions)

1. **Phase A (port as-is):** cgo SQLite driver (`mattn/go-sqlite3` with `sqlite_fts5`) + official sqlite-vec cgo bindings, plaintext file, same schema. Reason: the port must read the existing `vec0` shadow tables unchanged. Wrap opening in one internal package (`internal/store.Open(ctx, cfg)`), pool connections (the Python code reopens per call), and run the existing pragmas. Make the schema-init code idempotent exactly as today.
2. **Phase B (encryption):** SQLCipher format, upstream source from nixpkgs (4.19.0) with static linking via `pkgsStatic`/musl; raw key from `database.key_file`; per-connection `PRAGMA key` before any other statement (a connect hook); `PRAGMA temp_store=MEMORY` and build with `SQLITE_TEMP_STORE=2`; `atrium db encrypt|rekey|backup|decrypt|shell` CLI. Keep WissCore/go-sqlcipher as fallback if the `libsqlite3`-tag spike fails, and SQLite3MC as a later option if AES performance proves poor on the target VPS.
3. **Pure Go is the alternative to choose only if** the owner prefers `CGO_ENABLED=0` over tamper detection/rekey/tooling **and** is willing to replace `vec0` (ncruces `vec1`, or KNN in Go over BLOBs; embeddings are 768 floats, search is `k`-nearest with an `account`/`visibility` filter, `src/atrium/search.py:147`). That is its own migration of 2 tables and 3 query sites. Then use Adiantum with `hexkey` and sign backups (restic already authenticates its repository).
4. Do the Phase A driver choice and the Phase B cipher choice as two independent decisions; the abstraction boundary above keeps them swappable.

Why SQLCipher over SQLite3MC: Phase A already needs a cgo SQLite plus sqlite-vec; SQLCipher has the largest ecosystem (CLI, docs, audits cited by the wrappers' READMEs), a packaged upstream in nixpkgs, BSD license, and a documented export/rekey/migrate story; the only maintained Go wrappers for SQLite3MC are unreviewed. Why not Adiantum/XTS: no tamper detection, deterministic, no rekey, no CLI, loses `vec0`.

## 9. Risks and unknowns

1. `[spike]` Link `mattn/go-sqlite3` (`libsqlite3` tag) against nixpkgs `libsqlcipher` and confirm sqlite-vec registers via `sqlite3_auto_extension`, FTS5 works, and WAL round-trips with the key set per connection. Also spike the WissCore fork as fallback.
2. `[spike]` `sqlcipher_export` against FTS5 + vec0 with real data; compare with the app-level copy.
3. sqlite-vec is pre-v1 (breaking changes, last stable 0.1.9, only alphas since), and brute-force; mail+Notion embedding counts in production are unknown here. Ticket suggestion below on vector storage.
4. `mattn/go-sqlite3` cgo build matrix, and OpenSSL in the binary (CVE cadence, static musl builds).
5. SQLCipher Community crypto is slower than Commercial (vendor claim "up to 4x"); on a small VPS CPU the embedding re-index and FTS5 rebuilds could be noticeably slower than plaintext. No measurement; benchmark with a copy of the real DB size.
6. Per-connection KDF if keyed with a passphrase; mitigated by raw key and pooling.
7. Key and data co-located, so threat model is offline theft; document it.
8. Old plaintext in restic/btrfs history.
9. Page-level HMAC does not stop rollback of the whole file to an older valid state; neither does anything else here.
10. Tooling lock-in: encrypted DB cannot be inspected with the plain `sqlite3` CLI; incident response needs the key and `sqlcipher`/`atrium db shell`.
