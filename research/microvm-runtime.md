# MicroVM runtime for the sandbox manager (ticket #24)

Researched 2026-10-17. Question: which VMM should the sandbox manager drive, and how do we do snapshot suspend/resume, workspace disks, the vsock control channel, per-VM networking with egress through a proxy, resource limits, NixOS packaging and Nix-built rootfs images per toolset combination? GPU is not needed.

Constraints taken from the plan: Linux with KVM only; one sandbox per thread, suspended when idle, deleted with the thread; manager is a separate Go binary reachable over HTTPS + mTLS (#54, #41); egress through a domain-allowlist proxy (#25); Nix-built rootfs on the manager host, no Nix inside the guest; environments pick composable toolsets (python, go, bun, rust), a resource profile, env vars, secrets, setup scripts.

## 1. Answer in brief

- **VMM: Firecracker (v1.17.0, 2026-09-10)**, behind a small Go `Hypervisor` interface so Cloud Hypervisor (v54.0, 2026-10-14) can be added if we ever need virtio-fs or CPU/memory hotplug.
- **Suspend = full memory snapshot + state file, disks stay on the host.** Two tiers: *warm* (snapshot on disk, processes preserved, resume ~tens of ms) and *cold* (disk only, fresh boot, ~hundreds of ms). Warm decays to cold after a TTL, or when a disk budget is hit.
- **Workspace = a per-thread raw ext4 image on a reflink-capable filesystem (XFS or btrfs)**, attached as virtio-blk. No virtio-fs (Firecracker has none, and Cloud Hypervisor's virtio-fs forces `shared=on`, which is incompatible with its fast restore modes).
- **Control channel = virtio-vsock** (host-side Unix socket per VM) between the manager and a small static Go guest agent that is PID 1. No network is needed for exec/file/session traffic.
- **Network = no NIC by default.** Egress goes guest → vsock → manager-side proxy (#25). This removes TAP/bridge/nftables/IP management and makes suspend/resume trivially safe. A TAP + nftables-pinned-to-proxy mode is the fallback if a tool cannot use a proxy.
- **Rootfs = read-only erofs image built by Nix per distinct toolset set** (base + toolsets), cached by Nix store path; a per-thread writable layer sits on top via overlayfs. The guest kernel is built in Nix from Firecracker's reference config plus EROFS.
- **Go SDK: do not depend on `firecracker-go-sdk`**; generate/hand-write a thin client from the pinned `firecracker.yaml`. The API is ~25 paths over a Unix socket.
- **NixOS: package `firecracker` from nixpkgs (unstable has 1.16.1) or overlay 1.17.0; write our own NixOS module for the manager. Use microvm.nix only as a reference for kernel/erofs/store-disk building**, not as the runtime.

### Notes per option

- **Firecracker.** Purpose-built for minimal guests; stable HTTP API; vsock is a UDS multiplexer so the manager needs no kernel `vhost-vsock` plumbing ([vsock.md](https://github.com/firecracker-microvm/firecracker/blob/v1.17.0/docs/vsock.md)). Release policy: patch releases for the last two MINOR versions for up to 1 year ([RELEASE_POLICY](https://github.com/firecracker-microvm/firecracker/blob/v1.17.0/docs/RELEASE_POLICY.md)); guest/host kernels 5.10, 6.1, 6.18 are the supported set ([kernel-policy](https://github.com/firecracker-microvm/firecracker/blob/v1.17.0/docs/kernel-policy.md)). Tested only on AWS `.metal` instances ([README](https://github.com/firecracker-microvm/firecracker/blob/v1.17.0/README.md#tested-platforms)); nested virtualisation is not in the test matrix [inference: works where `/dev/kvm` works but is unsupported by upstream]. Production host guidance: disable swap, cgroup v2, jailer, seccomp ([prod-host-setup](https://github.com/firecracker-microvm/firecracker/blob/v1.17.0/docs/prod-host-setup.md)).
- **Cloud Hypervisor.** Equal-quality Rust VMM with a richer device model and faster release cadence (v50.2 Feb → v54.0 Oct 2026). Documented API/CLI stability: no breaking changes without 2 major releases' notice ([README §Status](https://github.com/cloud-hypervisor/cloud-hypervisor/blob/v54.0/README.md)). Its **`copyonwrite` restore** maps the snapshot file private-COW so many VMs share page cache, and `ondemand` uses userfaultfd; **both fall back to eager copy or are refused when `shared=on`, hotplug zones, virtio-mem or any vhost-user device (virtiofsd) is present** ([snapshot_restore.md](https://github.com/cloud-hypervisor/cloud-hypervisor/blob/v54.0/docs/snapshot_restore.md)). So "virtio-fs workspace" and "fast restore" are mutually exclusive on CH. Also has an "offload daemon" mode that streams the snapshot to a user process (compress/encrypt/object store) ([same doc](https://github.com/cloud-hypervisor/cloud-hypervisor/blob/v54.0/docs/snapshot_restore.md#offload-snapshot-and-restore)) — useful if we later want encrypted or compressed snapshots.
- **QEMU.** Most featureful and most auditable; `microvm` machine type is minimal but lacks hotplug, and the full machine types have a far larger attack surface. Snapshot via migrate-to-file with `mapped-ram` (non-live) works, but QMP orchestration is heavier and Go QMP libraries are thin (`digitalocean/go-qemu` last pushed 2025-05-05). Not recommended for this use.
- **crosvm.** Chrome OS VMM; no stable releases; snapshotting is documented as experimental. Wrong risk profile for a project that wants suspend/resume to be dependable.
- **libkrun.** Great for "run a container-ish process in a VM" (virtio-fs rootfs, TSI networking where the VMM proxies sockets) ([README](https://github.com/containers/libkrun)). No snapshot, so it cannot satisfy "suspend when idle" without losing process state; TSI makes the VMM process the network-policy point which is workable but ties us to a C library via cgo.
- **Kata Containers.** An OCI/containerd runtime that wraps one of CH/FC/QEMU/Dragonball. Adds a containerd+CRI dependency stack we would not otherwise have, and the runtime **does not support checkpoint/restore** ([Limitations](https://github.com/kata-containers/kata-containers/blob/main/docs/Limitations.md#checkpoint-and-restore)). Rejected.
- **gVisor.** Not a VM; the Go-written Sentry reimplements the kernel, runs on KVM *or* systrap/ptrace, so it works where `/dev/kvm` does not (VPS without nested virt). Checkpoint/restore exists but is exposed only through raw `runsc` commands. Weaker boundary and syscall-compat risk for arbitrary coding toolchains [inference]. The plan says Linux + KVM only, so keep gVisor as *not adopted*; revisit only if a no-KVM deployment becomes a requirement.

## 3. Go SDKs

- **`firecracker-go-sdk`** ([repo](https://github.com/firecracker-microvm/firecracker-go-sdk)): last tag v1.0.0 (2022-09-07); commits since are dependency bumps and a jailer race fix (last 2025-12-24). It has `CreateSnapshot`, `PauseVM`, `ResumeVM`, and a `SnapshotConfig` that sets `MemFilePath` and `EnableDiffSnapshots`, which the 1.17 swagger marks **deprecated** (`mem_file_path`, `enable_diff_snapshots`) in favour of `mem_backend`/`track_dirty_pages`. It also predates `huge_pages`, `sync_snapshot_files`, `network_overrides`/`vsock_override` use, balloon hinting, memory hotplug. It pulls CNI/netlink dependencies we do not need. Verdict: do not depend on it.
- **Generate our own.** Firecracker's swagger is 2.0 (go-swagger territory or hand-written); CH's is OpenAPI 3.0.1 (oapi-codegen works). Pin the spec file per VMM version in the manager repo and add a CI check that the spec matches the packaged binary version.
- **Prior art in Go that is worth reading** (not dependencies): [`kernel/hypeman`](https://github.com/kernel/hypeman) (MIT; Go; CH + Firecracker + QEMU behind a `hypervisor` interface with standby/restore, UFFD pager, egress proxy; very active), [`e2b-dev/infra`](https://github.com/e2b-dev/infra) (Apache-2.0; Firecracker orchestrator, UFFD memory serving, NBD-backed rootfs, templates), [`arugula-salad/wisp`](https://github.com/arugula-salad/wisp) (single-host Go + Firecracker, vsock-only guest agent as PID 1, warm/cold lifecycle; 1 star, treat its numbers as anecdotal).

## 4. Snapshot suspend / resume

Facts from the Firecracker docs ([snapshot-support.md](https://github.com/firecracker-microvm/firecracker/blob/v1.17.0/docs/snapshotting/snapshot-support.md)):

- Snapshot = microVM state file + guest memory file (`PUT /snapshot/create`, VM must be paused). A **full** snapshot writes all guest memory; **diff** snapshots are *developer preview* and must be merged onto a base. Files are `fsync`'d unless `sync_snapshot_files=false` (new in 1.17).
- Resume (`PUT /snapshot/load`) accepts a `File` backend (kernel page cache, lazy, COW into anonymous memory) or `Uffd` (our process serves page faults). The memory file **must not be modified** while the VM lives.
- Drives, TAPs and the vsock UDS must be **at the same paths** as in the original VM; the load API has `network_overrides` and `vsock_override` only (not drives) ([swagger](https://github.com/firecracker-microvm/firecracker/blob/v1.17.0/src/firecracker/swagger/firecracker.yaml)). Jailer gives each VM its own chroot so the in-chroot paths can be constant.
- **Vsock is reset across snapshot/restore**: existing connections are dropped (guest gets `TRANSPORT_RESET`), guest *listening* sockets remain. Network connections are not guaranteed to survive. So the guest agent must listen (host-initiated model), and the manager must reconnect after resume.
- **Clock**: wall-clock continues from the snapshot instant; the guest must be stepped to host time (docs point to a FAQ); `clock_realtime` on load advances kvmclock on x86. VMGenID makes Linux ≥ 5.18 reseed its PRNG on resume; userspace that seeded its own RNG before the snapshot (e.g. ssh-agent key material, language runtimes) is *not* reseeded ([doc §VMGenID](https://github.com/firecracker-microvm/firecracker/blob/v1.17.0/docs/snapshotting/snapshot-support.md#vmgenid-device-limitation)). For *same-VM* resume this is harmless; it matters only if we ever clone from one snapshot.
- Take the snapshot only after the guest kernel finished booting; cgroup v2 on host is strongly recommended (cgroup v1 restore latency is high).
- Snapshot format is versioned per Firecracker binary; **a Firecracker upgrade can strand warm snapshots** ([versioning](https://github.com/firecracker-microvm/firecracker/blob/v1.17.0/docs/snapshotting/versioning.md)). The manager must tolerate "snapshot unusable → cold boot", which falls out naturally from the warm/cold design.
- Balloon: `free_page_reporting` (pre-boot, guest needs `PAGE_REPORTING`), and `free_page_hinting` (developer preview) ([ballooning.md](https://github.com/firecracker-microvm/firecracker/blob/v1.17.0/docs/ballooning.md)). Firecracker's reference guest config already enables `PAGE_REPORTING`, `VIRTIO_BALLOON`, `VMGENID`, `VSOCKETS`, `OVERLAY_FS`, `SQUASHFS`, `VIRTIO_MEM` but **not `EROFS_FS`** ([config](https://github.com/firecracker-microvm/firecracker/blob/v1.17.0/resources/guest_configs/microvm-kernel-ci-x86_64-6.1.config)), so our kernel needs EROFS added if we choose erofs.

**Cost model.** A full snapshot's memory file is as large as the guest RAM (e.g. 4 GiB per suspended thread). Options to bound this: (a) warm TTL then cold (drop snapshot); (b) sparse-ify the memory file after writing (`fallocate --dig-holes`) and keep it on a filesystem with transparent compression; (c) diff snapshots once out of developer preview; (d) CH offload-daemon-style streaming compression if we switch VMM. I did not measure how much `free_page_reporting` shrinks a full snapshot file [unverified — needs a spike].

**Warm/cold lifecycle (recommended):**

| State | Exists on host | Wake path |
|---|---|---|
| running | VMM process | – |
| warm | state + memory file + disks | restore snapshot, step clock, agent reconnects |
| cold | disks only | boot kernel + erofs, agent starts |
| deleted | nothing | – |

wisp's README reports ~15 ms warm resume and ~200 ms cold boot to a responsive agent on a single host ([lifecycle.md](https://github.com/arugula-salad/wisp/blob/main/docs/lifecycle.md)); treat as indicative only and measure on our target host. Policy knobs for the admin/manager config: idle timeout before suspend, warm TTL, max running VMs, snapshot-disk budget. Keep-awake signals (in-flight exec, attached session, running background task) come from the guest agent; this is where "sandbox tasks the agent started" meets suspend (see candidate ticket on keep-awake semantics).

## 5. Workspace disk persistence

- **Recommended:** one sparse raw `ext4` image per thread (`workspace.img`, size from the resource profile) attached as a second virtio-blk device, mounted at `/workspace` (and a second image or the same one for the overlayfs upper dir of the root, so `pip install`/`cargo build` caches survive cold boot). The image lives with the thread; deleting the thread deletes the VM dir.
- **Place VM dirs on XFS (reflink) or btrfs**, so "new thread from environment template" is a `cp --reflink` of a pre-seeded workspace image instead of rerunning setup scripts. wisp's operations doc reports using reflink clones for this ([operations.md](https://github.com/arugula-salad/wisp/blob/main/docs/operations.md)).
- **Disk quota = image size** (fixed at creation, growable offline with `resize2fs`, online via block-device rescan: Firecracker supports "trigger a block device re-scan" per [README](https://github.com/firecracker-microvm/firecracker/blob/v1.17.0/README.md)). Firecracker 1.17 also adds opt-in virtio-blk discard for writable `Sync` drives, so deleted files can return space to the host sparse file ([CHANGELOG](https://github.com/firecracker-microvm/firecracker/blob/v1.17.0/CHANGELOG.md)).
- **Why not a shared directory:** Firecracker has none; Cloud Hypervisor's virtio-fs needs `memory shared=on`, which disables its `copyonwrite` restore and falls back to eager copy, and vhost-user devices are unsupported for `ondemand` restore ([snapshot_restore.md](https://github.com/cloud-hypervisor/cloud-hypervisor/blob/v54.0/docs/snapshot_restore.md)). It also gives the guest a path into host filesystem metadata (libkrun's README explicitly warns about this: [security notes](https://github.com/containers/libkrun#virtio-fs)).
- **Consequence:** the manager cannot read workspace files while the VM is running (ext4 is not shared). File upload/download/diff/PR-prep must go through the guest agent (waking a warm/cold VM if necessary), or mount the image read-only on the host while the VM is stopped (cold only; mounting guest-controlled ext4 on the host kernel is itself an attack-surface risk, so prefer the agent) [inference].
- Snapshots of a *running* disk: the block device backing files are `fsync`'d at snapshot time; for **backups** of a workspace, quiesce via agent `fsfreeze` then reflink-copy the image.

## 6. vsock control channel

- Firecracker's vsock: host side is a Unix socket `uds_path`. **Host→guest**: connect to `uds_path`, send `CONNECT <port>\n`, read `OK <hostport>`. **Guest→host**: guest connects to CID 2 port N, which reaches `uds_path_N` on the host if something listens ([vsock.md](https://github.com/firecracker-microvm/firecracker/blob/v1.17.0/docs/vsock.md)). Cloud Hypervisor implements the same scheme ([vsock.md](https://github.com/cloud-hypervisor/cloud-hypervisor/blob/v54.0/docs/vsock.md)), so the manager's transport is VMM-independent.
- **Recommended pattern:** the guest agent *listens* on a control port (survives snapshot/restore because listeners persist; connections do not), the manager dials per request. Guest-initiated listeners on the host are used only for the proxy path (§7).
- Agent as PID 1 (from the rootfs, no systemd), written in Go and statically linked, built in the same repo/flake. Responsibilities: mount the erofs/overlay/workspace, set hostname/env from the manager's boot config (cmdline or a small config over vsock), run commands with PTY/stdio streaming, file read/write/stat/glob, process lifecycle and signals, port watch, time sync after resume, reaping zombies, graceful shutdown, keep-awake report, resource usage (memory pressure → balloon decisions).
- Wire protocol is a #41 decision; Connect/gRPC over vsock is the obvious candidate (HTTP/2 streams map well to exec sessions). Authentication on this channel is "the VM boundary": per-VM UDS under a root-owned dir; no network exposure.
- Secrets must not travel in the kernel cmdline (visible in `/proc/cmdline` inside the guest and in logs). Deliver over vsock after boot, into agent memory/tmpfs; setup-only secrets are never persisted into a snapshot-able location [inference: anything in guest RAM is in the memory file; this is a risk for snapshot storage security, see §11].

## 7. Networking and egress

- **Default: no network device.** The agent opens a local proxy port inside the guest (e.g. `127.0.0.1:3128` and a transparent REDIRECT for TCP 80/443 if wanted) and tunnels each connection over vsock to a manager-side listener (`uds_path_<port>`), where the egress proxy (#25) makes the allow/deny decision per domain, injects credentials, and terminates/inspects TLS if needed. Properties:
  - No TAP, bridge, NAT, nftables, IP allocation, or netns per VM; nothing to leak between VMs; nothing to reconfigure on resume.
  - The guest cannot reach the host LAN, cloud metadata, or other sandboxes at L3 because it has no L3.
  - Limits: no UDP/ICMP, tools that ignore proxy settings need the in-guest redirect, DNS must be resolved by the proxy (the guest sends the hostname in `CONNECT`/SOCKS).
- **Fallback: TAP per VM** (Firecracker networking guidance in [network-setup.md](https://github.com/firecracker-microvm/firecracker/blob/v1.17.0/docs/network-setup.md)) with nftables allowing only `proxy_ip:port` and DNS-to-proxy, default drop. For same-VM resume the TAP name and guest IP stay constant; `network_overrides` exists if the TAP name must change. The "clone" problems (identical IP/MAC/TAP across clones, [network-for-clones.md](https://github.com/firecracker-microvm/firecracker/blob/v1.17.0/docs/snapshotting/network-for-clones.md)) do not apply unless we restore multiple VMs from one snapshot.
- Firecracker rate limiters exist per net and block device (token buckets for bandwidth and ops, [design.md](https://github.com/firecracker-microvm/firecracker/blob/v1.17.0/docs/design.md)); in the vsock-only design, bandwidth limits belong in the manager's proxy instead.
- Inbound (dev server preview): host→guest via the same vsock `CONNECT` mechanism, exposed by the manager as an authenticated tunnel; no port forwarding on the host (candidate ticket).

## 8. Resource limits

| Resource | Mechanism |
|---|---|
| vCPU, RAM | `machine-config` (`vcpu_count`, `mem_size_mib`; `smt`, `huge_pages`). Profile values come from the manager config (admin-defined, per the plan). |
| RAM elasticity | balloon with `deflate_on_oom`, `free_page_reporting`; `virtio-mem` hotplug in 1.17 ([swagger `/hotplug/memory`](https://github.com/firecracker-microvm/firecracker/blob/v1.17.0/src/firecracker/swagger/firecracker.yaml)). Balloon is cooperative: a compromised guest can ignore it, so the host must also cap via cgroup ([ballooning security disclaimer](https://github.com/firecracker-microvm/firecracker/blob/v1.17.0/docs/ballooning.md)). |
| Host-side hard caps | Jailer `--cgroup` (v2: `cpu.max`, `memory.max`, `io.max`, `pids.max`), `--resource-limit` (`fsize`, `no-file`), `--new-pid-ns`, `--netns`, `--uid/--gid` ([jailer.md](https://github.com/firecracker-microvm/firecracker/blob/v1.17.0/docs/jailer.md)). Parent cgroup for the whole manager so total sandbox use cannot starve the host. |
| Disk | image size + discard; optionally block rate limiter (bandwidth/ops). |
| Wall-clock / process | agent-side per-command timeouts, manager-side max-lifetime and idle policy; kill VMM on breach. |
| Concurrency | `max_running` in manager config; admission control returns "queued"/error to atrium. |

Host posture ([prod-host-setup](https://github.com/firecracker-microvm/firecracker/blob/v1.17.0/docs/prod-host-setup.md)): swap off (data remanence: guest memory can reach disk otherwise), cgroup v2, SMT/mitigation guidance, `kvm` module parameters. Cloud Hypervisor's [threat model](https://github.com/cloud-hypervisor/cloud-hypervisor/blob/v54.0/docs/threat-model.md) states the same assumptions (up-to-date kernel/microcode, mitigations, SMT off if necessary). The plan puts untrusted tenants out of scope, but the *content* the agent runs (prompt-injected code, dependencies) is adversarial enough to justify the full jailer setup rather than a bare `firecracker` process.

## 9. Nix: packaging, rootfs, kernel

**Packaging.**
- `firecracker` is in nixpkgs ([package.nix](https://github.com/NixOS/nixpkgs/blob/nixos-unstable/pkgs/by-name/fi/firecracker/package.nix)): 1.16.1 on unstable at check time, built from the workspace so `jailer` and `seccompiler` are included (`cargoBuildFlags = ["--workspace"]`). 1.17.0 needs an overlay or wait. `cloud-hypervisor` 54.0 and `virtiofsd` 1.14.0 are current.
- [microvm.nix](https://github.com/astro/microvm.nix) (MIT, active) declares *static* NixOS-defined VMs run as `microvm@.service`; for Firecracker it throws for shares, balloon, hotplug, credentialFiles ([runner](https://github.com/astro/microvm.nix/blob/main/lib/runners/firecracker.nix)). Our VMs are created dynamically by a Go service with per-thread state, so microvm.nix is the wrong abstraction for the runtime; it is a good reference for: kernel selection, erofs/squashfs store-disk building (`storeDiskType`, erofs flags `-zlz4hc -Eztailpacking -Efragments`), and the Firecracker JSON shape.
- **NixOS module for the manager** (ours): `services.atrium-sandbox-manager` with `enable`, `settings` (TOML), `package`, `firecrackerPackage`, kernel/rootfs artefact paths, state dir on an XFS/btrfs mount assertion, `/dev/kvm` access (`SupplementaryGroups=kvm`), the capabilities the jailer needs (`CAP_SYS_ADMIN` for mount/unshare, `CAP_MKNOD`, `CAP_SETUID/SETGID`, `CAP_NET_ADMIN` only for the TAP fallback) [inference: confirm against the jailer's actual syscall use], cgroup delegation (`Delegate=yes`), swap assertion, `boot.kernel.sysctl` for `vm.unprivileged_userfaultfd`/`/dev/userfaultfd` ACL if UFFD is used.

**Guest kernel.** Build with `linuxManualConfig` (or `kernel.override`) from Firecracker's `microvm-kernel-ci-{x86_64,aarch64}-6.1|6.18.config` (supported guest kernels per [kernel-policy](https://github.com/firecracker-microvm/firecracker/blob/v1.17.0/docs/kernel-policy.md)) plus `EROFS_FS`, `OVERLAY_FS`, whatever the agent needs. 1.17 also accepts `bzImage` on x86_64. The same kernel family boots under Cloud Hypervisor (PVH/bzImage) [inference], keeping the VMM swappable.

**Rootfs per toolset combination.**
- The manager host has Nix (plan: "Nix-built rootfs on the manager host"). Define in the manager's flake a function `mkImage { toolsets = [ "python" "go" ]; }` that returns an **erofs image** containing: the agent as `/init`, a small base (busybox/coreutils, bash, git, curl, ca-certificates, openssh client if needed), a `buildEnv` symlink farm exposing the chosen toolsets on `PATH`, and the closure at `/nix/store`. nixpkgs already has [`erofs-store-image.nix`](https://github.com/NixOS/nixpkgs/blob/nixos-unstable/nixos/lib/erofs-store-image.nix), `make-squashfs.nix`, `make-ext4-fs.nix` (all in `nixos/lib`).
- **Cache key = the sorted toolset set + toolset versions + base revision**, i.e. the Nix derivation hash. Nix itself caches builds; add GC roots per image used by an existing sandbox and a manager GC that drops images unreferenced for N days. The manager requests builds by calling `nix build` against a pinned flake and a generated expression (or `nix build --expr`), never from user-supplied Nix.
- Two layout choices:
  1. *One erofs per combination* (recommended for v1): simplest guest, one read-only device; combinations are few (4 toolsets → ≤ 15 non-empty sets, times pinned versions), and identical store paths dedupe in the builder's Nix store though not inside images.
  2. *Base + one erofs per toolset, overlayfs-merged at `/nix/store`*: less disk and one shared page cache per toolset, more guest init logic and more virtio-blk devices (Firecracker PCI device limit is 31 per the [unreleased changelog on main](https://github.com/firecracker-microvm/firecracker/blob/main/CHANGELOG.md)). Store paths are content-addressed so union-mounting disjoint directories is well defined [inference]. Keep as an optimisation.
- Writable layer: overlayfs with `upperdir` on the workspace/overlay ext4 so installs persist; `/tmp` as tmpfs (lost on cold boot, kept on warm).
- **Updating a toolset** (new nixpkgs revision) changes the image path; existing sandboxes keep their pinned image until the thread ends or the user rebuilds the environment. This needs an "environment image generation" notion in the data model (candidate ticket).
- Setup scripts and setup-only secrets: run once in a *build VM* from the environment's image → result is the workspace image (+ optionally a snapshot). New threads reflink-clone that result. This is the same template idea as e2b ([e2b-dev/infra `create-build`](https://github.com/e2b-dev/infra/tree/main/packages/orchestrator)).

## 10. Recommendation (tied to the plan)

1. **Firecracker as the sole v1 VMM**, wrapped in a `Hypervisor` interface (`Create`, `Boot`, `Pause`, `Snapshot`, `Restore`, `Resume`, `Balloon`, `Stats`, `Kill`) with a generated REST client over the UDS. Reasons: snapshot suspend is a first-class, documented feature; jailer is the best-documented containment story among the options; vsock UDS model is the simplest to orchestrate; minimal device model; 1-year patch-support policy; present in nixpkgs. Cloud Hypervisor is the designated second backend if (a) we need CPU/memory hotplug, (b) we want UFFD/COW restore to share memory across clones, or (c) Firecracker's snapshot format churn becomes painful.
2. **Warm/cold lifecycle** with admin knobs, **no NIC by default**, **vsock-only control + egress tunnel**, **ext4 workspace image on reflink FS**, **Nix-built erofs per toolset set**, **Nix-built kernel**.
3. **Hardware requirement stated in docs**: bare-metal or a VM with nested virtualisation (`/dev/kvm`), x86_64 (and aarch64 supported by Firecracker), XFS or btrfs for the state dir, cgroup v2, swap off, ≥ 1 core and 1–4 GiB RAM reserved per running sandbox plus the snapshot disk budget.
4. Keep gVisor, Kata and libkrun **out of v1**; document why in the manager design (no snapshot, extra stack, or weaker boundary).

## 11. Risks and open questions

- **Snapshots contain guest memory** — including any runtime secrets (GitHub token never enters the VM per the plan, but env secrets and Anthropic/pi/Claude Code credentials may). Memory files must be mode 0600, on a disk the manager owns, deleted with the thread; consider encrypting the state dir (LUKS/fscrypt) because the atrium DB is encrypted at rest (#40) while sandbox disks otherwise are not.
- **Firecracker upgrade invalidates snapshots**; policy: drain or cold-restart on upgrade; test matrix in CI uses the pinned binary.
- **Nested virtualisation** may be what "a beefier machine" is. Firecracker's CI is metal only; verify the target host (CPU model, `/dev/kvm`, provider) with a spike before committing.
- **Snapshot size/latency** at realistic guest RAM (2–8 GiB) is unmeasured here; the warm-resume numbers above are from a third-party project.
- **Developer-preview features** (diff snapshots, balloon hinting, PCI hotplug) should not be depended on in v1.
- **Crash consistency**: take disk snapshots only when the VMM is stopped or after agent `fsfreeze`; kill-9 of the VMM is equivalent to power loss for ext4 (journal replay on next boot).
- **Timer/clock and long suspends**: TLS certificates, token expiry, `git` credential helpers and scheduled in-guest jobs see a jump; agent should step the clock and inform running tools (SIGCONT-like hook).
- **Agent supply chain**: the guest agent binary runs as PID 1 as root in an untrusted-ish VM; it must treat all host messages as authenticated but guest data as hostile when forwarding.
- **License of dependencies**: Firecracker/CH/Go libs Apache-2.0 or MIT; QEMU is GPL-2.0 if ever bundled (relevant to #36).
