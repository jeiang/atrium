## 1. Answer in brief

1. **OpenAI API key through the gateway.** pi's `openai` provider speaks **only the Responses API**: one call, `POST {baseUrl}/responses` with `stream: true`, `store: false`, `maxRetries: 0` in the SDK and its own retry loop on top ([`openai-responses.ts`](https://raw.githubusercontent.com/earendil-works/pi/main/packages/ai/src/api/openai-responses.ts) lines 195-235, 320-330, 356-366). Chat Completions is used only for custom OpenAI-compatible endpoints (item 3). A gateway at `/gw/openai/v1/responses` (sibling of #25's Anthropic gateway) fits: per-sandbox bearer in, real key out, SSE tee. Usage arrives **only** in the terminal `response.completed`/`response.incomplete` event (`usage: null` in `response.created`/`in_progress`), so an aborted stream has no input-token count (unlike Anthropic's `message_start`): the gateway must estimate and flag the row `partial`. Pricing is a static table with per-model standard, Fast, Ultrafast and long-context (>272K input) rates and **cache-write** rates; billing is `uncached = input - cached - cache_write` per request. The big difference from Anthropic: OpenAI's **Admin API can create a project, a service-account key and a hard monthly project spend limit**, so a real provider-side backstop is programmable.
2. **ChatGPT/Codex subscription.** There is now an official route: **Sign in with ChatGPT (SIWC) "ChatGPT plan usage" for open-source/local apps**. pi implements it (provider `openai`, login "Sign in with ChatGPT", pi >= 0.99.0) and OpenAI lists pi as a supported open-source integration. The access token goes straight to `https://api.openai.com/v1/responses` with `store:false, stream:true`. In a NIC-less VM the login works by **pasting the redirect URL** back into pi's terminal prompt (loopback callback cannot reach the user's browser), so "terminal attach" is the right vehicle. Credentials (`auth.json`, rotating refresh token valid 30 days, 1 h access token) and a stable `deviceId` (host id, in pi's `settings.json`) can live on a **per-instance volume** mounted only into opted-in environments, exactly like Claude Code. OpenAI's terms say token storage must be "local and under the user's control, not in a remote or managed environment" and requests must come from "the user's local runtime or a remote runtime only that user controls": an owner-run manager satisfies this; the same terms forbid serving anyone else's requests with the plan. Atrium cannot meter these runs in dollars (they consume plan usage); show tokens and plan errors, not a budget.
3. **Self-hosted endpoint passthrough.** Not through the CONNECT proxy: a **separate manager listener** (own vsock port, fixed upstream from manager config, path/method allowlist, no redirects, IP pinned at config time) reached by an in-VM shim at `http://127.0.0.1:PORT/local/v1`. The private-address rule of the CONNECT proxy stays untouched (a CONNECT to that IP is still refused), so the exception is one route, one upstream, nothing a VM can steer. Metering: parse `usage` (chat completions) incl. the streaming `include_usage` chunk (llama.cpp supports it, [`server-task.cpp`](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/server-task.cpp) l.494), write rows with `cost_usd = 0`, `provider = 'local'`. **Finding that changes the premise:** the operator's current llama endpoint is 8192 context, one slot, thinking off, shared with mail jobs and paused while gaming ([cornn-flaek `modules/atrium/default.nix`](https://github.com/jeiang/cornn-flaek) l.87, 182-191, 143): it cannot host a coding agent as wired; the pi route needs its own endpoint setting.

Recommendations (detail in section 7): gateway for the API key (Phase B, with a request-body policy), subscription via pi's own SIWC login on the per-instance volume as the opt-in (S-A), atrium-held-token (S-B) deferred pending OpenAI's answer, passthrough as a manager route (with an atrium-hosted variant when the LLM is only reachable from atrium).

### 2.2 Gateway contract

Placement as in #25 section 5.2: atrium hosts the gateway, the manager relays from the VM over the existing mTLS channel, the instance OpenAI key never leaves the atrium host. VM side (no NIC, vsock shim per #25/round 2): `models.json` sets `providers.openai.baseUrl = "http://127.0.0.1:<shim-port>/gw/openai/v1"`; `OPENAI_API_KEY=<per-sandbox bearer>` (I suggest an `sk-atrium-...` shape so tools that sniff `sk-` behave; note pi's own sign-in detection needs `baseUrl == https://api.openai.com/v1`, so it cannot misfire against the gateway: [`isChatGPTSignIn`](https://raw.githubusercontent.com/earendil-works/pi/main/packages/ai/src/api/openai-responses.ts) l.42-49).

Policy the gateway should enforce (all `[inference]` unless cited):

- **Path/method allowlist**: `POST /v1/responses` only (+ `GET /v1/models` if a tool asks). Reject Files, Batch (`50%` priced), Fine-tuning, Realtime, Organization, Assistants, Containers, Vector stores: they bypass metering or spend elsewhere. `POST /v1/responses/input_tokens` and `/responses/compact` are not used by pi; decide when a second tool needs them.
- **Body policy**: parse JSON, then
  - require `model` in the price table (fail closed before spending anything);
  - reject `background: true`, `store: true`, `conversation`, `previous_response_id` (they create server state outside the ledger/ZDR posture) unless a tool requires them;
  - `service_tier`: default-deny `fast`/`priority`/`ultrafast`/`flex` (2x to 6x or discount rates; see 2.4) unless the environment allows; pi only sends it when its `serviceTier` option is set ([l.376](https://raw.githubusercontent.com/earendil-works/pi/main/packages/ai/src/api/openai-responses.ts));
  - **hosted tools**: allow `function`/`custom`/namespaces; deny `web_search` (priced $10/1k calls + content tokens), `file_search` ($2.50/1k + storage), `code_interpreter`/hosted shell (container-minute fees), `computer`, `mcp` connectors unless priced and enabled ([pricing: Tools](https://developers.openai.com/api/docs/pricing.md)). pi sends only function tools by default.
  - clamp/insert `max_output_tokens` from the environment's `max_output_tokens` setting (#80); `max_output_tokens` is a documented parameter on the API-key route (it is only rejected on the SIWC route, section 3.4).
- **Transport**: forward `Authorization` replaced by the real key; forward `OpenAI-Organization`/`OpenAI-Project` only from instance config; relay SSE unbuffered; request upstream identity encoding so the tee can parse; do not follow redirects; never forward client `Host`; strip hop-by-hop headers; relay `x-request-id`, `Retry-After`, `x-ratelimit-*` (documented in [rate limits](https://developers.openai.com/api/docs/guides/rate-limits.md)).
- **Identity**: per-sandbox bearer, ideally bound to the vsock CID/tap as in #25 candidate 9; revoke by deleting the bearer.
- **Refusal contract**: return an OpenAI-shaped error with HTTP 429 and `error.code = "insufficient_quota"` (or message containing "out of budget"/"quota exceeded"). pi's retry classifier tests a non-retryable pattern first (`insufficient_quota`, `out of budget`, `quota exceeded`, `billing`) and returns "not retryable" before it considers `429`/`rate limit` ([`retry.ts`](https://raw.githubusercontent.com/earendil-works/pi/main/packages/ai/src/utils/retry.ts) l.7-28, 265-269), so a budget stop ends the run instead of being retried for minutes. This is directly verified in source; the Anthropic equivalent in #55 is still `[inference]`.

### 2.3 Usage fields and parsing rules (spec for the Go adapter)

Source of truth: [Responses create reference](https://developers.openai.com/api/reference/resources/responses/methods/create.md) (`ResponseUsage`), [Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching.md), [Pricing](https://developers.openai.com/api/docs/pricing.md).

1. **Fields**: `usage.input_tokens`, `usage.input_tokens_details.{cached_tokens, cache_write_tokens}`, `usage.output_tokens`, `usage.output_tokens_details.reasoning_tokens`, `usage.total_tokens`; also response-level `service_tier` ("the processing mode actually used", may differ from the request) and `model` (snapshot id). `input_tokens_details` is "a detailed breakdown of the input tokens" and `output_tokens_details` a breakdown of output: both are **subsets**, so reasoning tokens are already inside `output_tokens` (pi does the same: output = `output_tokens`, reasoning reported separately).
2. **Billing buckets (GPT-5.6 and later)**: "Cache-write pricing is not an additive fee: input tokens use the uncached-input, cached-input, or cache-write rate" ([prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching.md)). So `uncached = input_tokens - cached_tokens - cache_write_tokens`; cost = `uncached*in + cached*cached_in + cache_write*write + output*out`. Cache write = 1.25x input, read = 0.1x (0.05x on GPT-6.1 Sol). Earlier models have no write charge.
3. **Where usage appears in a stream**: only on the terminal event. `response.created` and `response.in_progress` carry `"usage": null` (example stream in the reference). Terminal events: `response.completed`, `response.incomplete` (pi reads usage from both; `incomplete_details.reason` e.g. `max_output_tokens`), `response.failed` (no usage read by pi; the Response object has an optional `usage`, `[inference]` it may be null on failures). A request that ends `incomplete` was still generated and billed.
4. **Aborted/failed streams**: no terminal event means no usage, and "does not mean that no tokens were used" is OpenAI's wording for the Chat Completions streaming usage chunk ([chat streaming events](https://developers.openai.com/api/reference/resources/chat/subresources/completions/streaming-events.md) l.396-398: "If the stream is interrupted or cancelled, you may not receive the final usage chunk"). I found no primary statement on what a closed Responses connection bills `[unverified]`; assume input plus generated output so far. Rule: record `partial=1`, `estimated=1`, input estimated from the request (see below), output estimated from streamed deltas (bytes/4 `[inference]`), and let the Admin API reconciliation (2.6) true it up. There is no `message_start`-style input count to lean on.
5. **Estimating input for admission and for partial rows**: pi sends `session_id`; keep per-session the last settled `input_tokens` and add `len(new tail)/3.5` `[inference]`; first request of a session: `len(body)/3` as an upper-ish bound. Do not ship a tokenizer for the 6-series unless the estimate proves too loose (candidate ticket).
6. **Tier from usage**: price `service_tier` from the **response**: `default`/`auto` standard; `priority` (Fast) uses the Fast table (the response says `priority` even when `fast` was requested, [fast mode](https://developers.openai.com/api/docs/guides/fast-mode.md)); `flex` the Flex table; `ultrafast` the Ultrafast table (only `gpt-6-astra`, `gpt-6.1-sol` listed). A Fast request can be downgraded to `default` and billed standard ("response contains `service_tier: default`").
7. **Long context**: "Short context: <=272K input tokens. Long context: >272K input tokens", per request. Which count (`input_tokens` including cached/written) decides is not spelled out `[unverified]`; use total `input_tokens` (same as Anthropic's Haiku rule in #55) and let the Costs API show any delta.
8. **Alias to snapshot**: `response.model` may be a dated snapshot of the requested alias; map by prefix to the table, else unknown (rule 10).
9. **Hosted tools**: web search calls counted from `web_search_call` output items `[inference on the item type]`; container time is not in `usage` (billed per session, 5-minute minimum): another reason to deny them (2.2).
10. **Unknown model**: fail closed twice: the gateway rejects unknown `model` strings at admission; if a response nevertheless carries an unmapped `model`, price at the **highest per-category rate in the Standard table for the observed tier** (today `gpt-6-astra` long-context: $20 in / $25 write / $75 out per 1M, Fast table $40/$50/$150) and set `unpriced=1`. Never price at zero.
11. **Dedupe/attribution**: unique on the upstream `x-request-id` header (and `response.id`); persist `session_id` header, sandbox/thread/run, provider=`openai`, source=`gateway`.
12. **Compaction**: server-side `context_management` (`compact_threshold`) exists, but pi does not use it and the compaction guide does not say how its tokens appear in `usage` ([compaction](https://developers.openai.com/api/docs/guides/compaction.md)): `[unverified]`, capture a recorded stream before enabling it for any tool.
13. **Errors**: 429 `rate_limit_error`/`slow_down` and 503 `server_is_overloaded` carry `Retry-After`; hard project limit returns `project_spend_limit_exceeded` (help-center wording, `[unverified]` in primary API docs); no usage on non-2xx.

4. Reconcile against the Costs API (2.6) to catch rules the tables miss (long-context counting, promos).

### 2.5 Ledger fit, reservations, kill switches

- **Ledger (#80, [round 3](https://github.com/jeiang/atrium/issues/80))**: one row per request with `iterations`, `source`, unique `request_id`, `partial`, `unpriced`. Additions needed for this ticket: `provider` (`anthropic|openai|local|chatgpt_plan`), `cache_write_tokens` as a first-class column (Anthropic has 5m/1h buckets; OpenAI one), `reasoning_tokens`, `service_tier`, `estimated` flag, and `source` values `gateway_openai`, `chatgpt_plan`, `local_llm`. `iterations` stays Anthropic-only.
- **Reservation (admission)**: at request time reserve `est_input * rate_for_tier + max_output * out_rate` (max_output = clamped value or the model's 128K). Settle at the terminal event, release on abort and settle again from reconciliation. Same L1-L7 layering as #55 section 5.1; **new layer L8': provider-side hard cap**.
- **Provider-side backstop that Anthropic lacks**: the Admin API (organization **Admin key** required, owners only) has `POST /v1/organization/projects/{project_id}/spend_limit` (hard limit, `threshold_amount` in cents, `interval: month`, `enforcement.status: inactive|enforcing`), spend alerts (email only), project service accounts and `POST .../service_accounts/{id}/api_keys` with `name`, `scopes` (example `["api.responses.write"]`) and `expires_in_seconds` up to one year ([spend limit](https://developers.openai.com/api/reference/resources/admin/subresources/organization/subresources/projects/subresources/spend_limit/methods/update), [service account key](https://developers.openai.com/api/reference/resources/admin/subresources/organization/subresources/projects/subresources/service_accounts/subresources/api_keys/methods/create), [spend alert](https://developers.openai.com/api/reference/resources/admin/subresources/organization/subresources/projects/subresources/spend_alerts/methods/create)). Enforcement "is not instantaneous" so spend can slightly exceed (help center: [troubleshooting spend limits](https://help.openai.com/en/articles/6614457-troubleshooting-api-usage-and-spend-limits), secondary). Recommendation: **a dedicated OpenAI project for atrium sandboxes, a least-scope service-account key as the instance key, and (if the owner supplies an Admin key) atrium sets the project hard limit to the instance's monthly budget** (monthly granularity only). Scope names beyond the example are `[unverified]`.
- **Per-sandbox keys** are creatable (service-account keys with expiry) and would give per-key attribution in the Usage API, but the key would then be a secret per sandbox stored in atrium (still never in the VM). Marginal over the gateway ledger; skip unless an auditor-grade independent split is wanted `[inference]`.

### 3.2 Mechanics in a NIC-less microVM

pi flow (source read from `main`):

1. In an **interactive** pi session (`/login` -> OpenAI -> "Sign in with ChatGPT"), pi needs a device id: `getDeviceId` is wired only in interactive mode ([`interactive-mode.ts` l.6349](https://raw.githubusercontent.com/earendil-works/pi/main/packages/coding-agent/src/modes/interactive/interactive-mode.ts)); it creates a random UUID once and stores it in **global settings** (`settingsManager.getOrCreateDeviceId`, [`settings-manager.ts` l.1083-1088](https://raw.githubusercontent.com/earendil-works/pi/main/packages/coding-agent/src/core/settings-manager.ts)) and sends `ext_agent_host_id=urn:uuid:<id>`. So login is a terminal-attach job, not an RPC-mode job.
2. pi starts a callback server on `127.0.0.1:1455` (fixed port; fails with a port-in-use error otherwise; `PI_OAUTH_CALLBACK_HOST` changes the bind host) and prints the authorization URL plus a prompt "Complete login in your browser, or paste the final redirect URL here".
3. The user opens the URL on their own machine, signs in, chooses workspace, and consents to **"Use your ChatGPT plan"**. The browser then redirects to `http://127.0.0.1:1455/auth/callback?code=...&state=...&client_id=oaiapp_...`. That address is the user's own loopback, not the VM's, so it fails to load; the user **copies the URL from the address bar and pastes it into the terminal**. pi validates origin and path (`The pasted callback URL must start with http://127.0.0.1:1455/auth/callback`) and the `state`. This is the documented headless route ("paste the final redirect URL or authorization code back into Pi": [providers.md](https://raw.githubusercontent.com/earendil-works/pi/main/packages/coding-agent/docs/providers.md#authenticate-interactively)); OpenAI's own guidance for self-hosted VMs is the same shape: complete OAuth where the browser is, then get the credential file to the VM ([self-hosted VMs](https://developers.openai.com/siwc/token-sharing-open-source/self-hosted-vms.md)).
4. pi exchanges the code at `https://auth.openai.com/api/accounts/oauth/token` (needs egress), checks that the grant includes `chatgpt.tokens.use.direct`, stores `{access, refresh, expires, clientId, scopes}` in `auth.json` (mode 0600), refreshes with `grant_type=refresh_token&resource=https://api.openai.com/v1` (and `refresh_token_*` errors force re-login).
5. Every later run (RPC/JSON/print) uses `auth.json` with silent refresh. No further paste.

Alternative to pasting into a terminal: an **atrium web form** that writes the pasted URL to the PTY (UI work, candidate 4), or an atrium-native OAuth client (S-B below) where atrium's web page is the paste target. Either way no port forward is needed.

Egress needed (per environment, owner-editable): `auth.openai.com` (login, refresh), `api.openai.com` (inference, `/v1/models`); in API-key-through-gateway mode neither (only the gateway). Also `pi.dev` for catalog refresh unless `PI_OFFLINE=1`. The user's browser, not the VM, visits `chatgpt.com` for the usage page.

### 3.3 Where the credential lives; refresh; concurrency

- Files (pi): `<agent-dir>/auth.json` (credentials; agent dir = `PI_CODING_AGENT_DIR`, default `~/.pi/agent`: [configuration.md](https://raw.githubusercontent.com/earendil-works/pi/main/packages/coding-agent/docs/configuration.md)), `<agent-dir>/settings.json` (`deviceId`). Both must be on the **same per-instance volume** or the host id and the credential diverge.
- **Per-instance volume, opt-in per environment: yes, it works** and matches the round-4 Claude Code decision. It is the shape OpenAI's "self-hosted VMs" page describes (credential file on the user's VM, "let the VM manage token refreshes", "use its own host ID"). The host is "where an instance of your tool runs ... Your app defines what counts as one host and when its lifecycle begins and ends" ([overview](https://developers.openai.com/siwc/token-sharing-open-source.md)): per **instance volume**, not per thread VM, so deleting a thread's sandbox neither creates a new host nor needs a re-login.
- **Token lifetimes**: access token 1 h; refresh token 30 days, rotated and extended on every refresh ([token reference](https://developers.openai.com/siwc/token-sharing-open-source/token-reference.md)). An instance unused for 30 days needs a fresh login. The doc says to "serialize refreshes for the same session so two processes do not race a rotating token" ([accounts and sessions](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions.md)); a reused refresh token is an error (`refresh_token_reused`).
- **Concurrency across VMs**: pi serializes with `proper-lockfile` (mkdir-based lock, 30 s stale) around `auth.json` ([`auth-storage.ts`](https://raw.githubusercontent.com/earendil-works/pi/main/packages/coding-agent/src/core/auth-storage.ts)). That protects processes sharing one filesystem; two microVMs mounting the same volume concurrently rely on the share (virtiofs/virtio-blk) implementing atomic `mkdir` and coherent reads `[unverified, must be tested]`. Safe policies: (a) one subscription-mode sandbox at a time per instance; (b) the manager mounts the volume read-write into exactly one VM and exposes `auth.json` as a copy-in/copy-out; (c) refresh in the manager (needs the token on the manager). Recommend (a) for v1, with the manager rejecting a second opted-in sandbox start while one is running.
- Never store it in the atrium DB or echo it in the UI (consistent with #32 section 5). Revocation: user disconnects the app in ChatGPT Settings > Security and login; OpenAI does not notify the app ([errors](https://developers.openai.com/siwc/token-sharing-open-source/errors-and-recovery.md)), and `/logout` in pi removes the local credential without revoking it ([providers.md](https://raw.githubusercontent.com/earendil-works/pi/main/packages/coding-agent/docs/providers.md#authenticate-interactively)); OpenAI documents revocation through the discovery document's `revocation_endpoint` with the refresh token ([accounts and sessions](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions.md#end-the-renewable-session)); pi's `/logout` does not revoke, so atrium's "disconnect" action should do it.

### 3.4 What the subscription route permits and limits

From [preview limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations.md), [errors and recovery](https://developers.openai.com/siwc/token-sharing-open-source/errors-and-recovery.md), [help: using your plan in other apps](https://help.openai.com/en/articles/20001542-using-your-chatgpt-plan-in-other-apps-and-sites), [profiles and sessions](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions.md):

- **API surface**: `POST /v1/responses` (and `GET /v1/models` for the account's catalog: `models[].slug/display_name/visibility`) only; `store:false`, `stream:true`; `input` array; use `instructions` or developer messages (no `system` role items); **omit** `background, conversation, max_output_tokens, max_tool_calls, metadata, moderation, multi_agent, prompt, prompt_cache_retention, safety_identifier, temperature, top_logprobs, top_p, truncation, user`, and `previous_response_id` over HTTP. Unsupported: image generation, file search, Code Interpreter, native computer use, hosted MCP/connectors, `tool_search`. pi handles this itself when it detects the sign-in (it drops `prompt_cache_retention`, `prompt_cache_options`, `max_output_tokens`, `temperature`: [l.356-374](https://raw.githubusercontent.com/earendil-works/pi/main/packages/ai/src/api/openai-responses.ts)), **but only when `baseUrl` is exactly `https://api.openai.com/v1` and the key does not start with `sk-`**. Anything in the middle (a gateway) must do this sanitising itself (S-B).
- **Models**: whatever the account lists (examples use `gpt-6.1-sol`); pi hides classifier models and the Decisions API for OAuth logins ([`openai.ts`](https://raw.githubusercontent.com/earendil-works/pi/main/packages/ai/src/providers/openai.ts)); pi's context-window metadata for Codex backends (272K vs 500K) has moved repeatedly in the changelog, so do not hard-code context sizes.
- **Plans**: ChatGPT Go/Plus/Pro for "participating commercial apps"; "Supported open-source tools remain available to all ChatGPT users" (help article above). Plus has a **five-hour limit shared across all apps**; Pro has none. The user can set a **weekly per-app limit (10-100%)** in ChatGPT Settings > Usage and choose whether apps may use credits after plan limits (off by default, needs app limit 100%) ([help](https://help.openai.com/en/articles/20001542-using-your-chatgpt-plan-in-other-apps-and-sites)).
- **Errors** (stop inference; OpenAI does not fall back to another billing path): 401/403 admission, `subscription_sharing_usage_limit_exceeded` (429, resets in hours; pi treats it as non-retryable: [`retry.ts` l.24-27](https://raw.githubusercontent.com/earendil-works/pi/main/packages/ai/src/utils/retry.ts)), `subscription_sharing_usage_unavailable` (503), `subscription_sharing_unsupported_capability` (400, `error.param`), `subscription_sharing_user_not_eligible` (403), `..._route_not_supported`, `..._invalid_user` (401), `chatpass_v2_*` (403). Errors can arrive as `response.failed` after streaming began.
- **No dollar cost; no public API for plan balance**. Atrium can show per-run token counts from pi (`get_session_stats`, `message_update.usage`) and an "API-equivalent" estimate, a "Using ChatGPT plan / Manage usage" link to `https://chatgpt.com/settings/usage` (OpenAI's UI guideline), and the last plan error. It cannot cap spend in dollars; it can cap turns and wall clock (#55 L5-L7).

## 4. Item 3: manager-side passthrough to the operator's self-hosted endpoint

### 4.1 Facts about the endpoint today

- Atrium reaches the local models by two env URLs (`ATRIUM_CHAT_URL`, `ATRIUM_EMBED_URL`; `src/atrium/config.py:58-59,95-96`), calls `POST {url}/chat/completions` with `temperature: 0`, `cache_prompt`, `chat_template_kwargs.enable_thinking=false`, strict `json_schema` (`src/atrium/llm.py:71-86`), through `post_json` with no auth header (`src/atrium/http.py:12-22`).
- Host wiring (cornn-flaek `modules/atrium/default.nix`): llama.cpp on `127.0.0.1:8187` (chat) and `:8188` (embed) (l.10-11, 117-118), **no `--api-key`**, **`--parallel 1`** (l.87), chat model Qwen3.5-9B Q4_K_M with `--ctx-size 8192` and thinking disabled (l.182-191), units are in `gaming.pauseUnits` (l.143, so the endpoint disappears while the owner games).
- So: the endpoint is on the **atrium host's loopback**, serves mail classification, and is far too small for a coding agent (pi's system prompt plus tool schemas and file reads exceed 8K quickly `[inference]`).

### 4.2 Two topologies; the route differs

| | LLM reachable from atrium | LLM reachable only from the manager host |
|---|---|---|
| Route | **atrium-hosted** `/gw/local/v1/...` on the same gateway as the Anthropic/OpenAI routes (VM -> shim -> manager -> mTLS -> atrium -> LLM). **No private-address exception exists anywhere in the manager.** | **manager-hosted** listener (below); the manager posts usage records to atrium over the existing channel |
| Metering | Direct write to the ledger | Manager buffers rows and atrium ingests (needs an ingest API; the same needed for any manager-side tool) |
| Fit to the round-4 wording ("manager-side passthrough") | Satisfies the intent (the exception disappears) but is not manager-side | Literal |

Recommendation: build the manager-side route as decided, and make the **upstream target a manager setting** (`[local_llm] upstream = "http://127.0.0.1:8187/v1"`, bearer file), with the atrium-hosted variant allowed as an alternative `upstream = "atrium"` when atrium can see the LLM and the manager cannot. The common case (atrium host = LLM host, manager elsewhere) is the atrium-hosted variant; flag this to the owner as a simplification (candidate 9).

### 4.3 Manager-side route spec

- **Listener**: a dedicated vsock port per sandbox (or a mux path), separate from the CONNECT proxy. In the VM a shim listens on `127.0.0.1:<port>` and speaks plain HTTP; pi's `models.json` points an `openai-completions` provider at `http://127.0.0.1:<port>/local/v1` with a placeholder `apiKey` ([models.md](https://raw.githubusercontent.com/earendil-works/pi/main/packages/coding-agent/docs/models.md#configure-a-compatible-endpoint)).
- **Fixed upstream**: scheme/host/port from manager config only; the request cannot name a destination. Resolve at config load (and on SIGHUP), pin the IP, dial that IP; no redirects; `Host` rewritten; request size cap; per-sandbox concurrency 1 and a global queue (`--parallel 1` means one request at a time, and mail jobs must not starve).
- **Authentication**: VM-side per-sandbox bearer (or vsock CID binding) to the manager; manager-side the upstream API key from a `*_file` secret (`llama-server --api-key-file` is supported: [server README](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/README.md) l.213-214). The key never enters the VM.
- **Scope of the exception** (the ticket's last sub-question): (1) the CONNECT proxy's private-address refusal and `169.254.169.254` block are unchanged, so a CONNECT to the LLM IP/port is still rejected; (2) the nftables rules stay default-drop; (3) the route has exactly one upstream; (4) the manager process, not the VM, dials it; (5) the route is off unless the environment opts in. No general private-network access exists for the VM.
- **Path allowlist** (important: llama-server exposes admin endpoints): allow `POST /v1/chat/completions`, `POST /v1/completions`, `POST /v1/embeddings` (only if wanted), `GET /v1/models`, `GET /health`. **Deny** `POST/DELETE /models` (download/delete), `POST /models/load|unload` (router), `POST /props`, `/slots/*`, `/lora-adapters`, `/metrics`, `/v1/chat/completions/control`, `/tokenize` unless needed ([server README](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/README.md) endpoint list, l.837-2300). This also means pi's built-in `llama.cpp` router extension (which loads/unloads/downloads models through `/models*`) must be disabled in the VM (`-builtin:llama.cpp`, [llama-cpp.md](https://raw.githubusercontent.com/earendil-works/pi/main/packages/coding-agent/docs/llama-cpp.md)) and replaced by a generated `models.json` provider.
- **Body policy**: pin `model` to the configured id(s); clamp `max_tokens`; reject `stream_options` absent for streaming and add `{"include_usage": true}` (llama.cpp emits a final empty-`choices` chunk with `usage` when set: `server-task.cpp` l.494-504; pi sends it by default via compat `supportsUsageInStreaming: true`, [models-configuration](https://raw.githubusercontent.com/earendil-works/pi/main/packages/coding-agent/docs/models-configuration.md)).
- **Metering at zero cost**: parse `usage.{prompt_tokens, completion_tokens, total_tokens, prompt_tokens_details.cached_tokens}` from the JSON or the final SSE chunk, and optionally llama.cpp's `timings` (`prompt_n`, `cache_n`, `predicted_n`, ms) ([server README](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/README.md) l.1426-1470). Write a ledger row with `provider='local'`, `source='local_llm'`, `cost_usd=0`, `unpriced=0`, tokens recorded, `partial` on abort (no usage -> estimate or zero with `partial=1`). Zero-cost rows never count toward the budget and are shown in a separate "local" column.
- **Failure**: upstream down (e.g. gaming pause) returns an OpenAI-shaped 503 with `Retry-After`; pi retries transient errors with backoff ([`retry.ts`](https://raw.githubusercontent.com/earendil-works/pi/main/packages/ai/src/utils/retry.ts)).
- **Context/quality**: needs a larger context, tools-capable chat template (`--jinja`), and probably a different model than the mail one; endpoint settings must be separate from the mail URLs (candidate 10). Whether any 9B-class local model is useful for coding is #32 candidate 7.

## 6. Risks and unverified items

- SIWC is a preview, API-shape and limits can change; terms dated 2026-09-29. The open-source allowance is explicitly for "open-source projects, personal projects that run locally"; whether a self-hosted instance with a remote sandbox host is fully inside it is `[inference]`; there is no primary statement about remote VMs beyond the "remote runtime only that user controls" clause and the self-hosted-VM guide.
- Refresh-token rotation races between concurrent VMs sharing one volume (3.3) `[unverified]`; mkdir-lock semantics on the share not tested.
- A prompt-injected agent in the VM can read `auth.json` (S-A): damage is limited to the owner's plan usage plus whatever egress hosts are open; the refresh token lives 30 days and can be revoked in ChatGPT Settings.
- Aborted Responses streams: billing for generated tokens after disconnect is not stated in a primary source I could read; estimation + reconciliation only.
- Long-context counting, Fast-tier downgrade accounting, promotional pricing windows and cache-write rounding are table-driven and need recorded fixtures + Costs API checks.
- `insufficient_quota` as a refusal is verified against pi's regex only; other OpenAI-compatible clients may retry differently.
- The service-account key `scopes` vocabulary and Admin key handling (a high-privilege secret) were not fully read; storing an Admin key in atrium has its own risk and belongs behind the encrypted-DB ticket.
- OpenAI's "ChatGPT plan usage" has a "no charge/free" requirement and UI guidelines (show "Using ChatGPT plan", Manage usage link) that atrium's UI must follow if atrium ever becomes the SIWC client.
- pi on a ChatGPT login has context-window metadata that has changed several times ("272K vs 500K" in the changelog): do not trust a fixed number.
- Nothing here was exercised against live services (no keys, no accounts): everything is from documentation and source.
